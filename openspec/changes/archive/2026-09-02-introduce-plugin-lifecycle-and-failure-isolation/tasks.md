## 4. Migration linter

- [x] 4.1 Implement the CI migration linter (blocks `RemoveField`, `DeleteModel`, nullability-narrowing without a default, unless explicitly marked maintenance-mode). — Built on `django-safe-migrations` (already a `core/backend` dev dependency, already added to `INSTALLED_APPS` in `environments/development.py`, but previously unconfigured) rather than hand-rolling an operation-walking linter: its `SM002`/`SM003` rules already detect `RemoveField`/`DeleteModel`, its `SM020` already detects `AlterField` narrowing nullability (`null=True`→`False`, unconditionally — Django's `AlterField` can't safely backfill existing NULLs, default present or not, so "without a default" doesn't need separate handling), and its built-in `# safe-migrations: ignore SM002 -- <reason>` inline comment is exactly the "marker ... with a required justification comment" design.md calls for. Added `SAFE_MIGRATIONS = {'WARNINGS_AS_ERRORS': ['SM002', 'SM003'], 'EXCLUDED_APPS': [...]}` to `environments/development.py` — SM002/SM003 ship as WARNING upstream, so promoting them is what actually makes them build-failing; SM020 is already ERROR severity upstream, needing no promotion. Added `.github/workflows/migration-lint.yml` (this repo had zero CI infrastructure previously) running `poetry run python -m django_safe_migrations.cli --diff origin/<base-ref> --format=github` — diff mode only, so the linter checks migrations newly introduced by a PR rather than retroactively failing on pre-existing destructive migrations already in history (e.g. `catalog/migrations/0012_catalog_entity_identity.py`). Note for local use: the `check-migrations` console script doesn't add the cwd to `sys.path`, so it can't import `server.settings` — `python -m django_safe_migrations.cli` does (documented in `core/backend/README.md`).
- [x] 4.2 Verify it blocks a synthetic destructive migration and allows an explicitly-marked one. — Covered by `test_migration_lint.py` (`server/apps/plugins/tests/`): synthetic `RemoveField`/`DeleteModel` migrations written to real temp files (suppression-comment and operation-line lookup both re-read the migration's source file by path, so a real file is needed, not an in-memory object) and run through `MigrationAnalyzer.analyze_migration` directly, asserting `SM002`/`SM003` are raised and are in the promoted `WARNINGS_AS_ERRORS` set; a third case with an inline `# safe-migrations: ignore SM002 -- <reason>` comment confirms the issue is suppressed. Additionally hand-verified the full CLI end-to-end against a real (throwaway, never committed) destructive migration dropped into `atlas.database-schema`: unmarked, `--diff HEAD` exits 1 with the `SM002` warning; with the inline marker added and staged, it exits 0.
- [x] 4.3 Add the cross-plugin migration-dependency check. — Added `manage.py check_migration_boundaries` (`server/apps/plugins/management/commands/`): maps each plugin-owned Django app label to its plugin id via `PluginDescriptor.django_apps` (same `resolver.load_selected_descriptors` + app-config-by-name pattern as `purge_plugin`), walks every on-disk migration's `dependencies` via `MigrationLoader(None, load=False).load_disk()` (no DB connection needed), and flags a plugin migration that depends on another plugin's app label. Core (`atlas.catalog`) is exempt on both sides of the check — neither "a plugin's migration depends on Core" nor "Core's migration depends on a plugin" is a violation, since the spec's literal wording constrains *plugin* migrations only and Core's own history already, deliberately, depends on `ingestion` (`CatalogEntity.ingested_from`). Verified clean against the real migration history (`test_no_cross_plugin_dependencies_in_the_real_migration_history`) plus unit tests of the pure `_violation_for`/`_find_violations` logic against synthetic plugin/dependency data (own-history allowed, Core-as-target allowed, Core-as-source exempt, cross-plugin flagged). Wired into `migration-lint.yml` alongside 4.1's check.
