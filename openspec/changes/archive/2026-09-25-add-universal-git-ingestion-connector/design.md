## Context

`plugins/ingestion/backend/atlas_plugin_ingestion/connectors/github.py` hardcodes `GITHUB_API_BASE = 'https://api.github.com'` and is the only registered implementation of the `atlas.ingestion.connectors.v1` extension point (`pipeline.py` imports its `CONNECTOR_ID` directly rather than choosing per repository). `RegisteredRepository` (`models.py`) stores `full_name` (`owner/repo`) and `access_token` (plaintext `CharField`) — GitHub-shaped, unencrypted, with no outbound-destination validation on the requests the connector makes. The archived `extract-ingestion-plugin` design explicitly deferred "adding a second connector" as a Non-Goal, even though the `SourceConnector` ABC (`connectors/base.py`) was written to support one.

No example demonstrates ingestion end to end; `examples/authentication/` has four runnable examples with a shared compose/bootstrap/README shape (`examples/authentication/oauth2-gitea/` is the closest template: health-gated one-shot bootstrap containers, a Docker-volume-mounted runtime-secrets file, a scenario-driven README).

The project already has a working pattern for deployment-level secrets: `PluginConfigSchema` + `SecretRef`/`resolve_secrets` (`plugin-api/python/atlas_plugin_api/config.py`), used today by `atlas.auth.gitea`/`atlas.auth.oidc` for OAuth client secrets, and a working pattern for outbound-destination validation: `allowedDestinations`/`allowDevelopmentHttp` on provider config (`plugins/auth-gitea/backend/atlas_plugin_auth_gitea/config.py`).

## Goals / Non-Goals

**Goals:**
- One connector implementation that ingests from any git host reachable over HTTPS or SSH, with no per-provider branching.
- Zero ingestion credentials stored in the database, ever.
- No subprocess invocation anywhere in the fetch path (removes the `ext::`-transport and SSH-argument-injection classes by construction, not by allowlisting).
- A runnable example proving the above against a self-hosted git service (Gitea), including the parts of the operator journey (Django admin access, manifest editing, re-running ingestion) that the existing auth examples don't fully cover for ingestion's needs.

**Non-Goals:**
- Rewriting anything downstream of discovery/fetch — parsing (`parsing.py`), validation (`validation.py`), claim arbitration, and upsert through the Entity Service are unchanged.
- Building an in-app UI for managing sources or registered repositories; Django admin remains the operator surface for `RegisteredRepository`, and the manifest remains the surface for `sources`.
- Supporting anonymous `git://`, `file://`, or arbitrary git transport helpers — only `https://`/`http://` and `ssh://` are supported transports.
- Push/webhook-based ingestion triggering; the existing poll-based `ingestor` scheduler (`runapscheduler.py`) and the one-off `manage.py ingest` command are unchanged as trigger mechanisms.
- Retrofitting encryption onto unrelated plaintext secrets elsewhere in the codebase. This change removes the *need* for a database-stored ingestion credential; it does not audit or fix other secret storage.
- Preserving existing `RegisteredRepository` rows across the migration. No production deployment of `atlas.ingestion` is known to exist; only tests and (after this change) the new example reference the model, so the migration is destructive rather than data-preserving. Flag this assumption for confirmation before implementation.

## Decisions

### One universal `GitConnector` via shallow clone, not one connector per provider
Git's smart HTTP and SSH wire protocols are the same regardless of host; what differs between GitHub/GitLab/Bitbucket/Gitea is their *REST API* shape (pagination, auth header conventions, JSON schema), which is exactly what the current `GitHubConnector` couples to. Cloning `--depth 1 --single-branch` and reading the manifest off disk removes that coupling entirely — `list_manifest_paths` becomes `os.walk`, `fetch_file` becomes `open()`, `get_head_sha` becomes the clone's resolved `HEAD`. It also collapses the current N+2 REST calls per repository per pass (one `commits/{branch}`, one `git/trees`, one `contents` per manifest) into a single clone operation.

*Alternative considered:* implement `GitLabConnector`, `BitbucketConnector`, `GiteaConnector` alongside `GitHubConnector`, each against its own REST API. Rejected: four APIs to track (pagination, rate limits, auth conventions, response shapes each different), versus one wire protocol that's already uniform. This also directly satisfies the "second connector" work the original design explicitly deferred, in one implementation instead of three.

### `dulwich` + `paramiko`, not subprocess `git`/`ssh`
Git's own `ext::<command>` transport helper is a known command-injection primitive if any part of a clone URL is influenced by data an operator (not necessarily a trusted developer) entered through Django admin. Git's SSH transport itself shells out to the system `ssh` binary, which has its own history of argument/hostname-smuggling issues (e.g., a hostname starting with `-`). `dulwich` is a pure-Python git implementation with no transport-helper dispatch, and its SSH vendor can be backed by `paramiko` — a pure-Python SSH2 client — instead of shelling to `ssh`. Neither transport ever invokes a subprocess, closing both injection classes structurally rather than through URL/argument allowlisting we'd have to get right and keep right.

*Alternative considered:* subprocess `git` with a strict scheme allowlist, argv-array invocation (never `shell=True`), and `GIT_TERMINAL_PROMPT=0`. Rejected primarily because the SSH transport still shells to the system `ssh` binary internally regardless of how carefully the outer `git` invocation is constructed — the mitigation would have to be re-litigated for a second subprocess boundary. `GitPython` was also considered and rejected for the same reason (it wraps subprocess `git`).

*Diligence required before implementation:* confirm the pinned `dulwich` release's shallow-clone and SSH-vendor support are mature enough (spike against a local Gitea instance, both HTTPS and SSH, before committing to version pins).

*Spike findings (resolved during task 2.1):* pinned `dulwich==1.2.15` (latest) and `paramiko==5.0.0` (latest); shallow, single-branch clone (`depth=1`, `branch=...`) works cleanly over both transports. Two things the spike surfaced that the connector implementation works around rather than relying on upstream defaults:
- `dulwich.contrib.paramiko_vendor.ParamikoSSHVendor` — the module this decision originally pointed at — was removed from the packaged `dulwich` distribution after `1.1.0` (still present in-tree through `1.1.0`, dropped from `pyproject.toml`'s `packages` list, and later from the repo, in `1.2.0`). Downgrading wasn't attractive anyway: even at `1.1.0` that vendor hardcodes a no-op `paramiko.MissingHostKeyPolicy` (accepts any unknown host key), which contradicts the fail-closed requirement below. `connectors/git.py` implements its own minimal `SSHVendor` directly against `paramiko.SSHClient` instead — this is what makes fail-closed host-key verification possible at all, not a workaround for a packaging gap.
- `HttpGitClient`'s `extra_headers` constructor/`porcelain.clone` kwarg is accepted but never actually attached to a request in `1.2.15` (dead parameter — verified by round-tripping a real bearer token against a private Gitea repo: it 401s). `authKind: bearer` instead constructs the client with an explicit `urllib3.PoolManager(headers={'Authorization': f'Bearer {token}'})`, which `HttpGitClient._http_request` does read (`req_headers = dict(self.pool_manager.headers)`).

### Deployment-level `sources` in plugin config, not per-repository DB credentials
`atlas.ingestion` plugin config gains a `sources` list; each source has `id`, `baseUrl`, `authKind` (`basic` | `bearer` | `ssh-key`), and `credential` (a `SecretRef` or `FileRef`, resolved once at process startup via the existing `resolve_secrets` mechanism). `RegisteredRepository` keeps only `source_id` + `path` + `default_branch` — no credential field. This mirrors how every other plugin secret in this codebase is already declared (OAuth client secrets via `{fromEnv: ...}`), and it shrinks the SSRF surface: the set of reachable hosts is fixed at deploy time through the manifest, not enterable at runtime through Django admin. Only `path` needs runtime validation (see below), not an arbitrary URL.

*Alternative considered:* keep `access_token` on `RegisteredRepository` but encrypt it at rest (Fernet field). Rejected: this would be the first database-level encryption in the project, it only protects against DB-dump/backup exposure (not a compromised application process, which still needs the key in memory to decrypt), and it doesn't fit the deployment shape described for this project's primary use case — a company runs Atlas against one or a small, known set of internal git services, configured once, not an open set of git hosts operators add at runtime. Recorded here as a viable alternative for a future "operator self-registers arbitrary git hosts at runtime" use case, which is explicitly out of scope for this change.

*Trade-off accepted:* `source_id` cannot be a real Django `ForeignKey`, since sources live in resolved plugin config, not a database table. Referential integrity is therefore application-level, not DB-level (see Risks).

### `resolve_secrets` gains recursion into nested config
Today `resolve_secrets` (`plugin-api/python/atlas_plugin_api/config.py`) only inspects top-level fields of a `PluginConfigSchema` for `SecretRef`. `sources` is a list of sub-models, each with its own `credential` field, so this function needs to walk into `BaseModel` and `list[BaseModel]`-typed fields recursively, rebuilding each nested model the same way it already rebuilds the top-level one (`model_validate` on the resolved dict). This is shared infrastructure in `plugin-api/`, useful to any future plugin with a list of sub-configs that can each carry a secret, not an ingestion-specific hack.

### `FileRef` as a sibling type to `SecretRef`, not a second optional field on it
A new reference kind, `{fromFile: <path>}`, is added for multi-line secret material (SSH private keys are the first such use case in this project — `{fromEnv: ...}` alone forces awkward base64-encoding of key material into a single-line env var). It's implemented as its own frozen `BaseModel` (`FileRef`, `from_file: str`), with config fields typed `str | SecretRef | FileRef` where a secret may come from either source, rather than adding an optional `from_file` field onto `SecretRef` itself.

*Alternative considered:* one `SecretRef` with both `from_env: str | None` and `from_file: str | None`. Rejected because it admits an invalid state (both set, or neither set) that has to be validated defensively; two distinct types make "exactly one reference kind" structural instead of enforced.

`authKind: ssh-key` sources use `credential: {fromFile: ...}` pointing at a mounted private key (the `oauth2-gitea` example's `gitea-runtime-secrets` Docker volume is the template for how a bootstrap step writes a file another container reads read-only). `authKind: basic`/`bearer` sources keep using `{fromEnv: ...}`.

### SSH host-key verification is fail-closed by default
A scheduled ingestion pass runs unattended; it must never block on an interactive host-key prompt, and it must not silently trust-on-first-use as a substitute for one, since TOFU on a headless job with no operator watching is equivalent to accept-all in practice. `authKind: ssh-key` sources therefore require either explicit known-hosts content/path, or an explicit `acceptUnknownHostKeys: true` development-only opt-in — mirroring `allowDevelopmentHttp`'s shape and tone in `plugins/auth-gitea/.../config.py`.

### `path` validation instead of URL validation
Because `baseUrl` is fixed per source at deploy time, `RegisteredRepository.path` only needs to reject empty values, leading `/`, `..` path segments, control/whitespace characters, and any `://`-containing value (which could otherwise override `baseUrl` entirely when naively concatenated). This is a much smaller validation surface than validating an arbitrary operator-supplied clone URL would have been.

### Clone lifecycle
Each pass clones into a fresh, per-repository temporary directory (removed in a `finally` block regardless of outcome), with a wall-clock timeout so one slow or oversized repository cannot stall an entire scheduled pass. `get_head_sha`, `list_manifest_paths`, and `fetch_file` all operate against that same local checkout within one pass — no second network round trip per manifest file, unlike the current REST-based connector.

## Risks / Trade-offs

- **New, less battle-tested dependencies** (`dulwich`, `paramiko` — neither currently in `core/backend/pyproject.toml`) → pin exact versions; add integration tests that exercise a real shallow clone (HTTPS and SSH) against a throwaway local git server, not only mocks, so a `dulwich` upgrade that regresses shallow-clone behavior is caught in CI.
- **No DB-level referential integrity on `source_id`** → validate `source_id` against the currently resolved `sources` config in the admin form (`clean()`/`full_clean()`), so a typo surfaces immediately in Django admin rather than silently at the next scheduled ingestion pass; when a pass does encounter a `source_id` no longer present in config (e.g., an operator removed a source from the manifest), log and surface it as clearly as an unresolved-reference or claim conflict is today, not a silent skip.
- **`fromFile` depends on the deployment actually mounting a file at a stable path** → the example and docs must show the concrete mount pattern (extending the `oauth2-gitea` runtime-secrets-volume idiom), or operators have no working reference for wiring an SSH key in.
- **Breaking change for `RegisteredRepository`** → no known production deployment of `atlas.ingestion` exists yet (only tests and, after this change, the new example reference the model), so a destructive migration (drop `full_name`/`access_token`, add `source_id`/`path`) is acceptable; anyone who deployed ahead of this change landing needs to re-register repositories against the new shape.
- **SSRF is reduced, not eliminated** — fixing the host set at deploy time removes the runtime-admin attack surface, but an operator with manifest-edit rights (a trust boundary that already exists for every other plugin's `allowedDestinations`) can still point a source's `baseUrl` at an internal address. Mitigate with the same `allowedDestinations`/`allowDevelopmentHttp` validation pattern already used by `plugins/auth-gitea` at config-resolution time, for defense in depth and consistency — but the design should not claim to fully eliminate SSRF, only to shrink who can influence it and when.
- **Scope of `ref`**: the current pipeline only ever fetches at `default_branch` (confirmed via `pipeline.py`); this is preserved, not regressed — shallow clone only ever needs the tip of one branch, matching existing behavior exactly.

## Migration Plan

1. Extend `resolve_secrets` for nested/list config fields and add `FileRef`, with their own unit tests. Purely additive — no existing plugin's behavior changes.
2. Implement `GitConnector` against the existing `SourceConnector` ABC (dulwich + paramiko, HTTPS and SSH, shallow clone, timeout, cleanup), with unit and integration tests, without yet wiring it as the pipeline's registered connector.
3. Add the `sources` schema to `atlas.ingestion` plugin config; add the `RegisteredRepository` migration (drop `full_name`/`access_token`, add `source_id`/`path`); update `admin.py` for the new fields and `source_id` validation; update `pipeline.py`/`plugin.py` to resolve `GitConnector` per repository's configured source instead of the hardcoded GitHub `CONNECTOR_ID` import.
4. Remove `GitHubConnector` and its tests.
5. Update `docs-site/docs/using-atlas/ingest-repository.md`, `troubleshoot-ingestion.md`, and the `catalog-info-yaml.md` reference to the new registration flow.
6. Build `examples/ingestion/` on top of the now-working connector.

Rollback: each step is an independent, revertible commit; no production data migration risk given the assumption in Non-Goals (no existing production `atlas.ingestion` deployments). If that assumption turns out to be false, this plan needs a data-preserving migration step inserted before step 3, which should be re-scoped at that point rather than assumed away.
