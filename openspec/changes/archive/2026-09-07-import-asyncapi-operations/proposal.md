## Why

`add-operation-subscription-explorer` shipped `ApiOperation`/`ServiceOperationUsage` as a fully-featured child resource of `API` (documentation tabs, channel-scoped publishers/subscribers graph, Link/Unlink) with a model deliberately kept "import-ready," but explicitly deferred AsyncAPI parsing as a Non-Goal — operation documentation is entered only through Django admin or seed fixtures today. `spec_fetch.apply_api_spec_source`/`resolve_api_spec_url` and `atlas_plugin_ingestion`'s periodic `due_for_spec_refresh` already fetch and store an `asyncapi`-typed API's `spec_content` verbatim, exactly as they do for `openapi`-typed APIs, but nothing parses `channels`/`operations` out of it. `openapi_import.py` already solves the identical problem for OpenAPI (`ApiDetails.post_save` → `sync_endpoints_from_spec` → `ApiEndpoint` upsert) — AsyncAPI has no counterpart. As a result, an `asyncapi`-typed API with a real spec URL has zero Operations unless someone hand-transcribes them, which defeats the point of pointing Atlas at a live AsyncAPI document: the impact-analysis value `add-operation-subscription-explorer` was built for (publishers/subscribers graph, Linked Services) has no data to work with until a human does that work by hand.

## What Changes

- Add an AsyncAPI (2.x and 3.0) parser that turns an `asyncapi`-typed API's `spec_content` into `ApiOperation` rows: `channel_address`, `channel_protocol` (best-effort, from `servers`), `direction`, `operation_key`, `operation_id`, `summary`, `description`, `tags`, and one or more `message` shapes (name/schema/example) — matching the exact shape `OperationMessageOut`/`ApiOperation.message` already expose.
- `direction` is computed using the mapping already verified and recorded in `add-operation-subscription-explorer`'s design.md and codified in `specs/api-operations/spec.md`: AsyncAPI 2.x `publish` → `receive`, 2.x `subscribe` → `send`, 3.0 `action: send`/`action: receive` pass through unchanged. This change does not re-derive that mapping — it implements the mapping the model was already built around.
- `operation_key` is computed per `specs/api-operations/spec.md`'s existing identity rule: the AsyncAPI 3.0 operations-map key for 3.0 documents; `channel_address + direction` for 2.x documents (2.x has no separate operation-map key).
- Wire this parser into the same shared point `openapi_import.py` already uses: `ApiDetails`'s `post_save` signal (`plugins/apis/backend/atlas_plugin_apis/signals.py`), so it runs identically after a user-initiated create/patch and after the ingestor's periodic `spec_url` refresh — no call site has to remember to invoke it separately, and no changes are needed to `spec_fetch.py`, `kinds/api_handler.py`, or `atlas_plugin_ingestion`.
- Upsert by the existing `operation_key` identity (scoped per API): new operations create `ApiOperation` rows, changed operations update the existing row (id and any `ServiceOperationUsage` links stay stable), operations that disappear from a re-parsed spec are soft-removed (`status='removed'`), and a previously-removed operation that reappears is revived to `active` — mirroring `openapi_import.py`'s exact upsert shape for `ApiEndpoint`.
- `$ref` values inside message schemas are stored verbatim (unresolved), matching `openapi_import.py`'s existing treatment of `$ref` in endpoint schemas and `EndpointSchemaOut`'s existing unresolved-`$ref` rendering (`OperationMessageOut.schema_` reuses that same type).
- A spec that fails to parse as AsyncAPI (malformed `channels`, unrecognized version, etc.) never raises out of the save/refresh path and never touches existing `ApiOperation` rows — recorded via two new `ApiDetails` fields (`operations_synced_at`/`operations_sync_failed`), mirroring `endpoints_synced_at`/`endpoints_sync_failed`.
- Fix and enrich `seed_booking_demo.py`'s two demo AsyncAPI documents (`ASYNCAPI_SPEC`, `BOOKING_EVENTS_ASYNCAPI_SPEC`): three of their four `publish`/`subscribe` keywords are currently inverted relative to the verified 2.x mapping above (discovered while researching this change — the hand-authored `OPERATIONS` fixture's `direction` values were chosen to match the intended demo narrative, not derived from the raw spec text). Once a real parser is wired to `post_save`, those specs would parse into `ApiOperation` rows with a *different* `operation_key` than the hand-authored fixture uses for the same channel (`operation_key` depends on `direction`), producing duplicate, orphaned demo rows per channel — silent duplication, not the `IntegrityError` OpenAPI's own analogous seed-wiring initially hit (that case is identity-stable across real-vs-hand-authored writers; this one isn't). Rather than patching the keywords and keeping a parallel hand-authored fixture (the OpenAPI precedent's accepted-drift approach), this change removes the fixture: the spec text is corrected and enriched (description, tags, message names/examples) to be the sole source of truth, `OPERATIONS`/`_create_operations()` are deleted, and the resulting `ApiOperation` rows come entirely from the importer this change adds — eliminating the fork risk instead of managing it.
- **BREAKING (behavioral, not API-breaking):** for `asyncapi`-typed APIs, `ApiOperation` fields become spec-derived on every successful parse — a manual Django-admin edit to an importer-managed operation's documentation fields is overwritten the next time its API's spec resolves. (Non-`asyncapi`-typed APIs, and operations on APIs with `spec_source=none`, are entirely unaffected and remain manually authored.)

## Capabilities

### New Capabilities
- `asyncapi-operation-import`: parsing an API's resolved AsyncAPI (2.x/3.0) `spec_content` into `ApiOperation` rows, triggered on every successful spec resolution (create, patch, periodic refresh), including the create/update/revive/soft-remove upsert rules, the verified `publish`/`subscribe`/`action` → `direction` mapping, and parse-failure handling.

### Modified Capabilities
- `api-operations`: "Operation documentation is entered administratively in this change" no longer holds universally — for an `asyncapi`-typed API, `ApiOperation` rows are now written by the importer whenever its spec resolves, not only through Django admin/fixtures. The "no self-service create/edit API" guarantee is unchanged (the importer is a system-triggered side effect of saving/refreshing an API's spec, not a client-facing create/edit endpoint), and the soft-removal invariant (`ServiceOperationUsage` never cascade-deleted) is extended to cover import-triggered removal.

## Impact

- **Backend (`plugins/apis/backend/atlas_plugin_apis`):** new `asyncapi_import.py` module (parser + upsert); `signals.py`'s existing `ApiDetails` `post_save` receivers gain a second sync call and a shared self-save recursion guard; `models/api.py` gains two sync-status fields (new migration); `admin.py`/`api/schemas.py`/`api/views.py` expose the new failure indicator, mirroring the existing `endpoints_synced_at`/`endpoints_sync_failed` surface exactly.
- **Frontend (`plugins/apis/frontend`):** `ApiSpecPanel.tsx`/`entityDetailTabs/api.tsx` gain an "Operation sync failed" indicator alongside the existing "Endpoint sync failed"/"Stale spec" labels; `core/frontend/src/lib/types.ts`'s `ApiSpec` type gains the two new fields.
- **No new runtime dependency** — the parser walks the already-`yaml.safe_load`-parsed spec dict directly, following `openapi_import.py`'s precedent, rather than adding an AsyncAPI object-model library.
- **Ingestion plugin (`plugins/ingestion`):** no code change — `due_for_spec_refresh` is already type-agnostic and keeps calling `resolve_api_spec_url`/`details.save(...)` exactly as today; the new sync rides the same `post_save` signal `recompute_relations` and `sync_endpoints_from_spec` already ride.
- **Seed data (`seed_booking_demo.py`):** `ASYNCAPI_SPEC`/`BOOKING_EVENTS_ASYNCAPI_SPEC` text corrected and enriched to be self-sufficient (see What Changes); `OPERATIONS`/`_create_operations()` are deleted, and `_create_operation_usages()`'s lookup of `ApiOperation` rows is served by a query against the importer's output instead of a fixture-created dict.
