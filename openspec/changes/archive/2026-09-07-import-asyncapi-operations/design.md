## Context

`atlas_plugin_apis` already solved this exact problem once, for OpenAPI (`import-openapi-endpoints`, archived): a hand-rolled walker (`openapi_import.py`) parses `ApiDetails.spec_content`, hooked off `ApiDetails`'s `post_save` signal, upserting `ApiEndpoint` rows keyed by `(api, method, path)`. `ApiOperation`/`ServiceOperationUsage` (`add-operation-subscription-explorer`, archived) is the AsyncAPI-side sibling of `ApiEndpoint`/`ServiceEndpointUsage`, deliberately built "import-ready" — but that change's own Non-Goals explicitly deferred the parser: "AsyncAPI 2.x/3.0 spec parsing/import — a dependent follow-up change (tentatively `import-asyncapi-operations`)... ships with admin/fixture-authored data only." This change is that follow-up.

```
              ApiDetails.post_save
                       │
        ┌──────────────┴──────────────┐
        ▼                              ▼
type == 'openapi'?             type == 'asyncapi'?   ◄── new receiver, this change
        │                              │
        ▼                              ▼
openapi_import                 asyncapi_import.sync_operations_from_spec (new)
  .sync_endpoints_from_spec            │
        │                              ▼
        ▼                    upsert ApiOperation by operation_key
upsert ApiEndpoint by                  (create / update / revive / soft-remove)
  (api, method, path)
```

Three properties make this not a mechanical relabeling of `openapi_import.py`, all already surfaced and resolved by `add-operation-subscription-explorer`'s design.md — this change implements decisions that document already made, it does not re-decide them:

1. **AsyncAPI 2.x's `publish`/`subscribe` are defined from the channel's perspective and are easy to get backwards.** Verified against the primary spec source there (`spec/asyncapi.md` v2.6.0, Channel Item Object) and codified in `specs/api-operations/spec.md`'s "Operation direction is a normalized, spec-version-agnostic fact" requirement: 2.x `publish` → stored `receive`; 2.x `subscribe` → stored `send`; 3.0 `action: send`/`action: receive` pass through unchanged. This parser implements that mapping; it is not free to reinterpret it.
2. **`operation_key` is version-shaped differently than `ApiEndpoint`'s `method + path`.** Per `add-operation-subscription-explorer` design.md Decision 4: the AsyncAPI 3.0 operations-map key for 3.0 documents (spec-mandated, unique, stable across a channel-address edit); `channel_address + direction` for 2.x documents (2.x has no separate operation-map key, but at most one `publish`+one `subscribe` per channel makes this pairing inherently unique).
3. **A 2.x document has no per-channel `servers` scoping; a 3.0 document does.** `channel_protocol` (Decision 2 of that design) is "from the document's/channel's `servers`/`protocol`, when resolvable" — resolvability differs by version (see Decision 4 below).

**Newly discovered while researching this change:** `seed_booking_demo.py`'s two demo AsyncAPI documents (`ASYNCAPI_SPEC`, `BOOKING_EVENTS_ASYNCAPI_SPEC`) do not consistently follow the verified mapping above. Checking each channel's raw `publish`/`subscribe` keyword against the hand-authored `OPERATIONS` fixture's `direction`:

| API | Channel | Spec keyword | Mapping says | Fixture says | |
|---|---|---|---|---|---|
| notifications-api | `booking.confirmed` | `subscribe` | `send` | `receive` | mismatch |
| notifications-api | `payout.completed` | `subscribe` | `send` | `receive` | mismatch |
| notifications-api | `notification.delivery-status` | `publish` | `receive` | `send` | mismatch |
| booking-events-api | `booking.confirmed` | `subscribe` | `send` | `send` | matches |

The seed file's own comment confirms this was intentional at the time: `direction` was "hand-authored directly... so each value reflects the intended real behaviour rather than the 2.x wording's easy-to-invert perspective" — i.e. the demo author picked the *narratively correct* direction without deriving it from the (also hand-written) spec text, and got the spec text's keyword backwards in three of four cases relative to the mapping the model was actually built around. This is not a bug in the mapping or in the fixture's intent — the fixture's `direction` values already say what the demo *means* (notifications-api receives booking/payout events to notify people about them; it sends a delivery-status update). It is the demo spec *text*'s `publish`/`subscribe` keywords that don't yet agree with that meaning under the verified mapping.

## Goals / Non-Goals

**Goals:**
- Parse `spec_content` for an `asyncapi`-typed API (2.x and 3.0) into the exact `ApiOperation` fields `api/schemas.py` (`OperationOut`/`OperationMessageOut`) already defines and the frontend already renders.
- Run identically after every successful spec resolution — first save, later PATCH, and periodic `spec_url` refresh — via the same `post_save` hook `openapi_import.py` already uses, adding a second receiver rather than a parallel mechanism.
- Upsert by `operation_key` (scoped per API): create new, update changed, revive a previously-removed operation that reappears, and soft-remove (never delete) an operation that disappears — preserving every existing `ServiceOperationUsage` row regardless of which of those four things happens to its operation.
- Compute `direction` using the mapping already verified in `add-operation-subscription-explorer`'s design.md and codified in `specs/api-operations/spec.md` — this change is the mapping's first real producer, not a place to re-derive or adjust it.
- Fail safe: a spec that can't be parsed as AsyncAPI never raises out of a save/refresh request and never mutates existing `ApiOperation` rows; the failure is recorded and surfaced the same way `endpoints_sync_failed` already is.
- Correct and enrich `seed_booking_demo.py`'s demo AsyncAPI spec text so it is the sole authority for the demo catalog's `ApiOperation` rows, and remove the parallel hand-authored `OPERATIONS` fixture that would otherwise fork into duplicate rows once a real parser exists (see Decision 6).

**Non-Goals (deferred or out of scope):**
- Resolving `$ref` (e.g. a channel/message defined under `components.messages` and referenced by `$ref` from a channel's or operation's `messages` list) into its referenced content. Stored/represented unresolved, matching `openapi_import.py`'s exact stance on `$ref` and `EndpointSchemaOut`/`EndpointSchemaViewer`'s existing unresolved-`$ref` rendering (`OperationMessageOut.schema_` reuses that same read type). A 3.0 operation whose messages are pure `$ref`s into a channel's message map, with no inline `payload` on the operation itself, yields a message entry with only a name derived from the ref's last path segment — no schema/example — same spirit as an unresolved `$ref` anywhere else in this plugin.
- Channel address normalization or cross-document channel matching — inherited as-is from `add-operation-subscription-explorer` design.md Non-Goals; `channel_address` remains an exact string, and this change does not introduce any auto-link between two `ApiOperation` rows (from the same or different APIs) that happen to share one.
- Any self-service "re-import now" button, import history/audit log, or diff preview UI — sync is implicit in saving/refreshing the spec, same as `openapi_import.py`.
- `openapi`/`grpc`/`graphql`-typed APIs — `ApiOperation` is channel+direction shaped; only `type='asyncapi'` is in scope, matching `ApiEndpoint`'s existing type-scoping precedent.
- AsyncAPI 3.0's `reply` (request/reply) operations — already excluded from the model itself (`add-operation-subscription-explorer` design.md Non-Goals); the parser does not attempt to represent them.
- Byte-exact verification of every AsyncAPI 3.0 message-indirection edge case (channel-local vs. `components.messages`, an operation's `messages` narrowing a channel's own message set) — flagged as an Open Question below; the implementer should re-verify against the primary AsyncAPI spec source before finalizing the 3.0 message walker, the same way `add-operation-subscription-explorer`'s design.md re-verified the 2.x direction mapping rather than assuming it.

## Decisions

### 1. Hook into `ApiDetails`'s existing `post_save` signal, alongside the OpenAPI receiver — not a new mechanism
**Decision:** Add a second `post_save` receiver in `signals.py`, `_sync_operations_on_save`, calling `asyncapi_import.sync_operations_from_spec(instance)`. It fires after every `details.save()`, exactly like `_sync_endpoints_on_save` and `_recompute_on_save` already do, regardless of which write path (create, patch, periodic refresh) produced it.

**Why:** Identical reasoning to `import-openapi-endpoints` design.md Decision 1, which itself extended `signals.py`'s own stated rationale for `recompute_relations`: "every way an entity's kind-specific data can be written... recomputes relations the same way without every call site needing to remember to do it." A third kind of kind-specific derived data (`ApiOperation`, after `Relation` and `ApiEndpoint`) gets the identical mechanism rather than inventing a new one.

**Alternative considered:** A single combined receiver that dispatches on `instance.type` to call either `sync_endpoints_from_spec` or `sync_operations_from_spec`. Rejected: `openapi_import.py`'s `sync_endpoints_from_spec` is already unconditionally safe to call for any type (it no-ops on `type != 'openapi'`) — the two functions are already mutually exclusive by construction, so a dispatching wrapper adds a branch with no behavioral benefit over two independent receivers, and splits less cleanly if a third API type ever gets its own importer.

### 2. Shared self-save recursion guard, expanded to cover both sync status field pairs
**Decision:** `signals.py`'s existing `_SYNC_STATUS_FIELDS` frozenset (currently `{'endpoints_synced_at', 'endpoints_sync_failed'}`, used by `_sync_endpoints_on_save` to skip re-running when a save's `update_fields` is exactly its own status self-write) is expanded to `{'endpoints_synced_at', 'endpoints_sync_failed', 'operations_synced_at', 'operations_sync_failed'}` and used, unchanged in shape, by **both** `_sync_endpoints_on_save` and the new `_sync_operations_on_save`.

**Why:** Both receivers fire on every `ApiDetails` save regardless of type (Decision 1), so `sync_operations_from_spec`'s own `details.save(update_fields=['operations_synced_at', 'operations_sync_failed'])` re-fires `_sync_endpoints_on_save` too (and vice versa for the OpenAPI sync's self-save firing the new receiver) — each no-ops internally on a type mismatch, but only if its own recursion guard doesn't itself get confused by a self-write whose `update_fields` isn't a subset of *that receiver's own* pre-existing narrower set. Expanding one shared frozenset both receivers check keeps the invariant simple: "a save whose `update_fields` is nothing but one of these two sync-status self-writes never triggers a re-parse from either receiver," instead of tracking two separate two-field guards that each receiver would have to remember to update if a third importer's status fields are added later.

**Alternative considered:** Two separate frozensets, one per receiver, each containing only its own two fields. Rejected: no correctness difference (a self-write's `update_fields` is always exactly one pair or the other, never a mix), but doubles the constants to keep in sync for zero behavioral gain, and the shared-set version already reads as "any known sync-status self-write" rather than "my own sync-status self-write specifically" — the more honest description of what's actually being guarded against (wasted re-parses from an unrelated sync's self-save, not just recursion into itself).

### 3. `asyncapi_import.py` is a hand-rolled walker over the parsed dict, mirroring `openapi_import.py` exactly
**Decision:** `asyncapi_import.py` parses `yaml.safe_load(spec_content)`, detects version via top-level `asyncapi: "2.x"` vs `asyncapi: "3.x"`, and walks:
- **2.x:** `channels` → per-channel `publish`/`subscribe` fields directly.
- **3.0:** top-level `operations` map (each entry has `action: send|receive` and a `channel` reference) plus the `channels` map it references (for `address`/`servers`).

No new dependency is added — same rationale as `openapi_import.py`'s own Decision 3 (`EndpointSchemaOut`'s "provisional, JSON-Schema-*like*" precedent applies identically to `OperationMessageOut`'s reuse of that same type).

**Why:** This plugin already has exactly one precedent for "parse a spec dict into plugin-owned child rows," and it was itself explicitly justified against adopting a spec object-model library. Reusing the same shape (hand-rolled, per-version branch, normalize into one output record before touching the DB) keeps both importers legible as one pattern applied twice, rather than two differently-structured parsers for sibling problems.

**Alternative considered:** A single shared "spec walker" abstraction parameterized over OpenAPI/AsyncAPI differences. Rejected: the two formats' structures (`paths`+method-keyed operations vs. `channels`+direction-keyed-or-separate-operations-map) diverge enough at every level (identity, parameters vs. messages, response codes vs. no equivalent) that a shared abstraction would mostly be indirection around two things that don't actually share logic beyond "call `yaml.safe_load` once" — not worth introducing for two call sites.

### 4. `channel_protocol` resolution is version-specific and best-effort, never guessed
**Decision:** For 2.x, a channel's protocol resolves only when the document's top-level `servers` map has exactly one entry — its `protocol` is used for every channel (2.x has no per-channel server scoping). For 3.0, a channel's protocol resolves only when its own `servers` list references exactly one server — that server's `protocol` is used. In every other case (zero servers, multiple servers with no per-channel narrowing in 2.x, a 3.0 channel referencing zero or multiple servers), `channel_protocol` is left empty, per `ApiOperation.channel_protocol`'s own "when resolvable" model docstring and `specs/api-operations/spec.md`'s existing "Operation with no resolvable protocol" scenario — never a best-guess pick among ambiguous candidates.

**Why:** `add-operation-subscription-explorer` design.md Decision 2 already scoped `channel_protocol` as advisory/display-only, and the model/spec already have a defined empty-state behavior for "can't resolve" — extending that same threshold to "ambiguous" (as opposed to inventing a tie-breaking rule, e.g. "first server alphabetically") keeps the field honest: it says a specific protocol only when the document itself makes that specific, not a plausible guess dressed up as fact.

**Alternative considered:** Always resolve to the first server's protocol when more than one exists. Rejected: silently picks one broker's protocol to label a channel that may legitimately span multiple protocols (e.g. AMQP and Kafka mirrors of the same logical channel) — a wrong-looking specific value is worse than an honest blank, matching this plugin's existing "don't guess" posture (e.g. `openapi_import.py`'s own `$ref`-left-unresolved stance, and `channel_address`'s exact-string-only Non-Goal).

### 5. Message extraction: `payload` → schema, first `examples[]` entry → example, one entry per alternative
**Decision:** A channel operation's `message` maps to one or more `OperationMessageOut`-shaped entries: `payload` (verbatim, `$ref` unresolved) becomes `schema`; the message's own `name`/`title`/`summary` (when present) become the entry's `name`/decorative fields; the first entry of the message's `examples` array (the AsyncAPI-spec-proper sibling field — `[{name?, summary?, payload}]`), when present, has its `payload` used as the entry's `example`. A message declared as `oneOf: [...]` (multiple alternative shapes on one operation) produces one entry per alternative, matching `specs/api-operations/spec.md`'s existing "Operation with multiple message shapes" scenario.

**Why:** `payload`/`examples` are AsyncAPI's own Message Object field names (distinct from OpenAPI's `schema`/`example`, which `openapi_import.py` maps 1:1) — this is the natural, minimal translation into the shape `OperationMessageOut` already contracts for, following the same "walk the document's own field names into the existing read shape" approach `openapi_import.py` used for `requestBody`/`responses`.

**Why not also read an `example` keyword embedded directly inside `payload`'s own JSON-Schema:** JSON Schema permits an `example` (or `examples`) annotation keyword nested inside a schema, and a schema author can embed one there instead of using the message's own sibling `examples` field — `seed_booking_demo.py`'s current demo spec text does exactly this (see Risks). This decision does not special-case that shape: an embedded schema-level `example` simply travels through as part of `schema` untouched (the same way any other JSON-Schema annotation keyword would), and `OperationMessageOut.example` stays `None` unless the message's own proper `examples` field is present. Special-casing "hoist a schema-embedded `example` keyword up to the message level" would mean guessing at author intent for an annotation JSON Schema itself does not require to mean "this is the message's canonical example" — the spec already has an unambiguous field for that (`examples`), so this parser only reads that one.

**Alternative considered:** Detect and hoist a `payload.example`/`payload.examples` keyword to the message-level `example` field when the message's own proper `examples` field is absent. Rejected: adds a second, non-spec-sanctioned code path for something the format already has one clear way to say, purely to accommodate demo spec text this change already fixes at the source (Decision 6) — the fallback would exist for zero specs other than the ones this change is itself correcting.

### 6. Seed data gets one source of truth: enrich the spec text, delete the hand-authored `OPERATIONS` fixture
**Decision:** Unlike `import-openapi-endpoints` (which kept `_create_endpoints()`'s hand-authored `ENDPOINTS` overlay as an accepted, documented drift risk against the real parser), this change removes the parallel authority entirely for AsyncAPI operations. `ASYNCAPI_SPEC`/`BOOKING_EVENTS_ASYNCAPI_SPEC` are corrected and enriched directly:
- Flip the three mismatched channels' keywords so they agree with the verified mapping applied to the *intended* direction (Context table): `booking.confirmed` and `payout.completed` in `ASYNCAPI_SPEC` become `publish`; `notification.delivery-status` becomes `subscribe`.
- Add each operation's `description`, `tags` (2.x Tag Objects), and each message's `name`, moving each channel's embedded `payload.example` into a proper message-level `examples: [{payload: {...}}]` field (Decision 5) — the fields the hand-authored `OPERATIONS` fixture used to supply on top of the spec text, now supplied by the spec text itself.

`OPERATIONS` and `_create_operations()` are deleted. `_create_apis()` already triggers `sync_operations_from_spec` synchronously (via `ApiDetails.post_save`) inside its per-API loop, so by the time it returns, every `ApiOperation` row for both `asyncapi`-typed demo APIs already exists, produced by the real importer. `_create_operation_usages()`'s existing need for a `{(api, operation_key): ApiOperation}` lookup (to link `OPERATION_USAGES`) is served by a small query against the rows the importer already wrote, not by re-asserting them.

**Why:** `import-openapi-endpoints`'s accepted drift risk is safe to accept *because* it's purely cosmetic — `method`+`path` never disagree between the real parser and hand text, so `update_or_create` always finds and overwrites the same row; only documentation content can drift. Here, the identity itself (`operation_key`) is direction-dependent, so an unfixed mismatch doesn't drift, it *forks* — the hand-authored `update_or_create` creates a second, orphaned row instead of finding the parser's. Patching only the mismatched keywords (fixing the fork) while keeping the dual-authoring (Alternative A below) still leaves that fork-risk latent for the next person who edits either copy without updating the other. Deleting one of the two copies removes the risk class outright rather than managing it, and makes the demo catalog exercise the actual feature this change builds — the same reason `seed_booking_demo.py` already lets `openapi_import` produce `ApiEndpoint` rows before `_create_endpoints()` runs, rather than skipping that path in seed data.

**Why the cross-API "two documents, one channel" scenario still works:** `add-operation-subscription-explorer` tasks.md 8.1's scenario (both `notifications-api` and `booking-events-api` declaring an operation on `booking.confirmed`) is already expressed by the two spec documents both declaring that channel — it was never something `OPERATIONS` added on top; it falls out of parsing both documents for free.

**Alternative A considered (patch, don't consolidate):** Keep `OPERATIONS`/`_create_operations()`, fix only the three backwards keywords and the embedded-example shape, exactly mirroring `import-openapi-endpoints`'s own accepted-drift precedent. This was this design's first pass. Superseded once seed data was confirmed free to restructure: it leaves the fork-risk latent (nothing stops a future edit to one copy without the other from reintroducing duplicate rows) and keeps two authorities saying the same thing for zero remaining benefit — the enrichment needed to make the spec text self-sufficient (description/tags/message names) is no larger than the diff Alternative A already required (keyword flips + example reshaping).

**Alternative B considered:** Leave the demo spec text as-is and change `OPERATIONS`'s `operation_key`/`direction` to match what a real parse of the current (uncorrected) text would produce. Rejected: flips the *meaning* of three of the four demo operations (e.g. notifications-api's `booking.confirmed` operation would become `send`, contradicting its own intended narrative — "Receive booking-confirmation events" / "Consumed to notify the guest and host").

## Risks / Trade-offs

- **[Risk]** Decision 6's seed-text fix depends on this document's re-derivation of "what the fixture's `direction` values were meant to imply" being correct — if some other channel/direction pairing in the demo data was actually intentional-and-already-correct in a way this document misread, fixing the spec text could make the *meaning* wrong instead of the keyword. → **Mitigation:** cross-checked every one of the four affected operations' `summary`/`description` text against its `direction` before concluding it was the intended value (Context table); the one already-matching case (`booking-events-api`) is left untouched as a control that the mapping itself, applied correctly, does agree with intended meaning at least once in this same demo data.
- **[Risk]** Deleting `OPERATIONS`/`_create_operations()` (Decision 6) means the demo catalog's operation documentation quality is now bounded by how much detail can reasonably live in YAML spec text (`description`, `tags`, message `name`/`examples`) — a future demo-data improvement that would have been a one-line `OPERATIONS` dict edit now requires editing spec text that also has to remain valid AsyncAPI. → **Mitigation:** accepted; the enrichment needed (Decision 6) is no more elaborate than any other field already in these specs, and the constraint ("demo copy must be expressible as valid spec text") is the same constraint a real spec-driven API already lives under — arguably a truer test of the importer than authoring text the importer never has to actually parse correctly.
- **[Risk]** The 3.0 message-indirection walker (Decision 5 / Non-Goals) is the one piece of this design not yet exercised against a real 3.0 document in this repository (no 3.0 sample exists in `seed_booking_demo.py` today, unlike 2.x). → **Mitigation:** flagged as an Open Question; implementer re-verifies the exact 3.0 `channels`/`operations`/`messages` shapes against the primary spec source before finalizing, the same rigor `add-operation-subscription-explorer` applied to the 2.x direction mapping. Landing 2.x support alone first and following up for 3.0 is an acceptable phased alternative if the 3.0 shape proves to need more than a straightforward extension.
- **[Risk]** Manual admin edits to an importer-managed operation are overwritten on next sync, identical in kind to `import-openapi-endpoints` design.md's own accepted Decision 6 risk for endpoints. → **Mitigation:** same acceptance — no per-field "locked" flag introduced, for the same reasons (real complexity for an unrequested workflow); documented here so it isn't a surprise the second time this shape of tradeoff appears in this plugin.
- **[Risk]** A very large AsyncAPI document parsed synchronously inside a `post_save` signal could slow an API's create/patch request or one iteration of the periodic refresh loop, identical in kind to `import-openapi-endpoints`'s own accepted risk. → **Mitigation:** none needed at expected scale (seed data tops out at a handful of channels per API); revisit only with real evidence, same threshold already applied to the OpenAPI importer.
- **[Risk]** A spec that validly represents a channel/operation shape this parser doesn't recognize (e.g. an exotic 3.0 `messages` narrowing, a 2.x channel `bindings`-only definition with no `publish`/`subscribe`) silently skips that one operation rather than erroring loudly. → **Mitigation:** every skip is logged (`logger.warning`, channel/operation-scoped, mirroring `openapi_import.py`'s per-operation skip logging) — a single malformed channel/operation does not blank out the rest of a spec's import, same posture as the OpenAPI importer's Decision 5.

## Migration Plan

- One new Django migration in `atlas_plugin_apis` adding `ApiDetails.operations_synced_at` (nullable datetime) and `ApiDetails.operations_sync_failed` (boolean, default `False`) — purely additive, no change to `ApiOperation`/`ServiceOperationUsage`'s existing schema (`add-operation-subscription-explorer`'s tables are reused as-is), and no change to the existing `endpoints_synced_at`/`endpoints_sync_failed` columns.
- No data backfill: on deploy, every existing `asyncapi`-typed API with non-empty `spec_content` gets operations on its next save or periodic refresh, not immediately — same accepted one-time gap `import-openapi-endpoints`'s own Migration Plan already documented and accepted for `spec_source='inline'` APIs whose content hasn't changed since before this change.
- Seed data: `seed_booking_demo.py`'s corrected and enriched `ASYNCAPI_SPEC`/`BOOKING_EVENTS_ASYNCAPI_SPEC` text ships in this change, and `OPERATIONS`/`_create_operations()` are removed (Decision 6) — a fresh run of `seed_booking_demo` after this change produces the same `operation_key`s and equivalent documentation content as before, now written by the importer instead of a parallel hand-authored dict, with `_create_operation_usages()` looking up those importer-produced rows instead of rows a fixture just created.
- Rollback: reverse the one migration (drop the two new columns); any `ApiOperation` rows already created by the importer are ordinary rows indistinguishable from admin-authored ones and are **not** removed by rollback — same as `import-openapi-endpoints`'s own rollback stance.

## Open Questions

- **Exact AsyncAPI 3.0 message-indirection shapes** (channel-local `messages` map vs. `components.messages`, an operation's own `messages` array narrowing a channel's full message set) — this design states the intended *behavior* (walk the channel's referenced messages, treat an unresolved `$ref` as name-only per Non-Goals) but the precise field paths should be re-verified against the primary AsyncAPI 3.0 spec source during implementation, the same way `add-operation-subscription-explorer` re-verified 2.x `publish`/`subscribe` semantics before committing them to this model.
- **Should `seed_booking_demo.py` gain a third, AsyncAPI 3.0-typed demo API** so this importer's 3.0 path has real seed coverage, the way 2.x already does via `ASYNCAPI_SPEC`/`BOOKING_EVENTS_ASYNCAPI_SPEC`? Not decided here; worth resolving during task planning rather than shipping 3.0 support with zero seed-data exercise of it.
