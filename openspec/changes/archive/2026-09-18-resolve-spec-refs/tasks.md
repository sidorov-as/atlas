## 2. Shared `$ref` resolver (`atlas_plugin_apis/spec_refs.py`)

- [x] 2.1 Create `plugins/apis/backend/atlas_plugin_apis/spec_refs.py` with `resolve_schema(node, spec: dict, *, path: frozenset[str] = frozenset(), merge_siblings: bool = False) -> Any`. The walk is **schema-aware, not "any dict/list"** (design.md Decision 1): recurse only into `properties` (each value), `items`, `additionalProperties` (when it's a dict, not a bare `bool`), `allOf`/`oneOf`/`anyOf` (each list member), and `not` — never into `example`, `examples`, `default`, `enum`, or `const` (those hold arbitrary user data that may itself contain a `$ref`-shaped key with no schema meaning at all). Whenever the node passed in (top-level call) or one of these schema-bearing positions is a `dict` containing `"$ref"`, strip the leading `#` from the pointer string (`jsonpointer.resolve_pointer` requires a bare `/...`-rooted pointer — confirmed it raises `JsonPointerException` on a `#/...` fragment), resolve it via `jsonpointer.resolve_pointer(spec, ...)`, and recurse into the resolved node
- [x] 2.2 Implement the cycle guard: before recursing into a resolved `$ref`, check whether its pointer string is already in `path`; if so, leave that occurrence as the unresolved `{"$ref": ...}` node instead of recursing; otherwise recurse with `path | {pointer}`
- [x] 2.3 Implement the dangling-pointer case: `jsonpointer.resolve_pointer` raising (pointer not found in the document) leaves that occurrence as the unresolved `{"$ref": ...}` node, same shape as the cycle case, and does not raise out of `resolve_schema`
- [x] 2.4 Implement `merge_siblings` (design.md Decision 7 — **note the corrected fallback rule below**, an earlier draft of this task got it wrong): read every key on the `$ref` node besides `$ref` itself as `siblings`, regardless of `merge_siblings`.
  - **Resolves successfully (not a cycle, not dangling) + `merge_siblings=True`:** recursively resolve each `siblings` value that's itself schema-shaped (`resolve_schema(value, spec, path=path, merge_siblings=True)` — a sibling can itself carry a `$ref`, e.g. a local `not`/`allOf` override), then shallow-overlay the (now-resolved) `siblings` on top of the recursively-resolved target (sibling wins on a key collision; no deep merge into the target's own `properties`).
  - **Cycle or dangling + `merge_siblings=True`:** return the node unchanged (`$ref` + `siblings`).
  - **Any outcome (resolves, cycles, or dangles) + `merge_siblings=False`:** return `{"$ref": "<pointer>"}` alone — `fallback = node if merge_siblings else {"$ref": pointer}`. Do **not** reuse `node` unchanged for the cycle/dangling case regardless of `merge_siblings` — that was an earlier draft's bug: it leaks `siblings` (e.g. a `description`) onto an unresolved-`$ref` node even when `merge_siblings=False`, and `EndpointSchemaViewer` renders `schema.description` unconditionally (`EndpointSchemaViewer.tsx` lines 52-53, outside its `$ref`-vs-`type` label branch), so that leaked sibling would visibly render under the leaf on the AsyncAPI side, where it must not.
- [x] 2.5 Unit tests for `spec_refs.py` in isolation: a bare top-level `$ref` resolves to its target's expanded content; a `$ref` nested inside a property resolves; a `$ref` resolving to another `$ref` (a chain) fully resolves through the chain; a self-referential schema (direct: property refs its own containing schema) stops at the cycle and leaves that occurrence unresolved; a schema referenced from two independent, non-overlapping branches resolves fully on both branches (not treated as a cycle); a dangling `$ref` (pointer resolves to nothing) is left unresolved without raising; a `#/...`-fragment pointer resolves correctly (guards against regressing the normalization in 2.1); a `$ref` found inside `example`/`examples`/`default`/`enum`/`const` is left completely untouched (regression test for the schema-aware-walk scoping in 2.1 — this is not the cycle/dangling shape, it's "never even looked at"); with `merge_siblings=True`, a `$ref` with a sibling `description` resolves to the target's content plus that `description` overlaid; with `merge_siblings=True`, a sibling key that collides with a key on the resolved target wins over the target's own value; with `merge_siblings=True`, a sibling value that itself contains a `$ref` is resolved before being overlaid; with `merge_siblings=True`, a `$ref` with a sibling `description` that hits a cycle keeps that `description` on the returned unresolved node; with `merge_siblings=True`, the same for a dangling pointer; with `merge_siblings=False` (the default), each of the three outcomes — resolves, cycles, dangles — is tested separately and none of them attach the sibling `description` to the returned node (this 3-way split is the direct regression test for 2.4's corrected fallback rule)

## 3. AsyncAPI: message identity resolution (`asyncapi_import.py`)

- [x] 3.1 Extend `_resolve_channel_message` (3.0 path) into a **loop, not a single dereference** (design.md Decision 5): starting from the channel's `messages.<name>` entry, while the current node is a `dict` with a string `$ref` key (`isinstance(node, dict) and isinstance(node.get('$ref'), str)`), track visited pointers in a `path: frozenset[str]` and dereference `<pointer>` against the full spec dict (e.g. into `components.messages`). Stop and map the node via `_map_message` as soon as it is **not** itself a `$ref` — regardless of whether it has a `payload` key. **Do not use `_has_inline_payload`/`'payload' in message` as the stop condition** (an earlier draft of this task did): AsyncAPI's Message Object has no required fields, so a valid, final message with only `name`/`title`/`summary` and no `payload` must still stop the loop and get mapped, not get mistaken for an unresolved reference. Fall back to today's name-only stub in exactly two cases: the pointer doesn't resolve to anything (dangling), or the pointer is already in `path` (cycle) — both are the same fallback shape, not two different ones.
- [x] 3.2 Extend `_map_message`/`_extract_messages_2x` (2.x path) with the equivalent loop-with-cycle-guard fix, using the same `$ref`-presence stop condition as 3.1 (not `_has_inline_payload`): when a channel's `publish`/`subscribe` `message` field (or a `oneOf` member) is `{"$ref": "<pointer>"}`, dereference it the same way (following a chain, guarding cycles) before mapping; produce a name derived from the ref's last path segment (matching 3.0's existing fallback shape) rather than an empty-name entry when the pointer doesn't resolve or cycles
- [x] 3.3 Fix `_extract_messages_3x`'s no-explicit-`messages`-narrowing branch (today: `[_map_message(m) for m in channel_messages.values() if _has_inline_payload(m)]`, which has the same bug twice over — it silently drops any channel-map entry that is itself a `$ref` *and* it would drop a valid inline, payload-less Message Object too): route each `channel_messages` entry through the same dereference-loop-or-fall-back-to-stub logic as 3.1, keyed on the `$ref`-presence check, instead of filtering on `_has_inline_payload` and discarding the rest — a channel whose messages are all `$ref`s into `components.messages`, never narrowed by any operation's own `messages[]`, must still surface them, and a channel with an inline payload-less message must not lose it either.
- [x] 3.4 Wire the resolved message object's `payload` (and any nested `$ref`s within it) through `spec_refs.resolve_schema(payload, spec)` (default `merge_siblings=False`, per design.md Decision 7) before assigning it to the mapped message's `schema`, in both the 2.x and 3.0 code paths
- [x] 3.5 Extend the malformed-entry catch (`_parse_channels_2x`/`_parse_operations_3x`'s existing per-channel/per-operation `try`/`except`) to also cover the new dereferencing step, so a pathological reference (e.g. one the cycle guard can't help with) still logs-and-skips that one operation rather than aborting the whole spec's parse
