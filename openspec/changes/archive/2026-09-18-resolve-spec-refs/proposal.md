## Why

`asyncapi_import.py` and `openapi_import.py` both deliberately never resolve `$ref` against a document's `components`/`definitions` — a considered Decision in both archived designs (`import-openapi-endpoints`, `import-asyncapi-operations`), reused verbatim by `EndpointSchemaOut`/`EndpointSchemaViewer` and `OperationMessageOut`. For OpenAPI this degrades gracefully: a response/request schema slot is always a single, unambiguous location, so an unresolved `$ref` still renders as a labeled leaf (e.g. `User`, `Error`) — confirmed live on `test-api GET /v1/users/{id}`, whose `4xx` responses all show only the word "Error", five times, with no fields. For AsyncAPI 3.0 it degrades much further: a real-world spec ("Orders Events API", `test-asyncapi`) structures messages with two hops of indirection — an operation's `messages[]` entry `$ref`s into a channel's own `messages` map, whose entry is *itself* just a `$ref` into `components.messages` — and the parser only follows the ref's name, never dereferences into `components`, so it falls back to a name-only stub with no schema at all. The operation's Message tab is completely empty. This exact shape was flagged as an untested Open Question in `import-asyncapi-operations`' design.md ("the 3.0 message-indirection walker... is the one piece of this design not yet exercised against a real 3.0 document") and a real spec has now hit it. AsyncAPI 2.x has the same gap with no fallback at all (`_map_message` on a bare `{$ref: ...}` message field yields an entry with an empty `name` too), an untested corner of the existing suite.

Both importers' unresolved-`$ref` stance was a reasonable call when the model had no seed evidence it degrades this badly — that evidence now exists. This change reverses that stance for both importers: `$ref` values are resolved against the same document's `components`/`definitions` at sync time, so the catalog stores and displays the message/schema content a spec actually documents instead of a bare pointer or an empty tab.

## What Changes

- **AsyncAPI message identity resolution (2.x and 3.0):** when a channel's `messages.<name>` entry, or the message a 2.x `publish`/`subscribe` (or `oneOf` member) points at, is itself an unresolved `{"$ref": ...}` rather than an inline message object, dereference through to the real message object (typically in `components.messages`) before mapping it. Replaces today's "give up with a name-only stub" (3.0) or "give up with an empty entry" (2.x, unguarded today) with the actual message's `payload`/`examples`/`name`/etc.
- **Shared schema-content resolution (AsyncAPI + OpenAPI):** a new resolver, used by both `asyncapi_import.py` and `openapi_import.py`, recursively resolves `$ref` values found inside a `payload`/parameter/request-body/response schema against the same document's `components.schemas` (3.x) / `definitions` (Swagger 2.0), producing an expanded schema tree instead of a bare `{"$ref": ...}` leaf. A key found alongside a `$ref` (a sibling, e.g. a local `description` override) is discarded on AsyncAPI's side, matching its Reference Object semantics exactly; on OpenAPI's side it's preserved (overlaid on top of the resolved target) as a deliberate pragmatic policy, not because OpenAPI 3.0/Swagger 2.0's own Reference Object semantics call for it — only 3.1's JSON-Schema-based `$ref` does, and this plugin doesn't distinguish 3.0 from 3.1 (design.md Decision 7).
- **Cycle safety:** the resolver tracks the `$ref` path currently being expanded; re-entering a `$ref` already on that path stops recursion and represents that occurrence as an unresolved `{"$ref": ...}` node instead of expanding it again — `EndpointSchemaViewer` already renders that shape as a labeled leaf, so a self-referential schema (e.g. a `Category` with `children: Category[]`) degrades to "expand down to the cycle, then a leaf label" rather than looping or erroring.
- **New dependency:** `jsonpointer` (RFC 6901 pointer resolution only — `~0`/`~1` escaping, array indices). The recursive walk, `components`-root lookup, and cycle guard around it are hand-rolled, consistent with both importers' existing "hand-rolled walker, no spec object-model dependency" precedent; this is not a `prance`/`openapi-core`-style full spec object model, and all `$ref`s in scope are internal-document-only (`#/...`) so no remote-ref resolution is needed.
- Resolution happens once, at sync time (inside `sync_operations_from_spec`/`sync_endpoints_from_spec`), and the resolved shape is what gets denormalized onto `ApiOperation.message`/`ApiEndpoint.request`/`ApiEndpoint.responses` — consistent with how `channel_protocol`/`tags`/etc. are already computed once at sync time rather than resolved on read.
- `EndpointSchemaViewer` (frontend) requires no code change — it already renders both an expanded property tree and a bare `$ref` leaf; there's no existing test suite for it today (`EndpointSchemaViewer.tsx` has no `.test.tsx` sibling), so this change adds a new `EndpointSchemaViewer.test.tsx` with a resolved-schema fixture to confirm no regression, not new rendering logic.
- **BREAKING (behavioral, not API-breaking):** a message/parameter/request/response schema that today stores a bare or nested `$ref` string will, after this change, store the resolved schema content instead (or a deeper unresolved `$ref` only where a real cycle is detected). Existing tests asserting the old verbatim-`$ref` behavior (`test_ref_payload_is_stored_verbatim_and_unresolved`, `test_3x_bare_ref_message_with_no_inline_payload_yields_name_only_entry` in `atlas_plugin_apis/tests/test_asyncapi_import.py`, and the analogous OpenAPI test) are deliberately rewritten to assert the new resolved behavior, not incidentally broken.

**Non-Goals (explicitly out of scope for this change):**
- New fields not currently modeled at all — `message.headers`, `message.correlationId`, more than the first `message.examples[]` entry, message-level `tags`/`externalDocs`, operation-level `bindings`/`externalDocs`, channel-level `title`/`summary`/`description` distinct from the operation's own `description`. Real gaps, but a separate, narrower follow-up once identity/schema resolution lands.
- Any vendor/custom spec extension (e.g. an `x-catalog`-shaped block) — out of scope entirely, not part of standard AsyncAPI/OpenAPI.
- External (`http(s)://`, remote-file) `$ref` resolution — every `$ref` in scope is an internal JSON Pointer into the same document.

## Capabilities

### New Capabilities
(none — this change modifies the resolution behavior of two existing import capabilities; it does not introduce a new user-facing capability of its own)

### Modified Capabilities
- `asyncapi-operation-import`: the existing requirement "Message payload schema is stored unresolved" is replaced — a message's payload schema is now resolved against `components.schemas` (except where a real reference cycle stops recursion), and a channel/operation message reference that itself resolves through one or more `$ref` hops is dereferenced into the real message object instead of yielding a name-only stub.
- `openapi-endpoint-import`: the existing requirement "Schema `$ref` values are stored unresolved" is replaced — parameter, request body, and response schemas are now resolved against `components.schemas` (3.x) / `definitions` (Swagger 2.0), except where a real reference cycle stops recursion.

## Impact

- **Backend (`plugins/apis/backend/atlas_plugin_apis`):** new shared resolver module (used by both importers); `asyncapi_import.py` gains message-identity dereferencing (2.x and 3.0) plus schema-content resolution; `openapi_import.py` gains schema-content resolution for parameters/request bodies/responses; `requirements`/`pyproject` gains the `jsonpointer` dependency.
- **Tests:** `test_asyncapi_import.py` and `test_openapi_import.py` get rewritten fixtures/assertions for the new resolved behavior (including new cycle and cross-component-reference fixtures), replacing the two tests named above that encode the old stance.
- **Frontend (`plugins/apis/frontend`):** no functional change to `EndpointSchemaViewer`/`OperationMessageTab.tsx`; a new `EndpointSchemaViewer.test.tsx` suite (none exists today) adds coverage for a resolved (expanded) schema tree to confirm the existing renderer handles it without change.
- **No change** to `ApiOperation`/`ApiEndpoint` model shape, migrations, signals wiring, or the create/update/revive/soft-remove upsert rules — this change only affects what content lands inside the already-existing `message`/`request`/`responses` JSON fields.
