## Context

`atlas_plugin_apis` has two hand-rolled spec walkers — `openapi_import.py` (`import-openapi-endpoints`) and `asyncapi_import.py` (`import-asyncapi-operations`) — that both made the same considered call: never resolve `$ref` against `components`/`definitions`, store it verbatim, and let `EndpointSchemaOut`/`EndpointSchemaViewer` (shared by `ApiEndpoint.request`/`.responses` and `ApiOperation.message`) render a bare `{"$ref": ...}` as a labeled leaf. That call held up fine for OpenAPI, where a schema always sits in one unambiguous slot (`requestBody.content[type].schema`, `responses[code].content[type].schema`) — confirmed live against `test-api GET /v1/users/{id}`, whose response schemas are bare `$ref`s to `User`/`Error` and render as exactly that: a leaf label, no properties, but not empty.

AsyncAPI 3.0 breaks the same assumption harder. A real spec ("Orders Events API") reaches a message through two `$ref` hops: an operation's `messages[]` entry `$ref`s to `#/channels/orderCreated/messages/OrderCreated`, whose value in the channel's own `messages` map is *itself* only `{"$ref": "#/components/messages/OrderCreated"}` — not an inline message. `asyncapi_import.py`'s `_resolve_channel_message` looks up that name in the channel's `messages` map, finds a dict with no `payload` key (because it's still a `$ref`, not the real message), and falls back to a name-only stub. The operation's Message tab renders completely empty. This exact shape was an explicit, flagged Open Question in `import-asyncapi-operations`' own design.md ("not yet exercised against a real 3.0 document") — it now has been, and it fails badly. AsyncAPI 2.x has the same root gap with a worse fallback: `_map_message` on a bare `{"$ref": ...}` message field produces an entry with an empty `name`, not even the ref-derived name 3.0 falls back to — an untested corner of the current suite.

This design reverses both importers' "never resolve" stance, replacing it with: resolve what the document itself defines, and only fall back to an unresolved `$ref`/name-only stub for something a resolver genuinely can't reach (a dangling pointer, or a real reference cycle).

## Goals / Non-Goals

**Goals:**
- Resolve an AsyncAPI message reference through as many `$ref` hops as the document actually defines (channel's `messages` map entry → `components.messages`, or any other in-document indirection) before falling back to a name-only stub — for both 2.x and 3.0, fixing 2.x's currently-worse, untested fallback along the way.
- Resolve `$ref` values found inside a payload/parameter/request-body/response schema against the same document's `components.schemas` (3.x) / `definitions` (Swagger 2.0), recursively, so `EndpointSchemaViewer` can render the properties a spec actually documents instead of a bare pointer label — for both AsyncAPI and OpenAPI, via one shared resolver.
- Never loop or crash on a genuinely self-referential schema; degrade to an unresolved `$ref` leaf at the exact point a cycle is detected, not before.
- Do this with a minimal, narrowly-scoped dependency addition, consistent with both importers' existing "hand-rolled walker, no spec object-model dependency" precedent.
- Resolve once, at sync time, so the resolved content is what gets denormalized onto `ApiOperation.message`/`ApiEndpoint.request`/`.responses` — matching how every other derived field in this plugin (`channel_protocol`, `tags`, lifecycle status) is already computed once at sync time, not on read.

**Non-Goals:**
- New fields this parser doesn't already model — `message.headers`, `message.correlationId`, more than the first `message.examples[]` entry, message/operation-level `tags` beyond what's already parsed, `externalDocs`, `bindings`, or channel-level `title`/`summary`/`description`. Real gaps (see the proposal's Non-Goals), left for a narrower follow-up once resolution itself lands.
- Any vendor/custom extension block.
- External (`http(s)://`, separate-file) `$ref` resolution — every `$ref` in every spec this plugin has seen, and every spec AsyncAPI/OpenAPI's own `$ref` conventions expect for a single-document API description, is an internal JSON Pointer (`#/...`). Fetching or caching a remote document is out of scope.
- Any frontend change — `EndpointSchemaViewer` already renders both an expanded tree and a bare `$ref` leaf; this design only changes what shape reaches it.
- A general "resolve `$ref` anywhere in any JSON" utility beyond what these two importers need — the resolver is scoped to `components.schemas`/`definitions`/`components.messages`-shaped lookups inside one already-parsed spec dict, not a standalone package.

## Decisions

### 1. One shared resolver module, used by both importers — not two implementations
**Decision:** Add `atlas_plugin_apis/spec_refs.py` with a single entry point, roughly `resolve_schema(node, spec: dict, *, path: frozenset[str] = frozenset(), merge_siblings: bool = False) -> Any` (`Any`, not `dict` — a schema node can legitimately be a `list` (e.g. `allOf`/`oneOf`/`anyOf` members) or a JSON Schema boolean (`true`/`false`, valid as an `additionalProperties`/`items` value), not only a `dict`), that recursively walks a schema-shaped node, replacing any `{"$ref": "<pointer>", ...}` it finds with the resolved node's own (recursively resolved) content, using `jsonpointer.resolve_pointer(spec, pointer)` for the actual lookup. Both `asyncapi_import.py` and `openapi_import.py` call this on every schema value they currently store verbatim (`payload`, parameter `schema`, request body `schema`, response `schema`); `openapi_import.py` passes `merge_siblings=True`, `asyncapi_import.py` uses the `False` default (see Decision 7).

**The walk is schema-aware, not "any dict/list whatsoever":** `resolve_schema` only recurses into positions a JSON Schema / OpenAPI / AsyncAPI schema object actually uses to nest a subschema — `properties` (each value), `items`, `additionalProperties` (when it's a schema, not a bare `bool`), `allOf`/`oneOf`/`anyOf` (each list member), and `not`. It does **not** recurse into `example`, `examples`, `default`, `enum`, or `const` — those hold arbitrary user data that may happen to contain a key literally named `$ref` (e.g. `example: {"$ref": "#/components/schemas/User"}` as a piece of example JSON, not a schema reference), and treating that as something to dereference would corrupt user data the resolver has no business touching. A `{"$ref": ...}` found at the schema's own top level (the node passed into `resolve_schema` itself) is always eligible for resolution regardless of position — it's the caller's job (Decisions 3/4 of the OpenAPI/AsyncAPI importers) to only ever call `resolve_schema` on an actual schema-bearing value (`payload`, a parameter/request-body/response `schema`), never on an `example`/`default` value.

**Why:** `$ref` → `components.schemas`/`definitions` resolution is format-agnostic — it doesn't touch the `paths`-vs-`channels` structural walking that both archived designs' Decision 3 already declined to share (that decision was about *not* building one shared walker for two structurally different document shapes; this is a much narrower, genuinely shared concern: "given this whole parsed dict and a JSON Pointer string, give me the node"). Splitting it into two copies would mean fixing the same cycle-guard bug twice if one is ever found. The one behavioral knob that does differ by format (`merge_siblings`, Decision 7) is a caller-supplied flag, not a hidden per-format branch inside the resolver — the recursive walk, cycle guard, and pointer lookup stay identical for both callers. Scoping the walk to schema-bearing keywords only (rather than "every dict/list found anywhere") matters because this data isn't a resolver-owned document — `example`/`default`/`enum`/`const` values are arbitrary content an API author wrote, and a naive "recurse into everything" walk would silently rewrite that content the first time it happened to contain a `$ref`-shaped key, which is a real (if narrow) way for this change to corrupt data it was never asked to touch.

**Alternative considered:** Resolve inline inside each importer, no shared module. Rejected: the resolution logic (recursion + cycle guard + `jsonpointer` lookup) is identical for both; the only per-importer difference is *which* fields get passed through it, which stays in each importer's own code.

### 2. Resolve at sync time, denormalized into storage — not lazily at read/serialize time
**Decision:** Resolution happens inside `sync_operations_from_spec`/`sync_endpoints_from_spec`, before the resolved shape is written into `ApiOperation.message`/`ApiEndpoint.request`/`.responses`. The API layer (`api/schemas.py`'s `OperationMessageOut`/`EndpointSchemaOut`) is unchanged — it already just serializes whatever's stored.

**Why:** Every other piece of derived data in this plugin (`channel_protocol`, `tags`, operation/endpoint lifecycle `status`) is already computed once at sync time and stored, not recomputed per request. Resolving at read time would mean carrying the full parsed spec dict (or re-parsing `spec_content`) through to the serializer for every list/detail request — a bigger, cross-cutting change to the read path for no behavioral benefit, since the spec only changes on sync anyway.

**Alternative considered:** Store `schema`/`message` as-is (verbatim, current behavior) and resolve lazily inside `OperationMessageOut`/`EndpointSchemaOut` at serialization time. Rejected: reintroduces a "resolve against what spec?" problem (the serializer doesn't have the parent `ApiDetails.spec_content` in scope today, and threading it through is more invasive than resolving once where the full document is already in hand), and diverges from this plugin's established denormalize-at-sync pattern for no gain.

### 3. New dependency: `jsonpointer` only — not `jsonref`, `referencing`, or a spec-object-model library
**Decision:** Add `jsonpointer` (PyPI) for RFC 6901 pointer resolution (`~0`/`~1` escaping, array-index segments) only. The recursive walk over a schema dict/list, and the cycle guard around it, are hand-rolled in `spec_refs.py`. `jsonpointer.resolve_pointer` expects a pointer starting with `/` (e.g. `/components/schemas/User`), not a URI fragment — confirmed directly (`jsonpointer.resolve_pointer(doc, "#/a/b")` raises `JsonPointerException: Location must start with /`; `"/a/b"` succeeds). Every `$ref` string in scope here is a `#`-prefixed fragment (`#/components/schemas/User`), so `resolve_schema` strips the leading `#` before calling `resolve_pointer` — a one-line normalization, not a parsing step.

**Why:** All `$ref`s in scope are internal (`#/...`); no library's remote/file-ref-fetching machinery is needed. `jsonref`'s eager mode recurses into real cycles unguarded (`RecursionError`) and its lazy-proxy mode isn't directly `json.dumps`-able into a `JSONField`, so a custom cycle guard would be layered on top of it regardless — buying little over hand-rolling the walk. `referencing` is a lower-level `Registry`/`Resolver.lookup` primitive; using it still means writing the same recursive walk and cycle guard this design writes anyway, just against a different single-lookup primitive than `jsonpointer.resolve_pointer`. A full spec-object-model dependency (`prance`, `openapi-core`) is explicitly what both archived designs' Decision 3 already rejected, twice, and AsyncAPI has no comparably mature Python-side equivalent regardless.

**Alternative considered:** Zero new dependencies — hand-roll JSON Pointer resolution too (split on `/`, unescape `~1`→`/`/`~0`→`~`, index into dict/list). Rejected only narrowly: pointer-escaping edge cases are exactly the kind of thing worth not re-verifying by hand when a small, single-purpose, dependency-free-itself library already does it correctly; the actual walker/cycle-guard logic — the part with real design risk — stays hand-rolled either way.

### 4. Cycle guard tracks the current expansion path, not a global "already seen" set
**Decision:** The `path: frozenset[str]` parameter threaded through `resolve_schema` accumulates the pointer strings currently being expanded along *this* recursive descent. Encountering a `$ref` already in `path` stops recursion and leaves that occurrence as an unresolved `{"$ref": ...}` node. A `$ref` resolved once on one branch and again independently on a sibling branch (the common, non-cyclic case — e.g. two different properties both pointing at `#/components/schemas/Money`) is resolved fully both times, since neither occurrence is its own ancestor.

**Why:** A global "resolve each distinct `$ref` only once, ever" cache would incorrectly flatten the second-and-later legitimate, non-cyclic use of a shared component into an unresolved stub — exactly the failure mode this change exists to eliminate (most reuse-heavy specs, like the ones this change was motivated by, reference the same shared schema from many places on purpose). Tracking the live path instead of a global set only stops the case that's actually unsafe: a `$ref` that would expand into itself.

**Alternative considered:** A fixed maximum recursion depth instead of path-tracking. Rejected as the primary mechanism: an arbitrary depth cap would either reject legitimately deep (but finite) real-world schemas or fail to catch a cycle that loops within the cap — path-tracking catches exactly the unsafe case with no false positives on deep-but-acyclic schemas. (A depth cap as a secondary, defense-in-depth safety net against a pathologically wide/deep but acyclic schema is flagged under Risks, not adopted as the detection mechanism.)

### 5. AsyncAPI message-identity resolution stays in `asyncapi_import.py`, not the shared resolver
**Decision:** Dereferencing a channel/operation's message reference through to the real message object (`_resolve_channel_message`'s job today, extended to follow a `$ref` found at the channel-map-entry level too, and the equivalent fix to 2.x's `_map_message`) is AsyncAPI-shaped domain logic — it knows about `channels`, `operations`, and the Message Object's own fields (`payload`, `examples`, `name`, ...). Only once a message object is in hand does its `payload` get passed through the shared `spec_refs.resolve_schema`. OpenAPI has no equivalent identity-indirection step to share (Context) — its `schema` slot is already the thing to resolve, directly.

This dereferencing step is a **loop, not a single hop**, with its own path-tracking cycle guard — the same shape as Decision 4's, but kept separate from `spec_refs.py` per this decision's own rationale (it's walking message identity, not schema content). Starting from a channel-map entry (or, in 2.x, a bare `publish`/`subscribe`/`oneOf` message field), repeatedly follow `{"$ref": ...}` — typically into `components.messages`, but the loop doesn't assume a fixed depth — accumulating visited pointers in a `path: frozenset[str]`, until either: the current node is **not itself a `{"$ref": ...}` dict** (it's a real Message Object — mapped via `_map_message` regardless of whether it happens to have a `payload`, see below); a pointer is encountered that's already in `path` (cycle: fall back to the name-only stub, same fallback shape as a dangling pointer); or a pointer doesn't resolve to anything (dangling: same fallback). This matters even though the change's motivating case (`test-asyncapi`'s "Orders Events API") only exercises one extra hop — the Goals section's "as many `$ref` hops as the document actually defines" and the delta spec's blanket cycle-safety wording (`specs/asyncapi-operation-import/spec.md`) both already commit to arbitrary depth, and a single-hop-only implementation would silently under-deliver on that as soon as a document chains two message aliases.

**The loop's stop condition is "not a `$ref`," not "has a `payload`."** AsyncAPI's Message Object spec makes every one of its fields optional, including `payload` — a valid message can carry only `name`/`title`/`summary`/`headers` and no `payload` at all. `_has_inline_payload` (today's `'payload' in message` check, reused by the current draft of this design) conflates two unrelated questions: "is this node still an unresolved Reference Object?" and "does this message happen to document a payload?" A real, payload-less Message Object would fail `_has_inline_payload` and get incorrectly treated as still-unresolved — falling back to a name-only stub (in `_resolve_channel_message`) or being silently dropped (in the no-`messages[]`-narrowing branch below), even though it's already the real, final message object with nothing left to dereference. The correct check is structural, not content-based: `isinstance(node, dict) and isinstance(node.get('$ref'), str)` — true means "still a reference, keep dereferencing," false means "this is the Message Object itself, map it now via `_map_message`" (whose own handling of an absent `payload`, i.e. `schema: None`, is already correct and unchanged by this decision).

**Also folded into this decision:** `_extract_messages_3x`'s no-explicit-`messages`-narrowing branch (today: `[_map_message(m) for m in channel_messages.values() if _has_inline_payload(m)]`) has the same bug twice over — it drops every channel-map entry that is itself a `$ref` (never dereferencing it), *and* it would drop a valid inline, payload-less Message Object too, for the reason above. This branch needs the same dereference-loop applied per entry, keyed on "is this still a `$ref`," not a `_has_inline_payload` filter — so a channel that defines all its messages only as `$ref`s into `components.messages` (never narrowed by any operation's own `messages[]`) still surfaces them, and a channel with an inline, payload-less message doesn't lose it either.

**Why:** Keeps the shared module honestly scoped to "resolve `$ref`s inside a schema tree," matching Decision 1's rationale for *why* schema-content resolution is shared (format-agnostic) and *why* structural/identity walking isn't (format-specific) — the same boundary both archived designs already drew between the two importers' incompatible document shapes. The loop-with-cycle-guard (rather than one dereference) matches this design's own Goals and the delta spec's requirement text, which both already promise multi-hop, cycle-safe resolution for message identity, not just schema content — a single-hop implementation would meet the motivating example but not the requirement as written. Checking "is this a `$ref`" instead of "does this have a `payload`" is the only criterion that matches what a Reference Object actually is per the AsyncAPI spec — the presence of `payload` is a fact about a Message Object's content, not about whether the node in hand is a reference still waiting to be resolved.

### 6. A resolver that can't reach a real object still falls back the same way today's code does
**Decision:** `spec_refs.resolve_schema` and the AsyncAPI message-identity step both leave a `$ref` unresolved (schema) or fall back to a name-only stub (message identity) when the pointer is dangling (points at nothing in the document) — not only on a detected cycle. This preserves the existing "one malformed operation/channel is skipped and logged, not fatal" posture (`specs/asyncapi-operation-import/spec.md`'s and `specs/openapi-endpoint-import/spec.md`'s "Parse failures never interrupt..." requirements, unchanged by this design) for a spec that references something that genuinely isn't there.

**Why:** This change is about resolving what a document actually, resolvably defines — not about being stricter toward malformed specs than today's parser already is. A dangling `$ref` is a spec authoring error this plugin has never treated as fatal, and shouldn't start now.

### 7. Sibling keys next to `$ref`: merged for OpenAPI (`merge_siblings=True`), discarded for AsyncAPI
**Decision:** OpenAPI 3.0/Swagger 2.0's Reference Object and AsyncAPI 2.x/3.0's Reference Object both specify that sibling keys next to `$ref` are meaningless — but OpenAPI 3.1's Schema Object follows JSON Schema 2020-12, where `$ref` is just another keyword and siblings apply alongside it. This plugin doesn't distinguish `openapi: "3.0"` from `"3.1"` anywhere today (`_version_of` buckets both into one `VERSION_3X`), and adding that distinction just for this would be a new axis of version-awareness for one narrow corner. Instead: `resolve_schema` takes a `merge_siblings: bool = False` parameter. `openapi_import.py` always passes `merge_siblings=True` (covering 3.0, 3.1, and Swagger 2.0 uniformly — a pragmatic broadening beyond strict 3.0/2.0 semantics, not a dialect-accurate implementation); `asyncapi_import.py` uses the `False` default (matching AsyncAPI's Reference Object semantics exactly, both versions).

Mechanically: a `{"$ref": "<pointer>", **siblings}` node's `siblings` (every key except `$ref`) are read regardless of `merge_siblings`, but what happens to them depends on both `merge_siblings` and whether resolution succeeds:

- **`merge_siblings=True`, pointer resolves (not a cycle):** the siblings are themselves first resolved recursively (`resolve_schema(siblings_value, spec, path=..., merge_siblings=True)` for any sibling value that's itself schema-shaped — a sibling can legitimately contain its own `$ref`, e.g. a local `not`/`allOf` override next to the main `$ref`), then shallow-overlaid on top of the recursively-resolved target (sibling wins on a key collision; the overlay itself is shallow — no deep merge into the target's own `properties`).
- **`merge_siblings=True`, cycle or dangling:** the node is returned unchanged — `$ref` plus its siblings — so an authored sibling (e.g. a local `description` override) survives a cycle-stop or dangling ref exactly as it survives a successful resolve.
- **`merge_siblings=False`, any outcome (resolves, cycles, or dangles):** the fallback/result is always `{"$ref": "<pointer>"}` alone — siblings are read but never attached to what's returned, on *any* path, not only the successful-resolve one. Concretely: `fallback = node if merge_siblings else {"$ref": pointer}` for the cycle/dangling case specifically, mirroring the equivalent choice already made for the success case. This is a correction from an earlier draft of this decision, which returned `node` (siblings included) unchanged on cycle/dangling *regardless* of `merge_siblings` — reasoning that a leftover sibling was "inert" for AsyncAPI because `EndpointSchemaViewer`'s `typeLabel()` only reads `schema['$ref']`/`type` for the label. That reasoning missed that `SchemaNode` renders `schema.description` (`EndpointSchemaViewer.tsx` lines 52-53) *unconditionally*, outside the `$ref`-vs-`type` branch — so a `description` sibling left on an unresolved `$ref` node by mistake would visibly render under the leaf, which is exactly the AsyncAPI-side leak this design needs to not have. Every one of the three outcomes (resolves / cycles / dangles) needs its own explicit test under `merge_siblings=False` (task 2.5) precisely because this was wrong once already.

**Why:** A uniform "always discard siblings" rule (the simplest option) would be spec-correct for AsyncAPI and OpenAPI 3.0/Swagger 2.0, but silently drops author-written content (most commonly a local `description` override) on any real OpenAPI 3.1 document that uses the dialect's own sibling-keyword allowance — a real, visible regression in `EndpointSchemaViewer`, which already renders `schema.description`. A fully dialect-aware alternative (merge only when the document actually declares `"openapi": "3.1.x"`, discard for 3.0) would be spec-accurate for both OpenAPI dialects, but costs introducing 3.0-vs-3.1 branching this plugin has never needed before, for a corner with no observed motivating spec (unlike the message-indirection and schema-`$ref` gaps, which `test-asyncapi`/`test-api` demonstrate directly) — deferred rather than built speculatively, consistent with this design's existing "revisit only with real evidence" posture (Risks). Format-level (not dialect-level) scoping via one caller-supplied bool is the middle ground: cheap, keeps `resolve_schema`'s walk/cycle-guard/pointer-lookup identical for both callers (Decision 1), and only OpenAPI (where the real gap was identified) changes behavior.

**Alternative considered:** Deep/recursive merge (treat `$ref` + siblings as an implicit `allOf`, per JSON Schema 2020-12's actual application model, applying both schemas' constraints independently rather than overlaying one dict onto another). Rejected for this change: a shallow top-level overlay handles the common real-world pattern (a local `description`/`example`/`nullable` override) correctly, and the cases where shallow overlay and true `allOf` semantics diverge (e.g. a sibling `required` alongside a `$ref` target that has its own `required`) are speculative — no seed spec exercises them, and building `allOf`-accurate merge semantics is a materially bigger resolver than this change's stated scope.

## Risks / Trade-offs

- **[Risk]** Resolved (expanded) schema content is now denormalized into every message/schema slot that references a shared component, instead of a short `$ref` string — `ApiOperation.message`/`ApiEndpoint.request`/`.responses` JSON grows, proportionally to how many operations/endpoints share one large component and how deep it nests. → **Mitigation:** accepted; this plugin already fully denormalizes everything else it derives at sync time, and expected spec sizes (per both archived designs' own accepted-risk language for synchronous `post_save` parsing) are small. Revisit only with real evidence of a specific spec causing a problem.
- **[Risk]** A pathologically deep but acyclic schema graph (not a cycle, just very deep nesting) could make one sync pass slower or more stack-heavy than today's non-recursive verbatim copy. → **Mitigation:** none built in beyond ordinary Python recursion limits; flagged as an Open Question below rather than solved speculatively, consistent with this plugin's existing "revisit only with real evidence" threshold for post_save parsing cost.
- **[Risk]** This is a deliberate, intentional reversal of a previously-documented, reasoned Decision in both archived designs — a reader of just the old spec text would see the old requirement and assume it still holds. → **Mitigation:** the delta specs for both `asyncapi-operation-import` and `openapi-endpoint-import` explicitly `MODIFIED` (not silently drop) the "stored unresolved" requirements, and this design's Context section states directly why the original reasoning no longer holds now that a real spec exercises it badly.
- **[Risk]** Existing tests (`test_ref_payload_is_stored_verbatim_and_unresolved`, `test_3x_bare_ref_message_with_no_inline_payload_yields_name_only_entry`, and the OpenAPI-side analogue) currently assert the old behavior and will fail once this ships. → **Mitigation:** not a surprise regression — tasks.md scopes rewriting these deliberately as part of this change, asserting the new resolved behavior plus new cycle/cross-reference fixtures, not just enough to make them pass again.

## Migration Plan

- No model or migration changes — `ApiOperation.message`/`ApiEndpoint.request`/`.responses` are existing JSON fields; this change only alters what gets computed into them at sync time.
- No backfill: an existing API's stored rows keep today's verbatim-`$ref`/name-only content until that API's spec next resolves (create, patch, or the next periodic `spec_url` refresh) — the same accepted one-time gap both archived designs already documented for their own initial rollout.
- Rollback: revert the code change. Any rows already re-synced with resolved content are ordinary rows indistinguishable from rows a future sync (with the reverted code) would produce again — no cleanup needed.

## Open Questions

- **Defense-in-depth depth cap:** should `resolve_schema` also enforce a hard maximum recursion depth (independent of the cycle guard) against an extreme, acyclic, generated schema? Leaning no for the initial implementation (Decision 4's alternative) — revisit only if a real spec demonstrates it's needed.
