## Context

The catalog today models two levels of Service↔API relationship:

```
Component --consumesApis[]--> API      (spec field on ComponentDetails, standard-catalog plugin)
Component --providesApis[]--> API      (same)
```

`ComponentDetails.consumes_apis`/`provides_apis` are plain Django `ManyToManyField`s to the generic `CatalogEntity` table, written through the normal Component spec create/update path (`atlas_plugin_standard_catalog.kinds.component_handler`), and the core `entity-relations` capability derives bidirectional, queryable relation rows (`consumesAPI`/`apiConsumedBy`) from them on every write. That derivation is deliberately one-directional: **relations are computed from spec reference fields, never authored directly** (`entity-relations` spec, "Relations are derived, not authored" / "Direct relation authoring is rejected"). That rule is a property of the generic CatalogEntity-to-CatalogEntity relations table specifically.

`API` itself (`ApiDetails`) is owned by the `atlas.apis` plugin, which already declares `requires_plugins={'atlas.standard-catalog': '>=0.1 <1'}` for exactly this `providesApis`/`consumesApis` relationship — the plugin dependency this change needs already exists and is already load-bearing.

This change adds a third, finer-grained level: which specific *endpoints* of an API a Service actually calls. The design source (`endpoint-dependency-explorer-design-spec.md`, an external product/UX spec, not written against this codebase) proposes an `Endpoint` sub-resource of `API` and a `ServiceEndpointUsage` join with its own CRUD API, plus auto-creating `consumesAPI` when a Service is first linked to one of its endpoints. That source spec is UX/product-complete but architecture-naive: it assumes a generic REST CRUD backend and specifies React Flow for the graph. Neither assumption fits this codebase, so this design translates its requirements onto the actual plugin/kind/facet architecture rather than adopting its API/tech choices verbatim.

## Goals / Non-Goals

**Goals:**
- Model `Endpoint` as a child of `API`, owned entirely by `atlas.apis`, with full request/response documentation.
- Model `Service consumesEndpoint Endpoint` as a plugin-owned link with its own lifecycle (create/delete via dedicated endpoints), consistent with how a Facet's data has an independent lifecycle from the entity's core kind lifecycle (`entity-facets` spec) even though `Endpoint`/`ServiceEndpointUsage` are not literally Facets (a Facet is one `OneToOne`-per-entity record; endpoints are many rows per API).
- Keep `consumesAPI` semantics intact: linking a Service to an Endpoint auto-creates `consumesAPI` on that Service (design-spec §10.3 Variant A) through a boundary-respecting cross-plugin write, without either plugin importing the other's ORM models.
- Ship an Endpoint documentation UI (Overview/Request/Response tabs) and a Linked Services management UI (search/filter/sort/link/unlink) plus a compact, read-only consumers graph on Overview, built on React Flow.
- Preserve endpoint-dependency history: removing an `Endpoint` never silently destroys the `ServiceEndpointUsage` links recording who depended on it.

**Non-Goals (deferred to a later change):**
- OpenAPI import/sync (design-spec §68, §102) — the data model is kept compatible (`method + path` identity, own UUID) but no importer ships here.
- A full-screen, multi-focus graph explorer (design-spec §57-59) — only the compact Overview graph ships; its data shape (`GET /api/endpoints/{id}/consumers`) is kept forward-compatible with a future explorer.
- Impact-analysis reports, "unused endpoints" / "most-consumed endpoints" views, runtime-discovered dependencies (design-spec §102-103).
- Path-parameter normalization (design-spec §71) — endpoint identity is exact `method + path` for this change.

## Decisions

### 1. `Endpoint` is plugin-owned child data, not a registered Entity Kind
**Decision:** `ApiEndpoint` is a plain Django model in `atlas_plugin_apis.models`, FK'd to `ApiDetails.entity` (i.e. to the API's `CatalogEntity`), with no `kind_id`, no `EntityKindHandler`, and no top-level `/catalog/entities/...` route. It's addressed only via nested routes: `/apis/:apiId/endpoints/:endpointId` (frontend) and `/api/apis/{apiId}/endpoints/{endpointId}` (backend).

**Why:** An endpoint has no independent owner/team/tags/visibility of its own in the source spec — it inherits all of that from its API (design-spec §19: "Owner", "Domain", "Visibility" on the Endpoint Overview card are the *API's* owner/domain, not the endpoint's own). Making it a full Entity Kind would mean giving it a kind handler, permissions, capabilities, and a place in the generic entity list/search UI it doesn't need, for data that is 1:1 structurally with "child rows of an API" — much closer to how `database-schema-plugin`'s parsed `tables`/`relations` are plugin-owned structured data under a Resource, not their own kind. Design-spec §11 independently arrives at the same nested-route conclusion ("Не рекомендуется использовать raw path... /apis/user-api/GET/...", i.e. give it its own id but route it under its API).

**Alternative considered:** Register `endpoint` as a full Entity Kind (child kind, `partOf` its API via the generic `system`-style relation). Rejected: it would pull Endpoint into the generic entity list, capabilities, and permission model for no product benefit, and would require the generic `entity-relations` system to model "belongsTo API" as a derived relation, which is unnecessary machinery when the FK already does that job directly and exclusively within one plugin.

### 2. `ServiceEndpointUsage` is a bespoke, plugin-owned link — not routed through core `entity-relations`
**Decision:** `ServiceEndpointUsage` (FK to `ApiEndpoint`, FK to the consuming Service's `CatalogEntity`, `created_at`, `created_by`, `unique_together(endpoint, service)`) lives in `atlas_plugin_apis`, with its own REST surface:
- `POST /api/endpoints/{endpointId}/services` — body `{"serviceId": "..."}`, response includes `apiRelationCreated: bool` (design-spec §65)
- `DELETE /api/endpoints/{endpointId}/services/{serviceId}` — `204` (design-spec §66)
- `GET /api/endpoints/{endpointId}/services` — paginated, `search`/`team_id`/`sort`/`order`/`page`/`page_size` (design-spec §63-64)
- `GET /api/endpoints/{endpointId}/consumers` — the compact graph-data contract (design-spec §60), a subset/reshaping of the same underlying rows

**Why:** `entity-relations`'s "derived, not authored" rule governs the *generic* CatalogEntity-to-CatalogEntity relations table (`GET /api/{kind}/{id}/relations/`), which exists so any two entity kinds can declare a typed edge through a spec reference field uniformly. `ServiceEndpointUsage` is not that: it's a plugin-specific join with its own query shape (search/filter/sort/paginate, a dedicated consumers-graph projection) that the generic relations endpoint doesn't support and shouldn't be extended to support for one plugin's benefit. This is the same reasoning `entity-facets` uses to justify a Facet's independent lifecycle/endpoint ("uses an endpoint owned by the Facet's providing plugin" rather than the entity's core lifecycle transaction) — `ServiceEndpointUsage` follows that precedent even though it isn't literally a `OneToOne` Facet.

**Alternative considered:** Add `endpoint_id` as another spec-style reference field on `ComponentDetails` (e.g. `consumes_endpoints: list[ref]`) and let core `entity-relations` derive `consumesEndpoint`/`endpointConsumedBy` the normal way. Rejected: this would require `Endpoint` to be a full Entity Kind (Decision 1's alternative, already rejected) since the generic relations system only targets registered kinds by `targetKind`/`targetId`; it would also put a fast-changing, high-cardinality reference list (up to hundreds of endpoints across the whole catalog) directly in a Component's spec payload, making every Component read/write carry that list even when nobody asks for it — the source spec's own §39 anticipates "desятки/сотни" consumers per endpoint, i.e. this is exactly the shape a join table with its own paginated query API is for.

### 3. Auto-`consumesAPI` goes through a narrow extension-point function, not a spec-PATCH round-trip
**Decision:** When `POST /api/endpoints/{endpointId}/services` links a Service that doesn't yet have `consumesAPI` on the endpoint's API, `atlas_plugin_apis` calls a narrow extension-point function on the standard-catalog side — `add_consumed_api(component_entity, api_entity)`, registered/exposed from a new or extended `atlas_plugin_standard_catalog.extension_points` module — which performs `component.component_details.consumes_apis.add(api_entity)` (an idempotent M2M add) and then explicitly calls `atlas_plugin_api.relations.recompute_relations` for that Component. `atlas_plugin_apis` does not import `ComponentDetails`/`atlas_plugin_standard_catalog.models` directly, and does not go through the generic Component spec-PATCH endpoint.

**Why:** This is exactly the situation `atlas_plugin_apis.extension_points`'s own docstring already names and solves for the reverse direction: "these two ORM-backed plugin-to-plugin edges here can't be fixed by moving types into a contract package, since Django ORM querying needs the real model class... each gets a narrow function/registration surface instead" (see its `register_delete_guard`/`due_for_spec_refresh`). Writing `ComponentDetails.consumes_apis` is the same kind of ORM-backed edge, just in the opposite direction, so it gets the same treatment. It's also the safer of the two options: a Django M2M `.add()` is one atomic, idempotent DB write, whereas going through the generic spec-PATCH endpoint would require reading the Component's current `consumesApis`, appending the new ref, and writing the full list back — a read-modify-write sequence that races if two endpoint links for the same Service land concurrently (the second write can silently drop the first's append). The one thing this approach must do that a spec-PATCH would give for free is call `recompute_relations` explicitly, since it bypasses the kind handler's normal `update_details` flow that would otherwise trigger it — `add_consumed_api` does this as part of its own contract, not left to callers.

**Alternative considered:** Routing through the generic Component spec-PATCH endpoint using `atlas_plugin_standard_catalog.contracts.ComponentSpecPatch`. Rejected for the race-condition and precedent-mismatch reasons above.

Unlinking (`DELETE .../services/{serviceId}`) never removes `consumesAPI` (design-spec §45, kept as-is: the Service may consume other endpoints of the same API, or the `consumesAPI` may have been set by hand).

### 4. Endpoint identity and uniqueness
**Decision:** `ApiEndpoint.id` is its own UUID (never derived from `method`/`path`, design-spec §69). Business identity is `unique_together(api, method, path)` (exact path string, design-spec §70-71 — no automatic `{id}` vs `{userId}` normalization for this change). Frontend routes by `id`, not by method+path, avoiding URL-encoding issues design-spec §11 calls out.

### 5. Graph: React Flow, per explicit product direction — not `@gravity-ui/graph`
**Decision:** The "Services using this endpoint" compact graph (design-spec §46-58) is built on React Flow, matching the source design spec's original choice (design-spec §7, §43-59). Custom node components are registered via React Flow's `nodeTypes` map (`ServiceNode`, `EndpointNode`, design-spec §49-51), and the read-only/non-editable requirement (design-spec §52) is enforced via `nodesDraggable={false}`, `nodesConnectable={false}`, `elementsSelectable={true}` on the `<ReactFlow>` instance, with pan/zoom/fitView left enabled (React Flow's defaults, driven through its `Controls` component).

This reverses an earlier version of this design, which recommended `@gravity-ui/graph` (already used by `core/frontend/src/components/FlowGraph.tsx` for the Flow-editor feature) for internal consistency, since this codebase has no other React Flow usage. That recommendation was explicitly overridden by product direction in favor of React Flow — see Risks below for the tradeoff this accepts.

**Package name caveat:** do not assume a specific npm package name/version here — React Flow's ecosystem renamed its canonical package from `reactflow` to `@xyflow/react` at some point after v11; confirm the currently-correct package name and a concrete version during implementation (task 6.1) rather than treating either name as settled by this document.

**Layout:** unaffected by the library choice. This graph's shape is always the same (one endpoint center, an N-service ring, design-spec §48's radial/star layout) and bounded to ≤12 nodes on the compact Overview view (design-spec §57: beyond 12, show 12 + "N more" and push users to a future full explorer) — a fixed radial-position formula (angle = `2π * i / n`, fixed radius), computed once and passed as each node's `position`, is simpler and cheaper than any layout-engine pass for this specific bounded shape. No layout library (React Flow doesn't ship one; `elkjs` is not needed here) is added for this change. Reassess if a future full-screen explorer (Non-Goal) needs general-graph layout.

**Dependency impact:** `plugins/apis/frontend/package.json` currently depends on `@gravity-ui/icons` and `@gravity-ui/uikit` only; this change adds React Flow (exact package name per the caveat above) as a genuinely new dependency for this codebase.

### 6. Frontend structure follows existing plugin conventions, not the source spec's layout
**Decision:** New frontend code lives under `plugins/apis/frontend/src/{pages,components,entityDetailTabs}`, following the existing `ApiDetailPage.tsx` / `entityDetailTabs/api.tsx` / `routes.ts` / `navItems.ts` pattern, not the source spec's suggested `features/api-endpoints/{components,graph,hooks,api,model,pages}` tree (design-spec §85) — that tree belongs to a feature-folder frontend architecture this repo doesn't use. Cross-plugin-reusable pieces (`EntityFormShell`, `RefSelect`/`MultiRefSelect`, shared `lib/entities`/`lib/types`) are imported from `frontend/...` the same way `plugins/standard-catalog/frontend` already does.

### 7. Endpoints are read-only in this change; removal is soft, never destructive
**Decision:** No self-service create/edit UI ships for `ApiEndpoint` in this change, and no `endpoint.edit` permission is surfaced through any API. Endpoint documentation is entered administratively — Django admin or fixtures/seed data — for this change; a future change (Non-Goal: OpenAPI import) is the natural path to self-service authoring. `ApiEndpoint` gains a `status` field (`active` | `removed`, default `active`). Removing an endpoint — whether via a future admin action or a future importer noticing it disappeared from a spec — sets `status='removed'` rather than deleting the row, and `ServiceEndpointUsage` rows pointing at it are never cascade-deleted. The Django admin for `ApiEndpoint` exposes a "Mark as removed" action instead of allowing hard delete.

Consequences for the rest of the design:
- `GET /api/apis/{apiId}/endpoints` defaults to `status=active`; a `status=removed` (or `include_removed=true`) query param surfaces removed endpoints separately, and the frontend Endpoints list on the API page gets a "Removed endpoints" section/filter rather than mixing them into the default list.
- The Link Service action is not offered on a `removed` endpoint's page.
- Any view showing a `removed` endpoint's existing `ServiceEndpointUsage` links (its own page, its Linked Services tab) displays a visible warning, e.g. "This endpoint was removed from the API — N services still declare a dependency on it," rather than looking identical to an active endpoint.
- Because there's no create/edit API, `POST`/`PATCH`/`DELETE /api/apis/{apiId}/endpoints/...` are dropped from this change's backend surface; only `GET` (list, detail) ships. `endpoint.read` remains as the permission gating those reads; `endpoint.edit` is deferred to whichever future change adds self-service or import-driven authoring.

**Why:** This change's central product value is impact analysis — "what breaks if this endpoint is removed" (design-spec §95). A hard delete that cascades away the very `ServiceEndpointUsage` rows recording who depends on the endpoint would destroy that evidence at exactly the moment it matters most. Scoping authoring to admin-only for v1 avoids building a full CRUD/versioning UI for data this change doesn't yet have a real authoring workflow for (that's what OpenAPI import, a Non-Goal, is for), while still letting the soft-delete invariant exist in the data model now, since deletion can happen (via admin) even without a self-service UI.

**Alternative considered:** Hard `DELETE`, relying on `ServiceEndpointUsage.endpoint` being `on_delete=PROTECT` to block deleting an endpoint that still has links. Rejected: it makes removal an all-or-nothing operation (can't record "this endpoint is gone" until every consumer has been manually unlinked first), which is backwards from what impact analysis needs — the tool should be able to show "removed, but N services still expect it," not force that information to be discarded before the removal can even be recorded.

### 9. Permissions
New permission strings, registered by `atlas.apis` the same way its existing `api.read`/`api.edit` are: `endpoint.read` (gates the two `GET` endpoint views), `endpointDependency.read`, `endpointDependency.create`, `endpointDependency.delete` (link/unlink). `endpoint.edit` is not introduced by this change (Decision 7: no self-service endpoint authoring in v1). Users without the relevant `*.create`/`.delete` permission don't see Link/Unlink actions at all (design-spec §81: hide, don't disable-with-tooltip).

**Evaluator gap found during implementation (task 3.5):** the shared `RBACPolicyEvaluator` (`server.apps.catalog.authorization`) special-cased only `.edit` (ownership-based) and `.read` (any authenticated principal) permission suffixes before this change — a permission ending in `.create`/`.delete` fell through to `return False` for every non-superuser, which would have made Link/Unlink silently superuser-only despite this document's stated intent that any user holding `endpointDependency.create`/`.delete` (not just superusers) can act. Resolved by extending `RBACPolicyEvaluator.check` so `.create`/`.delete` share `.read`'s unrestricted-if-authenticated rule, since (like `endpoint.read`) `ServiceEndpointUsage` has no owner of its own to check membership against (Decision 1/2) — confirmed with the user rather than assumed. A future permission needing ownership-scoped create/delete would need its own evaluator branch, not this one.

## Risks / Trade-offs

- **[Risk]** A Service can accumulate many endpoint links whose auto-created `consumesAPI` becomes stale/misleading once unlink stops removing it (design-spec §45's own tradeoff). → **Mitigation:** this is an explicit, documented product decision (not an oversight) because a Service may still consume other endpoints of the API or have a hand-authored `consumesAPI`; a future "source: manual | endpoint-derived" tag on `consumesAPI` (design-spec §83) is the natural follow-up if this proves confusing, deferred as a Non-Goal here.
- **[Risk]** The auto-`consumesAPI` write is a second, cross-plugin side effect inside what's otherwise a single-plugin (`atlas_plugin_apis`) transaction. → **Mitigation:** wrap the `ServiceEndpointUsage` create and the `add_consumed_api` M2M write in one DB transaction; if that write fails, the link is not created, and the API response surfaces the failure rather than leaving a link with no corresponding `consumesAPI`.
- **[Risk]** Introducing React Flow means this codebase now has two functionally-overlapping node/edge graph libraries (`@gravity-ui/graph` for the Flow editor, React Flow for this feature), which is a real inconsistency a future reader may be tempted to "fix" by rewriting one to match the other. → **Mitigation:** this is a deliberate, explicitly-decided tradeoff (product direction), not an oversight — this document records that decision plainly so it isn't silently reverted; if a later change wants to consolidate on one graph library, it should treat that as its own proposal rather than a side effect of unrelated work.
- **[Risk]** React Flow's exact current package name/version isn't pinned by this document (see Decision 5's package-name caveat) — implementation could pick a deprecated or mismatched package. → **Mitigation:** task 6.1 requires confirming the current canonical package before adding the dependency, not assuming `reactflow` or `@xyflow/react` from memory.
- **[Risk]** `atlas.apis` already depends on `atlas.standard-catalog`; this change tightens that coupling further (a live cross-plugin write, not just a read-time reference field). If a future distribution wants `atlas.apis` without `atlas.standard-catalog`, endpoint linking would need a no-op fallback. → **Mitigation:** none needed now — `atlas.apis` already hard-requires `atlas.standard-catalog` (`requires_plugins`), so this doesn't introduce a new optionality gap; note it for anyone later reconsidering that dependency's optionality (out of this change's scope).
- **[Risk]** A `removed` endpoint that still has active `ServiceEndpointUsage` links could be missed if the warning state (Decision 7) isn't consistently applied everywhere those links surface. → **Mitigation:** `specs/api-endpoints/spec.md` and `specs/endpoint-service-dependencies/spec.md` both carry explicit scenarios for this; tasks.md's test group covers it.

## Migration Plan

- New Django migrations in `atlas_plugin_apis` for `ApiEndpoint` and `ServiceEndpointUsage` — purely additive (`CREATE TABLE`), no changes to existing `ApiDetails`/`ComponentDetails` tables or migrations.
- No data backfill: endpoints and links start empty; existing `consumesAPI` relations are untouched.
- Rollback: reverse the two migrations (drop the new tables); no existing behavior depends on their presence, so rollback is safe at any point before endpoint data is created in a live environment (after that, rollback is a data-loss operation like any other, same as every other plugin's migrations in this codebase).
