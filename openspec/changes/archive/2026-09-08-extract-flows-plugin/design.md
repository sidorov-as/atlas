## Context

Flow (`add-flows`, archived 2026-08-25) was built as a plain model inside `server.apps.catalog` before the plugin-contract-surface machinery existed — `add-flows` design.md Decision 1 chose that location purely because Flow "needs `System` and `refs.py` from `catalog` regardless" and a dedicated Django app would have been ceremony for one model, not because Flow was judged unsuitable for plugin-hood. Three days later, `introduce-frontend-extension-points` (2026-09-01) named Flows explicitly, alongside System/Component/Resource/API/C4, as a module a later change would split out of the in-tree "core" frontend plugin. The four changes that followed (`extract-standard-catalog-plugin`, `extract-apis-plugin`, `extract-c4-plugin`, `extract-ingestion-plugin`) did that for everything except Flow — `frontend/src/plugins/core/routes.ts` still carries the comment "Flows hasn't been extracted yet." This change closes that gap.

The concrete reason to do it now: a wanted follow-up feature adds "Query" (`atlas_plugin_apis`'s `ApiEndpoint`) and "Event" (`ApiOperation`) as new, live-referenceable Flow step kinds. Both are deliberately *not* registered Entity Kinds (`api-endpoints`/`api-operations` specs: "SHALL NOT be a registered Entity Kind") — they're plugin-owned child rows of an `api` `CatalogEntity`, addressed by UUID, reachable only through `atlas_plugin_apis`. Reaching them from Flow's save-time validation requires calling into `atlas_plugin_apis` through its published `.extension_points` module — the same inversion-of-control shape `atlas_plugin_ingestion` already uses (`atlas_plugin_apis.extension_points.due_for_spec_refresh()`) and `atlas_plugin_standard_catalog` already uses in the opposite direction (registers a delete-guard into `atlas_plugin_apis.extension_points`). `server.apps.catalog` (core) cannot do this: the enforced import-boundary check (`core/backend/server/apps/plugins/tests/test_import_boundaries.py`) only allows a plugin to import `atlas_plugin_api` and another plugin's declared `.contracts`/`.extension_points` — core code reaching into a plugin's internals at all isn't a case the boundary check, or `core-plugin-contract-surface`'s one-directional contract (core publishes *to* plugins, not the reverse), was built to support. Moving Flow into a plugin turns "core reaches into an optional plugin" (unsupported) into "plugin reaches into another plugin's declared contract surface" (built, tested, exercised twice already).

This change is scoped to the extraction only. It does not touch `atlas_plugin_apis`, does not add Query/Event step kinds, and does not design the resolver those will need — it only gets Flow onto the footing that follow-up requires.

## Goals / Non-Goals

**Goals:**
- `server.apps.catalog` and `frontend/src/plugins/core/` contain zero Flow-specific code after this change.
- Flow is built and selected as an independently identifiable, **optional** plugin (own `PluginDescriptor`, own frontend package boundary), matching `atlas.apis`/`atlas.c4`'s cardinality, not `atlas.standard-catalog`'s required one.
- Every `flow-management` and `visual-flow-editor` scenario passes unmodified — REST routes, response shapes, validation rules, canvas rendering, and the ownership-based write rule are all behavior-preserving.

**Non-Goals:**
- Adding "Query"/"Event" step kinds, any reference to `atlas_plugin_apis`, or any new `atlas_plugin_apis.extension_points` entry — tracked as a separate follow-up change once this extraction lands.
- Publishing `atlas-plugin-flows`/`@atlas/plugin-flows` to a real registry — workspace/path dependencies are enough, matching every prior extraction.
- Renaming `server.apps.catalog`'s Django app label, or otherwise cleaning up whatever remains in `apps.catalog` after Flow leaves — `extract-standard-catalog-plugin` design.md already deferred that question ("revisit once APIs/C4/Ingestion are also extracted"); Flow leaving doesn't resolve it either, since `Relation`/`EntityService`/both registries/generic API infra still live there.
- Changing Flow's strict-tree/entity-ref-resolution validation rules, or its JSON step grammar — `validate_steps()` moves verbatim.

## Decisions

**Flow's write-permission check moves to a registered `atlas.flows.flow.edit` permission checked against `instance.system`, not a new `.create`/`.delete` pair.** Flow's views today call `EntityWritePermission.check_create`/`check_write` — core-internal, unpublished, ownership-scoped (member of the target System's owner Group) for create, update, *and* delete alike. The published equivalent, `atlas_plugin_api.get_policy_evaluator().check(principal, permission, resource)`, is backed by `RBACPolicyEvaluator`, whose own docstring is explicit that ownership-scoping only applies to permissions ending in `.edit`; anything ending in `.read`/`.create`/`.delete` is unrestricted-if-authenticated *by design* (this is why `atlas_plugin_apis`'s `ServiceEndpointUsage`/`ServiceOperationUsage` create/delete permissions are unrestricted-if-authenticated — those resources genuinely have no owner to check). Flow's create/update/delete all resolve an existing `system` first, so a resource is always available at check time, unlike a brand-new top-level entity choosing its owner for the first time. Registering one `atlas.flows.flow.edit` permission and calling `check(principal, 'atlas.flows.flow.edit', instance.system)` from all three write paths reuses `RBACPolicyEvaluator`'s existing, kind-agnostic `.edit` branch exactly as built, preserving today's exact rule with **zero changes to core's evaluator**. `atlas.flows.flow.read` is registered too, unrestricted-if-authenticated like every other `.read` permission, matching list/retrieve's current `SessionAuth`-only gate.
Rejected: extending `RBACPolicyEvaluator` to ownership-scope `.create`/`.delete` generically — would risk silently tightening `atlas_plugin_apis`'s intentionally-unrestricted `ServiceEndpointUsage`/`ServiceOperationUsage` create/delete checks, for a need Flow alone doesn't force since the `.edit`-branch reuse above already covers it exactly.

**Migration keeps `Flow`'s DB table intact via an app-label-preserving move**, the same technique `ApiDetails` used (`extract-apis-plugin`): the Python model class moves to `atlas_plugin_flows.models`, but `class Meta: app_label = 'catalog'` is added explicitly (today it's implicit, inherited from living inside the `catalog` app) so the underlying table name and existing migration history are untouched — no data migration, no backfill.
Rejected: relabeling the table to `atlas_plugin_flows_flow` — a real data migration for zero behavioral benefit, and inconsistent with every prior extraction's precedent.

**`atlas.flows` is optional, not required**, matching `atlas.apis`/`atlas.c4`/`atlas.ingestion` rather than `atlas.standard-catalog`. Nothing else in the catalog references *into* a Flow (Decision 3 of `add-flows`: "nothing needs to reference a Flow, only the reverse") the way `Component.providesApis` structurally depends on the `api` kind existing, so omitting `atlas.flows` from a distribution degrades cleanly — Flow's UI/routes simply aren't present.
Rejected: required, by analogy with `atlas.standard-catalog` — rejected because nothing structurally depends on Flow existing, unlike Standard Catalog's System/Component/Resource which every other plugin's ownership model assumes.

**`atlas.flows` declares a manifest dependency on `atlas.standard-catalog` (`>=0.1 <1`).** Flow's `system` field resolves a System entity (`refs.resolve_ref(body.system, expected_kind=KIND_SYSTEM)`) — the exact same shape as `atlas.apis`'s own dependency on Standard Catalog for its `system`/owner references. `KIND_SYSTEM` itself is published centrally in `atlas_plugin_api` (not Standard-Catalog-owned), so this dependency is about there being real System entities to reference at runtime, not an import-time need.

**Flow's frontend moves as one unit — pages, canvas components, `lib/flow*` utilities, and its `routes`/`navItems` contributions — mirroring `@atlas/plugin-apis`'s `index.ts` shape** (`defineFrontendPlugin({ id: 'atlas.flows', contributions: [...flowsRoutes, ...flowsNavItems] })`). No entity-detail tab contribution: Flow isn't a `CatalogEntity` and has no detail-tab presence on another entity's page today. This extraction is also what dissolves the "closed core enum, no extension point" framing raised earlier for the Query/Event follow-up — once `flowNodeKind.ts`'s `FlowNodeKind` enum lives inside `@atlas/plugin-flows`, adding two more variants there is the plugin editing its own internal code, not one plugin injecting into another's closed surface; `frontend-plugin-contributions`'s four contribution kinds (route/nav item/entity-detail tab/home widget) are never implicated.

## Risks / Trade-offs

- **[Permission semantics subtly change if the `.edit`-reuse mapping (Decision 1) is implemented against the wrong resource]** Checking against anything other than `instance.system` (e.g. accidentally checking against the Flow's own non-existent "owner") would either always-deny or always-allow → **Mitigation**: existing `flow-management`/`catalog-auth`-adjacent test coverage for create/update/delete-as-non-member and as-member must be ported and pass unmodified against the new permission before this change is considered done.
- **[App-label-preserving move is a well-worn but still manual technique]** A mistake in `Meta.app_label`/migration state leaves the table orphaned or duplicated → **Mitigation**: verify with both a fresh-database migrate and a migrate-from-the-previous-state (existing DB) succeeding, matching `extract-standard-catalog-plugin`'s own verification step.
- **[Nothing yet exercises "optional plugin whose absence removes user-visible pages" for Flow specifically]** Unlike `atlas.apis` (absence only empties a few reference fields), removing `atlas.flows` removes entire pages/nav entries → **Mitigation**: this shape is already proven by `atlas.c4` (diagram viewer pages/nav disappear when absent); no new mechanism needed, just confirm Flow's nav item and routes are genuinely optional-safe (no other core page assumes `/flows` exists).
- **[Scope creep toward the Query/Event follow-up while already touching this code]** Easy to "just also" wire up `atlas_plugin_apis` while the files are open → **Mitigation**: explicit Non-Goal above; the follow-up is a separate proposal with its own design (the `atlas_plugin_apis.extension_points` resolver shape).

## Migration Plan

1. Scaffold `plugins/flows/backend/` (`atlas_plugin_flows`, `pyproject.toml`, `apps.py`, `plugin.py` with `PluginDescriptor` + `requires_plugins={'atlas.standard-catalog': '>=0.1 <1'}`) and `plugins/flows/frontend/` (`@atlas/plugin-flows`, `package.json`), contributing nothing yet.
2. Move `Flow`/`validate_steps()`/`StepValidationError` (`server/apps/catalog/models/flow.py`) into `atlas_plugin_flows.models`, adding the explicit `Meta.app_label = 'catalog'` (app-label-preserving move); move `FlowAdmin` (`admin.py`).
3. Move Flow's schemas (`FlowIn`/`FlowPatch`/`FlowOut`/`FlowListFilters`/`FlowPath` in `api/schemas.py`) and controllers (`FlowListController`/`FlowDetailController`, `api/views.py`) into `atlas_plugin_flows.api`; register their URLs from the plugin instead of `server/apps/catalog/api/urls.py`.
4. Register `atlas.flows.flow.read`/`atlas.flows.flow.edit` via `register_permission()` in `atlas_plugin_flows.plugin.register_runtime()`; replace the `EntityWritePermission.check_create`/`check_write` call sites with `get_policy_evaluator().check(...)` per Decision 1.
5. Move Flow's frontend files (pages, canvas components, `lib/flow*.ts`) into `@atlas/plugin-flows/src`; move their route/nav-item contributions out of `frontend/src/plugins/core/{routes,navItems}.ts` into the new package's own `routes.ts`/`navItems.ts`; wire up `defineFrontendPlugin`.
6. Delete the moved code from `server.apps.catalog`/`frontend/src/plugins/core/`; confirm nothing there still imports Flow.
7. Add `atlas_plugin_flows.plugin` to `SELECTED_PLUGINS` (`core/backend/server/settings/selected_plugins.py`) and the distribution manifest/lock source, as optional (absent from `REQUIRED_PLUGINS`).
8. Verify: full `flow-management`/`visual-flow-editor` spec-scenario suite passes unmodified; a fresh-DB migrate and an existing-DB migrate both succeed; composing a distribution without `atlas.flows` succeeds with no `/flows` route/nav entry present.

Rollback: steps 2-5 are independently revertible (each is a code-location move, no destructive DB step); step 6's deletion should only happen once steps 2-5 are confirmed working end-to-end.

## Open Questions

- Should the Flow REST routes move from `/api/flows/...` to a plugin-namespaced path, or stay exactly where they are (matching how `atlas_plugin_apis`/`atlas_plugin_standard_catalog` kept their existing paths on extraction)? Default to keeping today's paths unchanged, consistent with every prior extraction's "no REST route... changes" claim — flag only if the URL-routing mechanism plugins use turns out to require a path prefix.
- Exact `plugins/flows/backend/pyproject.toml`/`plugins/flows/frontend/package.json` dependency pins — mechanical, resolved during implementation from the `atlas_plugin_apis`/`@atlas/plugin-apis` precedent, not a design blocker.
