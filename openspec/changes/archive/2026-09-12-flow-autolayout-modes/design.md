## Context

Today a step's `position` (`flow-management`'s "Flow diagram layout direction and manual node positioning" requirement) is optional and per-step: if present it always wins over autolayout, if absent the step is placed by ELK on every render. `handleNodeDragStop` (`FlowCanvasEditor.tsx`) writes `position` to exactly the one step being dragged — so a single drag, anywhere in a Flow's lifetime, permanently splits that Flow into a per-step mix of "still ELK-live" and "frozen since that drag," and there is no way back to "fully live" short of the explicit, destructive "Auto layout" control overwriting every step at once. This mixed state is not a rare edge case: it's the default state of any Flow that has ever had a single node nudged by hand, which — per the exploration this design is based on — is most Flows past their first edit.

`flow-allow-reconvergence` made this mixed state load-bearing in a way it wasn't before: with reconvergence allowed, `alignSiblingColumns`'s sibling-shift could land a moved subtree on top of a frozen reconvergence target (fixed, with a collision guard, as part of that change). A second bug from the same root cause remains open: the canvas only takes `x`/`y` out of ELK's layout result and throws away ELK's own obstacle-aware edge routing (`bendPoints`), drawing edges with a generic `getSmoothStepPath` instead — so a reconverging edge that has to "jump" a column can visually cut straight through an unrelated node sitting in between. Naively trusting `bendPoints` doesn't work today because they're only valid for a graph ELK laid out *in full* — exactly what the mixed state prevents from ever being reliably true past a Flow's first edit.

Three narrower fixes were explored and set aside before landing on this design: rendering edges via `bendPoints` only when both endpoints happen to be currently "fresh" (rejected — that condition holds too rarely once a mixed state is the norm, per above); ELK's own interactive-layout affordances (`org.eclipse.elk.interactiveLayout`, `org.eclipse.elk.position`, `...semiInteractive` — confirmed present in the bundled `elkjs` build) to feed frozen positions in as constraints and let one `elk.layout()` call route around them (deferred — plausible, but unverified on this Flow shape, and doesn't remove the underlying two-tier-state complexity, just relocates it into ELK's own option surface); and a hand-rolled, purely local obstacle-avoidance patch for the specific edge-through-node case (rejected — solves only the rendering symptom, leaves the collision-guard-generating root cause in place for the next thing that touches sibling alignment).

For comparison, two other tools were checked during exploration: this repo's own ER-diagram editor (`erDiagramLayout.ts`) never persists position at all — "Auto layout" fully overwrites, drag is session-only, so it never accumulates a mixed state to begin with. EventCatalog's flow editor (external, inspected live) has no layout engine whatsoever — a fixed-grid, deterministic offset per add/branch action, and no cross-lane reconvergence to route around. Neither tool tries to make "some nodes frozen, others engine-managed" work at the same time; this design follows that precedent by making the split a whole-Flow, persisted, binary choice instead of a per-step accumulation.

## Goals / Non-Goals

**Goals:**
- Replace the per-step "`position` present → frozen" mixed model with one persisted, Flow-level `autolayout_enabled` flag: the whole graph is either always ELK-fresh, or ELK never runs against it.
- Make `layout_direction` a persisted Flow field instead of a per-viewer `localStorage` preference, so a shared, continuously-recomputed layout doesn't depend on which viewer's browser last touched it.
- Preserve today's "recompute everything on demand" affordance (today's "Auto layout" button) as a one-shot action available specifically in manual mode.
- Set up (not necessarily land, pending its own verification) the precondition for trusting ELK's `bendPoints` for edge rendering: a graph that is *always* fully fresh whenever autolayout is on.

**Non-Goals:**
- Actually switching `FlowEdges.tsx` to render via `bendPoints` is scoped as a follow-up task gated on a verification spike (see Risks), not committed to as part of this design sight-unseen.
- No UI for changing `layout_direction` after creation ships as part of this change — the field is persisted with a fixed default (`LAYOUT_LEFT_RIGHT`) so it doesn't need a later data migration, but exposing a picker is deferred.
- No backfill/migration tooling for existing Flow rows — see Migration Plan.
- No change to entity-ref validation, cycle detection, or any other `validate_steps`/`validateFlowSteps` rule — this change is scoped to positioning/layout only.

## Decisions

### Decision 1: `autolayout_enabled` is a persisted, Flow-level boolean — not a per-step or local concept
The per-step "has `position`?" check in `mergeStepPositions` is removed as the thing that decides freshness. Instead, one new `Flow.autolayout_enabled` field (default `true`) governs the whole Flow: when `true`, every step's `position` is ELK-computed and persisted on every `steps[]` mutation (see Decision 3); when `false`, `position` is exactly what dragging or deterministic placement last set it to, and nothing else touches it. This directly targets the root cause identified above — a per-step accumulation of frozen/fresh state — rather than adding a fourth patch on top of it.

**Alternatives considered**: keeping the per-step model and making edge rendering freshness-aware (deferred — see proposal.md); ELK's own interactive/incremental layout mode to blend frozen and free nodes inside one layout call (deferred — real option in the library, but unverified here, and trades one kind of complexity for another rather than removing it — worth revisiting later if the binary model proves too coarse in practice).

### Decision 2: `layout_direction` moves from `localStorage` (`flowDiagramPreferences.ts`) to a persisted `Flow` field
Once autolayout-on means "recompute and persist on every mutation," direction stops being a purely cosmetic, per-viewer choice: two editors with different local direction preferences opening the same live-autolayout Flow would otherwise fight over, and destructively rewrite, its shared layout on nothing more than which of them opened the editor last. `layout_direction` becomes a `Flow` field (default `LAYOUT_LEFT_RIGHT`), read by every viewer identically. `flowDiagramPreferences.ts`'s `localStorage`-backed preference is removed as a source of truth for this; if a purely cosmetic session preference is wanted for something else later, that's a separate, unrelated concern.

### Decision 3: Autolayout-on recomputes and persists on *every* `steps[]` mutation, not just explicit actions
Today, ELK only fully overwrites positions on an explicit "Auto layout" click or direction change; the passive per-render effect merges in stored positions instead of overwriting them. With `autolayout_enabled: true`, that passive effect stops merging — it recomputes the whole graph via ELK and writes every step's `position`, on mount and on every add/delete/edit, exactly as if "Auto layout" were silently re-invoked each time. This is what guarantees the graph is *always* 100% ELK-fresh while the flag is on (not just immediately after an explicit action), which is the precondition the edge-routing fix (Decision 1's stated Goal) depends on.

### Decision 4: Autolayout-off placement uses the existing deterministic helpers — no ELK involved
With `autolayout_enabled: false`, `computeFlowAutolayout` is never called. Dragging keeps working exactly as `handleNodeDragStop` does today. A newly added step's position comes from the already-existing, engine-free `nextConnectedPosition`/`resolveConnectedPosition` (connected add) and `nextRowPosition` (toolbar add) — both already collision-checked against other real steps' positions, so no new placement logic is needed, only routing the existing calls off of the flag instead of always running.

### Decision 5: The "Auto layout" control becomes a manual-mode-only, one-shot "tidy" action, distinct in name from the new setting
Reusing the label "Auto layout" for both the persisted setting and a button next to it invites reading them as the same control. The button is renamed (exact copy is an implementation/tasks concern, not a design one) and shown only while `autolayout_enabled` is `false` — while it's `true` the graph has nothing to tidy, since Decision 3 already keeps it fresh continuously. Activating the button runs the same underlying "ELK once, write every position" codepath as today's `handleAutoLayout`, but does not itself set `autolayout_enabled` to `true`.

### Decision 6: No migration; reseed instead
Every currently-persisted `Flow` row is seed/demo data (`seed_booking_demo.py`, extended by `flow-allow-reconvergence` to include reconverging examples). Rather than write a backfill for the two new fields' defaults, the plan is to re-run that seed command after this change ships. This is explicitly not a precedent for how a future change with real user data should handle the same kind of addition.

## Risks / Trade-offs

- **Loses the "nudge one node, keep the rest live" workflow.** Today's per-step model lets an author fix one awkwardly-placed node without giving up autolayout for the rest of the Flow. Under the binary model, touching any node while `autolayout_enabled` is `true`... doesn't apply — drags are simply overwritten again on the next mutation while the flag is on (Decision 3), so the only way to keep a manual tweak is to turn the flag off, which then stops the rest of the Flow from reflowing as new steps are added. This is a deliberate, explicit trade-off (confirmed in this change's originating discussion), not an oversight — flagging it here so it's visible to anyone reviewing this design later.
- **[Risk] Trusting `bendPoints` for edge rendering is unverified on real reconvergence shapes.** → **Mitigation**: scoped as a Non-Goal here; land Decisions 1-6 first (which are independently correct regardless of the edge-rendering outcome), then spike `bendPoints`-based rendering against the seeded reconverging demo Flows before committing to it as the edge renderer, with today's `getSmoothStepPath` kept as the fallback if it doesn't hold up.

  **Finding (tasks.md 6.1 spike)**: Ran `elk.layout()` directly (via `buildElkGraph`) against the three seeded reconverging demo Flows (`search-flow`, `cancellation-flow`, `notification-delivery-flow`) plus a plain control (`booking-flow`), and compared each edge's raw `bendPoints` (from ELK's own layout result, before `alignFlowPositions`) against the final, column-aligned node positions the canvas actually renders. For `search-flow` and `notification-delivery-flow`, `alignSiblingColumns` happens to produce a zero shift for every node — ELK's raw `bendPoints` already line up exactly with the rendered nodes, so `bendPoints`-based rendering would work unmodified for these two. For `cancellation-flow`, though, the reconvergence itself (`s6`'s short branch vs. `s2b→s3→s4`'s long branch, both feeding `s5`) is exactly the shape that triggers a real `alignSiblingColumns` shift: `s2b`/`s3`/`s4`/`s5` end up 240px further along the layout axis than ELK's raw output (`s6` — the short, unshifted branch — does not move). Every `bendPoints`-routed edge along the shifted branch (`s2→s2b`, `s2b→s3`, `s3→s4`, `s4→s5`) would render 240px short of the node it's supposed to connect to, and the reconverging edge `s6→s5` specifically has a raw `endPoint` that lands 240px away from `s5`'s actual rendered position, since its two endpoints have different alignment deltas (0 and 240) — no uniform translation fixes that.

  **Conclusion**: `bendPoints`-based rendering is not a drop-in replacement for `getSmoothStepPath`, even with the "always fresh" precondition satisfied by tasks 2-3. The blocker isn't staleness (ELK does run fresh on every mutation) — it's that `alignSiblingColumns`'s post-ELK column-alignment pass (itself needed to fix the sibling-alignment bug `flow-allow-reconvergence` already patched) moves nodes by a per-node, not flow-wide-uniform, delta, and ELK's `bendPoints` are computed before that pass runs. Adopting `bendPoints` as-is would visibly detach edges from their nodes on exactly the reconverging shapes this fix targets — worse than today's "cuts through a node" bug, not better. Recommendation: don't adopt `bendPoints` rendering now; keep `getSmoothStepPath`. The most promising follow-up, if revisited, is extending `alignSiblingColumns` to also translate each affected edge's `bendPoints` by its endpoints' deltas (nontrivial: a bend point isn't itself a node, so it isn't obviously "whose delta" to apply along the middle of a shifted edge) — verified against `cancellation-flow` specifically, since that's the shape that breaks today.
- **[Risk] Turning `autolayout_enabled` on is a destructive, overwrite-everything action.** → **Mitigation**: already covered by `FlowFormPage.tsx`'s existing save/cancel boundary — every canvas edit, including this one, is local component state until an explicit Save, and `Cancel` discards all of it uniformly. No new confirmation dialog is needed; this was confirmed against the actual code during this change's originating discussion, not assumed.
- **[Risk] Label collision between the persisted setting and the one-shot control.** → **Mitigation**: Decision 5's rename plus conditional visibility (see also Open Questions).

  **Finding (tasks.md 8.2 manual verification)**: `FlowGraph.tsx`'s read-only canvas (`FlowDetailPage.tsx`'s "Flow" tab) originally kept its pre-existing `mergeStepPositions(steps, false)` call unconditionally — i.e. always treating stored `position` as authoritative, never calling `computeFlowAutolayout`, on the theory that "while `autolayout_enabled`, the editor keeps every step's stored `position` ELK-fresh on every mutation, so it's already the position autolayout would compute." That's only true for a Flow that has actually been opened and saved in the editor since gaining the flag — the *editor's* passive effect only writes recomputed positions into local component state; persisting them to `steps[].position` still requires an explicit Save. A Flow seeded or migrated in with `autolayout_enabled: true` and no per-step `position` (every reseeded demo Flow, per Migration Plan) has nothing for the read-only view to fall back on, so every step defaulted to `{0, 0}` and rendered stacked on top of each other — reproduced against `search-flow` and `cancellation-flow` after re-running `seed_booking_demo`. Fixed by giving `FlowGraph`/`FlowGraphCanvas` the same `autolayoutEnabled`/`layoutDirection` props as the editor and mirroring its passive effect (minus the write-back, since a read-only view never persists): call `computeFlowAutolayout` itself whenever `autolayoutEnabled` is `true`, falling back to stored `position` only when it's `false`. `FlowDetailPage.tsx` now threads `flow.autolayoutEnabled`/`flow.layoutDirection` through.

## Migration Plan

No database migration. `autolayout_enabled` (default `true`) and `layout_direction` (default `LAYOUT_LEFT_RIGHT`) are added as ordinary model fields with defaults; every currently-persisted Flow is seed/demo data, so after this change ships, `seed_booking_demo.py` is re-run in the dev environment instead of backfilling existing rows. No rollback concern beyond the usual "revert the change" for a Flow's model fields.

## Open Questions

- Exact copy and placement for the renamed one-shot "tidy" control and for the `autolayout_enabled` setting's own UI surface (canvas toolbar vs. a Flow-level settings area) — left to tasks/implementation, not a design blocker.
- Whether a UI to change `layout_direction` after creation should ship later, and whether that reopens the "immediately recompute" behavior the current spec already describes for direction changes — out of scope here (Non-Goals), worth its own follow-up once the binary mode has shipped and been used.
- Whether ELK's interactive-layout option surface (Decision 1's alternative) is worth a second look if the binary model's "nudge one node" trade-off turns out to matter more in practice than expected.
- Whether dragging should be visually disabled on the canvas while `autolayout_enabled` is `true` (since Decision 3 means any drag is itself a `steps` change that immediately gets recomputed away — see specs delta's "a drag has no lasting effect" scenario), versus leaving the drag gesture available and letting the node visibly snap back on the next recompute. Left to tasks/implementation; either is consistent with this design.
