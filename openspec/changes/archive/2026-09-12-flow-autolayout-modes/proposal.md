## Why

`flow-allow-reconvergence` let two steps target the same next step, which exposed two layout bugs rooted in a deeper structural problem: a step's `position`, once dragged, is frozen forever while every other step keeps recomputing fresh on ELK — a permanent, per-step, uncoordinated mix of "still live" and "stuck." One bug from that mix (a sibling-alignment shift landing on a frozen reconvergence target) is already patched. The other — a reconverging edge visually cutting straight through an unrelated node, because the canvas discards ELK's own obstacle-aware edge routing and draws a generic straight-ish path instead — is not, and every fix explored that tries to keep the per-step mixed model (partial-freshness-aware edge routing, ELK's interactive-layout hints, a hand-rolled obstacle router) turned out to be either rarely applicable in practice or high-effort/high-risk for what it buys. Replacing the per-step mixed model with one explicit, Flow-level autolayout mode removes the mixed state the bug depends on, instead of patching around it a third time.

## What Changes

- Add a persisted, Flow-level `autolayout_enabled` boolean (default `true`) and a persisted `layout_direction` (default `LAYOUT_LEFT_RIGHT`), replacing today's per-step "`position` wins if present, else autolayout" merge and today's per-viewer, `localStorage`-only direction preference (`flowDiagramPreferences.ts`).
- **Autolayout ON**: every `steps[]` mutation (add, delete, edit — not just an explicit drag) recomputes the whole graph via ELK and persists the computed `position` for every step; there is no more per-step merge, so the rendered graph is always 100% ELK-fresh. Because it's always fully fresh, edge rendering can adopt ELK's own routing (`bendPoints`) unconditionally instead of today's plain `getSmoothStepPath`, which is expected to resolve the edge-through-node bug as a side effect rather than as a separate patch. This part needs a verification spike before being treated as settled — see design.md's Risks.
- **Autolayout OFF (manual)**: ELK never runs. Dragging a node continues to update just that node's `position`, unchanged. A newly added step is placed by the existing deterministic, engine-free helpers (`nextConnectedPosition`/`resolveConnectedPosition` for a connected add, `nextRowPosition` for a toolbar add) — no ELK involved, matching the same "no layout engine, just placement rules" pattern already used by comparable tools (this repo's own ER-diagram editor; EventCatalog's flow editor, external reference checked during exploration).
- Today's "Auto layout" control becomes a one-shot action available only while autolayout is off (there's nothing to tidy while it's on — the graph is already always fresh); activating it does not itself turn `autolayout_enabled` on. Its recompute-and-overwrite behavior is unchanged (still the same `handleAutoLayout` codepath) — only its availability and its relationship to the new persisted setting change.
- **BREAKING** (data model, additive): `Flow` gains two new persisted fields. No migration is needed — see Impact.

**Considered and deferred**: keeping today's per-step mixed model and instead making edge rendering "fresh-aware" (trust ELK's bendPoints only when both of an edge's endpoints currently have no dragged-and-frozen ancestor in the mix) was explored first. Deferred because a single manual drag anywhere in the flow permanently taints that node going forward, so the "both endpoints fresh" condition was judged to hold rarely enough in practice not to justify the two-tier rendering path it requires.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `flow-management`: the "Flow diagram layout direction and manual node positioning" requirement is replaced by an explicit two-mode model — a persisted `autolayout_enabled` flag governs whether the whole Flow's positions are continuously ELK-managed or fully manual, `layout_direction` becomes a persisted Flow field instead of a per-viewer preference, and the "Auto layout" control's scenario is updated to reflect that it only applies (and is only available) in manual mode.

## Impact

- Backend: `plugins/flows/backend/atlas_plugin_flows/models.py` (`Flow` model gains `autolayout_enabled`/`layout_direction` fields with defaults), exercised via `api/schemas.py`.
- Frontend: `plugins/flows/frontend/src/lib/flowLayout.ts` (`mergeStepPositions`, `computeFlowAutolayout`, edge construction in `buildElkGraph`/`buildFlowNodesAndEdges`), `plugins/flows/frontend/src/components/FlowCanvasEditor.tsx` (the passive layout effect, `handleNodeDragStop`, `handleAutoLayout`), `plugins/flows/frontend/src/components/FlowGraph.tsx` (the read-only diagram — also needed mode-aware resolution; see tasks.md 8.2's finding), `plugins/flows/frontend/src/components/FlowEdges.tsx` (edge path source, pending the bendPoints spike), `plugins/flows/frontend/src/lib/flowDiagramPreferences.ts` (direction preference removed as a local/`localStorage` concept), `plugins/flows/frontend/src/pages/FlowFormPage.tsx` (new fields wired into the save payload; existing `Cancel` already makes every canvas edit — including a mode flip — fully reversible pre-save, so no new confirmation UI is needed), `plugins/flows/frontend/src/pages/FlowDetailPage.tsx` (threads the Flow's `autolayoutEnabled`/`layoutDirection` down to `FlowGraph`).
- No database migration: every currently-persisted Flow is seed/demo data (`core/backend/server/apps/catalog/management/commands/seed_booking_demo.py`); the plan is to re-run that seed command after this ships rather than backfill the two new fields.
