## Context

The engine contract, the conformance suite, composition of exactly one engine, and the PostgreSQL adapter exist after the search core change. A second adapter is meant to prove that the seam is real. This one targets a dedicated, lightweight search server that supplies relevance ranking, typo tolerance and highlighting natively.

Constraints the adapter meets that the PostgreSQL one does not:
- It talks to a separate service over HTTP; writes are applied asynchronously and report completion through task status.
- Its document identifiers accept only a restricted character set, which the search document ids (`kind:key`) violate.
- Atomic replacement needs an index swap rather than a transaction.

At the distribution level, a composition currently describes backend packages, frontend packages and authentication runtime inputs generated by the composer. No plugin has needed a separate service, so the composer and lock have no representation for one. Plugin configuration is namespaced and secrets are resolved centrally.

The public demo deployment is a single container with the database inside it; it keeps the PostgreSQL adapter.

## Goals / Non-Goals

**Goals:**
- A second engine adapter that passes the same conformance suite and needs no change in the search plugin, sources or UI.
- A general, small way for any plugin to declare a required service, recorded in the lock and wired by generated inputs, with an escape hatch for an operator-supplied instance.
- Secrets handled as everywhere else in the system.

**Non-Goals:**
- Running this engine in the demo.
- Clusters, replicas, backups of the engine, or index migration between engines.
- Engine-specific UI features.
- A general service orchestration layer beyond declaring, locking and wiring one container or an external address.

## Decisions

### Decision 1: Adapter is a separate plugin selected instead of the default

A separate package registers the engine in its runtime hook and is mutually exclusive with other engines through the existing exactly-one rule.

Alternatives: a mode inside the PostgreSQL adapter (couples two engines and their dependencies); a runtime setting in the search plugin (breaks the "fork the adapter" story and the exactly-one validation).

### Decision 2: Encode document ids and keep the original in a field

The adapter derives a safe identifier from each document id with a reversible, collision-free encoding and stores the original id as a field it returns. Queries return the stored original.

Alternatives: hash the id (not reversible, so the original must still be stored and collisions are theoretically possible); change search document ids to a restricted character set (leaks one engine's rule into the contract and every source); a lookup table (extra state to keep consistent).

### Decision 3: Wait for engine tasks to finish and treat that as the acknowledgment

Every write waits for the engine's task to reach a terminal state within a configurable timeout; failure or timeout is reported as an engine error so pending changes remain.

Alternatives: fire-and-forget (the drain job would delete pending rows for writes that may fail, losing updates until the next rebuild); poll later in a separate job (more state, more moving parts).

### Decision 4: Replace by building a new index and swapping

Replace-all writes into a temporary index, waits, swaps it with the live one, then deletes the old one. The index settings (ranked searchable attributes, kind as a filterable attribute) are applied to the new index before the swap.

Alternatives: delete and refill in place (readers see an empty or partial index); versioned index names with an alias (the engine has no alias concept, so the swap operation is the equivalent).

### Decision 5: Declare highlights and typo tolerance as capabilities

The adapter reports it supplies highlights and typo tolerance. Highlights are converted to a neutral marker form that the search plugin renders safely, so engine markup never reaches the UI as HTML.

Alternatives: ignore native highlights (wastes the main reason to choose this engine); return engine HTML directly (an injection risk when indexed content contains markup).

### Decision 6: Required services are declared in plugin metadata and resolved by the composer

A plugin's static descriptor can list required services (id, purpose, default image, port, health check, configuration keys). The composer reads these from selected plugins, validates them, records them in the lock, and emits deployment inputs: a service definition plus the plugin's configuration entries. The manifest can mark a service as externally provided with an address, in which case no container is generated.

Alternatives considered:
- **Operators hand-write the service in their own compose file** (no change to tooling). Works but leaves the lock and validation blind to a hard dependency and gives plugin authors no standard way to say what they need.
- **A top-level manifest `services` list independent of plugins.** Decouples services from plugins but allows a selected plugin to lack its service silently and a service to be present with no consumer.
- **A fully general orchestration layer.** More than one dependency needs today.

The descriptor-driven approach keeps a service tied to the plugin that needs it and is the smallest representation that gives validation, locking and generation.

### Decision 7: Endpoint is operator configuration, outside the user-supplied-URL fetch rules

The existing safe-fetching rules protect fetches of user-supplied URLs. The engine address is trusted operator configuration for an internal service, so the adapter connects to it directly and only to it.

Alternatives: route through the safe fetcher (would block the private-network address that is the normal case); accept an address from users (never).

### Decision 8: Keep the PostgreSQL adapter as the default

The default manifest does not change. An example manifest and documentation show how to switch.

### Decision 9: One access key in the first version

The adapter uses a single configured key for both indexing and searching. Searches only originate from the backend and authorization happens in `resolve`, so separate keys add little; they remain a possible later option.

Alternatives: separate indexing and search keys (extra configuration for little gain here); no key (acceptable only on an isolated network, so a key stays required for any instance that enforces one).

### Decision 10: Generated service inputs include a persistent volume

The declared service names a data volume, and generated deployment inputs mount a named volume for it.

Alternatives: no volume (the index is lost whenever the container is recreated and search stays empty until the next rebuild); bind mount to a host path (portable only by accident).

## Risks / Trade-offs

- **Another process to operate** → the service is optional and only generated when selected; health feeds the status endpoint so failures are visible.
- **Task completion waits slow large rebuilds** → batch writes and a configurable timeout; rebuild runs off the request path.
- **Engine and index drift on engine restarts or lost volume** → the periodic rebuild repairs content; document a persistent volume for the service.
- **Composer extension is a new concept** → kept minimal (one declared service per need, container or external address) and documented; no behaviour change for plugins without services.
- **Id encoding adds a mapping layer** → covered by conformance and adapter tests with awkward ids.
- **Highlight conversion bugs could reintroduce markup** → test with markup-bearing content.
- **Access key mismanagement** → secrets resolved centrally, never in the lock or frontend projection.

## Migration Plan

1. Land the adapter package and its tests against a real instance in CI.
2. Extend plugin metadata, the composer, the lock and generated inputs for required services; no change for plugins without them.
3. Add an example manifest and documentation; keep the default manifest on PostgreSQL.
4. Operators switch engines by changing the manifest, regenerating, and letting the first rebuild fill the new engine; to go back, switch again.
5. Rollback: re-select the PostgreSQL adapter; the Meilisearch service and data can be removed.
