## Why

`docs/plugin-architecture.md`'s "Internal contract packages" rule — a plugin may import `atlas_plugin_api`/`@atlas/plugin-api` and explicitly declared contract-only packages, never core internals or another plugin's implementation — is violated pervasively by every first-party plugin built so far. All five backend plugins import directly from `server.apps.catalog` (the base entity model, kind registry, entity service, auth/authorization, api schemas/helpers, relations) instead of a published contract, and several plugins import another plugin's Django models/schemas directly (mostly `atlas_plugin_standard_catalog`, the de facto hub every other plugin depends on). `introduce-plugin-distribution-and-composer`'s CI import-boundary checks (tasks 5.1/5.2) documented every one of these as an allowlisted, tech-debt exception rather than fixing them, so the checks stop new violations without restoring the guarantee the architecture is supposed to provide: that Core and each Plugin version and evolve independently, and that a third-party operator could plausibly build a working plugin against only the published contract packages. Today a plugin's declared `compatibility.atlasCore` range is a decorative promise — Core's semver carries no obligation to keep `server.apps.catalog`'s internal module layout stable, only a real published contract would make that enforceable.

## What Changes

- Extract Core's actually-relied-upon plugin-facing surface into `atlas_plugin_api`/`@atlas/plugin-api` as real, versioned contract types/protocols: a base entity type/protocol standing in for `CatalogEntity`, the Entity Kind registration protocol/registry accessor, an entity-service-facing protocol, an auth/permission registration protocol, and whatever `refs`/`relations` helpers plugins genuinely need. Every first-party plugin currently importing the `server.apps.catalog`/`server.apps.plugins.permissions` internals allowlisted by `test_import_boundaries.py` is migrated onto the new contract types.
- For each plugin-to-plugin edge currently allowlisted in `test_import_boundaries.py`/`importBoundary.test.ts` (`ingestion` → `apis`/`standard-catalog`, `apis`/`c4`/`database-schema` → `standard-catalog`), decide and apply a per-edge fix: either the depended-on plugin publishes a small declared contract-only package/submodule (types only, no Django models/implementation), or the dependency is restructured through an existing capability/extension point instead of a direct type import. This is a real per-edge design decision, not one rule applied uniformly — resolved in design.md, not silently in code.
- Shrink both CI import-boundary checks' allowlists (`ALLOWED_CORE_SUBMODULES`, `ALLOWED_PLUGIN_TO_PLUGIN_EDGES` in `test_import_boundaries.py`; the equivalent frontend allowances) to match what's left after the extraction — ideally to empty, so the checks enforce the real rule rather than documenting exceptions to it.
- **BREAKING** (internal only, no external consumers yet per ADR 0021): every plugin's imports of `server.apps.catalog.*`/`server.apps.plugins.permissions`/another plugin's implementation module are replaced with imports from `atlas_plugin_api`/`@atlas/plugin-api` or a declared contract package. Plugin behavior is unchanged; only the import surface moves.
- Revisit whether the Python-side import-boundary check should move from the current hand-rolled AST-scanning pytest test onto `import-linter` (`layers`/`forbidden` contracts) now that the allowed-edge surface is small enough for a real layered-architecture config to replace an allowlist of documented exceptions — decided in design.md. The TypeScript-side check stays hand-rolled either way (no comparably-adopted equivalent tool is in use in this repo).

## Capabilities

### New Capabilities
- `core-plugin-contract-surface`: Core publishes the plugin-facing surface it actually expects plugins to use (base entity type, Entity Kind registration, entity service access, auth/permission registration) through `atlas_plugin_api`/`@atlas/plugin-api` as versioned contract types, instead of plugins reaching into `server.apps.catalog`/`server.apps.plugins` internals directly.
- `plugin-contract-packages`: a plugin that other plugins legitimately depend on (starting with `atlas_plugin_standard_catalog`) publishes a declared contract-only package or submodule — types only, no Django models or business logic — for the specific cross-plugin surface other plugins need, replacing direct imports of its implementation modules.

### Modified Capabilities
(none — `entity-kind-registry`, `plugin-registries`, `entity-lifecycle-service`, and `policy-evaluator-extension`'s existing requirements are unchanged; only *where* plugins reach these mechanisms from moves, not the mechanisms' own behavior)

## Impact

- **Backend**: `atlas_plugin_api` gains new modules (base entity type/protocol, kind registry accessor, entity-service protocol, auth/permission registration protocol). Every plugin package's imports of `server.apps.catalog.*`/`server.apps.plugins.permissions` are replaced; no behavior change.
- **Frontend**: `@atlas/plugin-api` gains the equivalent contract surface if any plugin-to-plugin frontend coupling needs one (current frontend plugins only import `@atlas/plugin-api` already — TBD in design.md whether this side needs any change at all).
- **Plugin-to-plugin**: `atlas_plugin_standard_catalog` (and any other plugin found to need it) gains a declared contract-only package; dependent plugins (`ingestion`, `apis`, `c4`, `database-schema`) migrate onto it or onto a capability/extension-point restructuring instead.
- **CI**: `core/backend/server/apps/plugins/tests/test_import_boundaries.py` and `core/frontend/src/plugins/importBoundary.test.ts`'s allowlists shrink to match the new, real boundary; a follow-up decision (not required for this change to land) is whether to replace the Python check with `import-linter`.
- **No product-behavior spec is modified** — every plugin's externally observable behavior (API responses, UI, permissions) is unchanged; this is a pure internal-boundary/packaging change.
- **Dependents**: any future first-party plugin, and the eventual external-operator-plugin story ADR 0021 anticipates, get a real contract surface to build against instead of undocumented internals.
