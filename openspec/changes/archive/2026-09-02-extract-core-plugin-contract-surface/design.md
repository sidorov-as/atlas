## Context

`introduce-plugin-distribution-and-composer` added CI import-boundary checks (`core/backend/server/apps/plugins/tests/test_import_boundaries.py`, `core/frontend/src/plugins/importBoundary.test.ts`) enforcing `docs/plugin-architecture.md`'s "Internal contract packages" rule: a plugin may import `atlas_plugin_api`/`@atlas/plugin-api` and explicitly declared contract-only packages, never core internals or another plugin's implementation. Adding the check surfaced that every first-party plugin already violates it — the checks shipped with two allowlists (`ALLOWED_CORE_SUBMODULES`, `ALLOWED_PLUGIN_TO_PLUGIN_EDGES`) documenting every current violation as known tech debt rather than fixing it, so CI stops new violations without restoring the guarantee ADR 0021 exists for: that Core and each Plugin can version and evolve independently, verified by nothing accessing an unpublished internal.

Two categories of violation exist, and they need different fixes:
- **Plugin → Core internals**: all five plugins import `server.apps.catalog.{models,models.base,kinds,kinds.handler,kinds.registry,api.auth,api.filters,api.helpers,api.schemas,services,services.entity_service,authorization,relations,refs}` and `atlas_plugin_c4` additionally imports `server.apps.plugins.permissions`. None of this is published in `atlas_plugin_api` today.
- **Plugin → Plugin**: `atlas_plugin_standard_catalog` is a de facto hub. Two edges are real ORM cross-plugin queries against another plugin's Django model (`atlas_plugin_ingestion.pipeline` filters `atlas_plugin_apis.models.ApiDetails` for its periodic spec-refresh job; `atlas_plugin_apis.kinds.api_handler.validate_delete` filters `atlas_plugin_standard_catalog.models.ComponentDetails` to block orphaning deletes) — these can't be fixed by moving *types* into a contract package, since Django ORM querying needs the real model class. The rest are pure Pydantic schema/type imports (`ApiIn`, `ApiSpecPatch`, standard-catalog's `api.schemas.*`), plus a handful of plugin↔plugin imports that exist only inside `tests/conftest.py` fixtures (`atlas_plugin_c4`, `atlas_plugin_database_schema` → `atlas_plugin_standard_catalog.models`, building test entities).

## Goals / Non-Goals

**Goals:**
- Every part of Core's plugin-facing surface that a first-party plugin actually needs is published through `atlas_plugin_api`/`@atlas/plugin-api` as a versioned contract type/protocol.
- `atlas_plugin_standard_catalog` publishes a declared contract-only package for the type/schema surface other plugins need from it.
- The two real ORM cross-plugin queries (ingestion's spec-refresh job, apis' `validate_delete`) no longer require the caller to import the other plugin's Django model directly.
- Both CI import-boundary checks' allowlists shrink to (ideally) empty, except test-only fixture imports, which stay allowlisted.
- No product-behavior change: every migrated import is a pure refactor, verified by the existing spec-scenario test suite passing unchanged.

**Non-Goals:**
- Publishing `atlas_plugin_api`/`@atlas/plugin-api` as a stable `1.0` public SDK — stays internal `0.x` per ADR 0021; this change gives the surface real contract types, not a stability promise.
- A general "plugin dependency injection" framework or event bus — the extension-point restructuring here is scoped to the one case that needs it (`validate_delete`), reusing the existing `EntityKindHandler.validate_delete` pattern already in the codebase, not inventing a new generic mechanism.
- Extracting `auth-local`/`auth-oidc` into standalone plugin packages — still deferred (per `introduce-plugin-distribution-and-composer` tasks.md 1.3's note), out of scope here.
- Migrating the import-boundary check to `import-linter` — a follow-up decision once this change's allowlists are near-empty (see Risks/Trade-offs), not required for this change to land.

## Decisions

**Core surface extraction, by original module:**
- `server.apps.catalog.models.base.CatalogEntity` → `atlas_plugin_api` cannot import the concrete model at all: `core/backend`'s `pyproject.toml` sets `package-mode = false`, so `server` is never an installable package anything can formally depend on (a static import only "works" today via the shared dev virtualenv, which is exactly the undeclared coupling this change removes). Instead, three Django-idiomatic pieces, none requiring `atlas_plugin_api` → `server`:
  - a `CatalogEntity` `Protocol` in `atlas_plugin_api` (id, kind, name, namespace, title, description, labels, tags, links, owner, source_kind, `SOURCE_MANUAL`/`SOURCE_YAML`, ingested_from, created_at, updated_at, `ref`, `details`) for static type hints only — no Django dependency needed for this half;
  - a `get_catalog_entity_model()` runtime accessor in `atlas_plugin_api`, resolving via Django's own app registry (`django.apps.apps.get_model('catalog', 'CatalogEntity')`, the same mechanism `get_user_model()` uses) — for `.objects.filter(...)`/`.DoesNotExist`/class-attribute call sites, requiring only a `django` dependency on `atlas_plugin_api`, not a `server` one;
  - plugin `*Details` models switch their `entity = OneToOneField(CatalogEntity, ...)` to Django's standard lazy string reference `OneToOneField('catalog.CatalogEntity', ...)` — Django's built-in mechanism for cross-app FKs, needing no import of the target class at all.
- `server.apps.catalog.kinds.{registry,handler}` → a `register_kind`/`kind_handler` function and the `ValidateDeleteError` type published by `atlas_plugin_api`.
- `server.apps.catalog.services.entity_service` → an entity-read/write protocol published by `atlas_plugin_api`, wrapping the existing `entity_service` singleton without exposing it directly.
- `server.apps.catalog.authorization`/`server.apps.plugins.permissions` → a permission-registration function published by `atlas_plugin_api`, replacing direct `policy_evaluator`/`registry` imports.
- `server.apps.catalog.api.{auth,filters,helpers,schemas}`, `server.apps.catalog.refs`, `server.apps.catalog.relations` → published as-needed by what plugins actually call (audited per plugin during implementation); each becomes either a re-export or a thin wrapping type in `atlas_plugin_api`.
- `server.apps.catalog.models.{relation,architecture_relationship,audit,tag,external_identity,flow}` (`Relation`, `ArchitectureRelationship`, `EntityAuditRecord`, `Tag`, etc.) — found during task 1.1's audit to be imported by plugins (e.g. `atlas_plugin_c4.c4`, `atlas_plugin_standard_catalog`'s tests) under the same blanket `server.apps.catalog.models` allowlist entry as `CatalogEntity`, but out of task 1's base-entity/KIND_* scope and not otherwise named in the original design — folded into task 5's audit alongside `refs`/`relations`/`api.*` rather than left unmigrated.
- Every one of these gets a matching entry removed from `ALLOWED_CORE_SUBMODULES` once its consumers migrate, so the allowlist and the actual `atlas_plugin_api` surface stay in lockstep — a submodule never sits in the allowlist and the published surface at the same time for long.

**Plugin-to-plugin edges — mixed strategy, chosen per edge (not applied uniformly):**
- **Pure type/schema imports** (`ingestion` → `apis`'s `ApiIn`/`ApiSpecPatch`; `ingestion`/`apis`/`c4`/`database-schema` → `standard-catalog`'s `api.schemas.*`/model *types*) move onto a declared contract-only package each depended-on plugin publishes (e.g. `atlas_plugin_standard_catalog.contracts`, `atlas_plugin_apis.contracts`) — types and value objects only, no Django models or business logic, matching `plugin-contract-packages` spec.
- **`ingestion`'s periodic spec-refresh job** (`ApiDetails.objects.filter(...)` in `pipeline.py`) moves onto a narrow function `atlas_plugin_apis` publishes in its contract package (e.g. `due_for_spec_refresh() -> Iterable[...]`) — `atlas_plugin_apis` keeps owning the ORM query and its own model; `ingestion` calls the function instead of importing `ApiDetails`. Chosen over inverting this into an extension point because this is `ingestion`'s own background job pulling data on its own schedule, not reacting to an event `atlas_plugin_apis` would need to publish — a function call is the natural shape.
- **`apis`'s `validate_delete` check against `ComponentDetails`** is restructured as an extension point: `atlas_plugin_standard_catalog` registers its own "does anything still reference this API?" check against the same `validate_delete`-style mechanism `EntityKindHandler` already uses elsewhere in the codebase, and `atlas_plugin_apis` stops importing `atlas_plugin_standard_catalog` for this at all. Chosen over a contract-package function because this is exactly the shape the codebase's existing extension-point pattern (a plugin registering a check that runs when another entity's lifecycle event fires) already covers — reusing it here is more consistent than adding a second, function-call-based mechanism for a structurally identical problem.
- **Test-only edges** (`atlas_plugin_c4`/`atlas_plugin_database_schema`'s `tests/conftest.py` importing `atlas_plugin_standard_catalog.models.*` to build fixture entities) stay allowlisted as a documented test-only exception, symmetric with the existing `server.apps.catalog.tests.factories` test-only allowance in the core-internals check. Not migrated onto the contract package: these are first-party test fixtures, not something a third-party plugin author's own tests would need to reach through a published contract, and requiring every plugin's test suite to route through a contracts-only fixture package is disproportionate cost for no externally-visible guarantee gained.

**CI check tightening**: both `test_import_boundaries.py`'s `ALLOWED_CORE_SUBMODULES`/`ALLOWED_PLUGIN_TO_PLUGIN_EDGES` and the frontend equivalent shrink as each edge is migrated (task-by-task, not one big-bang removal at the end) — each task that migrates an edge also removes that edge's allowlist entry in the same change, so the check can never regress silently mid-implementation.

## Risks / Trade-offs

- [The `validate_delete` extension-point restructuring changes control flow (inversion of who calls whom), not just an import path — larger diff and more test surface than a straight function-contract swap] → Scope it narrowly to the one case that needs it; if it proves more disruptive than expected during implementation, fall back to a contract-package function for this edge too and note the inconsistency rather than blocking the whole change on it (flagged here so a mid-implementation pause to reconsider isn't a surprise).
- [`atlas_plugin_api`'s base entity type must compose correctly with Django's model metaclass, which constrains how "just a Protocol" can work] → Resolved: plugins never subclass `CatalogEntity` (confirmed by auditing every plugin's usage during task 1.1) — they use it as an FK target and issue real ORM queries against it. Since `atlas_plugin_api` structurally cannot import the concrete model (`core/backend` is `package-mode = false`, not an installable dependency), the split is a `Protocol` for static typing plus a `get_catalog_entity_model()` runtime accessor via Django's app registry, plus Django's standard FK string-reference idiom for `*Details` models — see Decisions above. `core-plugin-contract-surface`'s spec scenario is updated to say "references" rather than "subclasses" to match.
- [Migrating five plugins' imports simultaneously is a wide, mechanical diff, similar in shape to `introduce-plugin-distribution-and-composer`'s monorepo restructuring] → Do it module-by-module (one `server.apps.catalog` submodule extracted and migrated at a time, each verified by the full test suite before moving to the next), not as one large simultaneous swap.
- [Import-linter would be a better long-term enforcement tool than the current hand-rolled AST scan, but only once the allowlists are near-empty] → Explicitly deferred (Non-Goals); revisit once this change lands and the exception surface is small enough for a real `layers`/`forbidden` config to replace the allowlist-based check without losing the inline rationale the current allowlists carry for what's left.

## Migration Plan

1. Publish each Core surface piece in `atlas_plugin_api` one at a time (base entity type, kind registration, entity service protocol, permission registration, then the smaller `refs`/`relations`/`api.*` pieces as audited), migrating its consumers and shrinking `ALLOWED_CORE_SUBMODULES` in the same step.
2. Publish `atlas_plugin_standard_catalog`'s and `atlas_plugin_apis`'s contract-only packages; migrate the pure type/schema plugin-to-plugin edges onto them, shrinking `ALLOWED_PLUGIN_TO_PLUGIN_EDGES` accordingly.
3. Add `atlas_plugin_apis.contracts.due_for_spec_refresh()` (or equivalent); migrate `ingestion`'s periodic job onto it.
4. Restructure `apis`'s `validate_delete` check as a `standard-catalog`-registered extension point; remove `atlas_plugin_apis` → `atlas_plugin_standard_catalog`'s `ComponentDetails` import entirely.
5. Confirm the two test-only edges are the only remaining `ALLOWED_PLUGIN_TO_PLUGIN_EDGES` entries; leave them allowlisted with their rationale, per the Decisions above.
6. Run the full backend/frontend spec-scenario suite end-to-end; confirm both CI import-boundary checks pass with their shrunk allowlists.
7. Rollback: each module-by-module step (1-4) is independently revertible (an import path change plus its allowlist entry), so a problem discovered partway through only requires reverting the step in progress, not the whole change.

## Resolved

- **ORM cross-plugin edges (ingestion→apis, apis→standard-catalog)**: mixed strategy — function-contract for `ingestion`'s periodic job, extension-point restructuring for `apis`'s `validate_delete` — decided above (Decisions), not applied uniformly.
- **Test-only plugin-to-plugin edges**: stay allowlisted as a documented test-only exception, symmetric with the core-internals check's existing test-only allowance; not migrated onto a contract package.
