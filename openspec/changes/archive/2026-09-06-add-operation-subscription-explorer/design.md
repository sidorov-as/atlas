## Context

`add-endpoint-dependency-explorer` (archived) modeled `Endpoint` as plugin-owned child data of `API`, plus a bespoke `ServiceEndpointUsage` join, for REST/OpenAPI. `ApiDetails.type` has included `TYPE_ASYNCAPI` since that change's own model (`models/api.py`), and `AsyncApiViewer.tsx` already renders a whole AsyncAPI document — but nothing in `atlas_plugin_apis` models the document's individual operations. This change is the AsyncAPI-side counterpart to `Endpoint`/`ServiceEndpointUsage`, following the same plugin-owned-child-data pattern, but the AsyncAPI operation model is not a 1:1 relabeling of the REST one — three properties of AsyncAPI itself force real (not cosmetic) differences from the `Endpoint` precedent, discovered while working through this design with the user before writing it down:

1. **AsyncAPI's own `publish`/`subscribe` vocabulary (2.x) is defined from the channel's perspective, and is easy to get backwards.** Verified against the primary spec source (`spec/asyncapi.md`, v2.6.0, Channel Item Object): a 2.x **`publish`** operation "defines the messages **consumed by the application** from the channel," and a 2.x **`subscribe`** operation "defines the messages **produced by the application** and sent to the channel." This is the reverse of the intuitive "publish = app sends" reading, and is exactly the confusion AsyncAPI 3.0's explicit `action: send | receive` was introduced to resolve. An earlier pass at this design initially recorded the mapping backwards; this document fixes that before any model or importer is built on top of it (the importer is a later change — Non-Goals below — but the enum this change ships must already be the version-agnostic, correctly-mapped one, or the importer would need a data migration to fix silently-inverted graph edges after the fact).
2. **An operation's direction is a fact about the document that declared it, not a fact about every other Service that might touch the same channel.** `Endpoint` never needed this distinction — a REST consumer link only ever means one thing ("this Service calls this endpoint"). A channel has two sides, and `ApiOperation.direction` only describes the one side the owning API document declares; a linked Service's own relationship to the channel (publisher or subscriber) is a separate fact that direction alone cannot express, particularly once more than one Service can be linked to one operation.
3. **Two independently-authored API documents can each contribute an operation for the same real-world channel.** `Endpoint` identity (`method + path`) never collides across two APIs describing genuinely different REST resources. An AsyncAPI channel is different: `orders-service`'s document might declare `send` on `order.created` while `billing-service`'s document declares `receive` on that same address — two distinct `ApiOperation` rows about one event. Nothing in this change auto-links or merges them (Non-Goals), but the list/graph UI still has to avoid presenting them as unrelated.

## Goals / Non-Goals

**Goals:**
- Model `Operation` as a child of `API`, owned entirely by `atlas.apis`, normalized so a future importer can populate it from either AsyncAPI 2.x or 3.0 without a schema change.
- Model `Service <-> Operation` as a plugin-owned link with its own lifecycle, like `ServiceEndpointUsage`, but carrying an explicit `role` — the piece `Endpoint` didn't need (Context, point 2).
- Avoid manually re-stating what an operation's own document already says: the document-owning Service's relationship to its own operations is implied by `direction`, not linked through `ServiceOperationUsage`.
- Ship an Operation documentation UI (Overview/Message tabs) and a Linked Services management UI, plus a compact, read-only publishers/subscribers graph, all grouped/scoped by channel address rather than by individual operation row (Context, point 3).
- Preserve operation-dependency history: removing an `Operation` never silently destroys the `ServiceOperationUsage` links recording who depended on it — same invariant as `Endpoint`.

**Non-Goals (deferred to a later change):**
- AsyncAPI 2.x/3.0 spec parsing/import — a dependent follow-up change (tentatively `import-asyncapi-operations`), mirroring how `import-openapi-endpoints` depended on this change's sibling. This change's model is kept import-ready (Decision 4's `operation_key`, Decision 2's `channel_address`/`channel_protocol`) but ships with admin/fixture-authored data only.
- Any automatic/derived link between two `ApiOperation` rows that share a `channel_address` (Context, point 3) — no auto-graph-edge, no auto-merge. `ServiceOperationUsage` stays 100% human-asserted in this change. (See Open Questions for what a future ingestion connector could do without a data-model change.)
- AsyncAPI 3.0's `reply` (request/reply) operations — not modeled.
- A full multi-channel topology explorer beyond the compact per-channel graph (same scoping as `Endpoint`'s Non-Goal for a full-screen explorer).
- Channel address normalization across differing templating styles (e.g. `user/{userId}/events` vs. a broker wildcard subscription) — `channel_address` is stored and compared as an exact string in this change, same spirit as `Endpoint`'s exact-`path`-string Non-Goal.
- Any auto-created/updated `ComponentDetails` relation as a side effect of linking a Service to an Operation. `Endpoint` linking auto-creates `consumesAPI` (Decision 3 of its own design) because `consumesApis`/`providesApis` M2M fields already existed for it to write to. No equivalent `publishesEvents`/`subscribesToEvents` field exists on `ComponentDetails` today, and introducing one — plus deciding whether a "publisher" link should write to `providesApis` given that field today models a single document-owning relationship, not an arbitrary fan-in of publishers — is a distinct cross-plugin design decision this change does not make. `ServiceOperationUsage` in this change has no side effect beyond its own row.

## Decisions

### 1. `Operation` is plugin-owned child data, not a registered Entity Kind
**Decision:** `ApiOperation` is a plain Django model in `atlas_plugin_apis.models`, FK'd to the API's `CatalogEntity` (mirrors `ApiEndpoint`), with no `kind_id`, no `EntityKindHandler`, no top-level `/catalog/entities/...` route — addressed only via `/apis/:apiId/operations/:operationId` (frontend) and `/api/apis/{apiId}/operations/{operationId}` (backend).

**Why:** Identical reasoning to `Endpoint` Decision 1 — an operation has no independent owner/team/tags/visibility; it inherits all of that from its API. No product need for it to appear in the generic entity list/search/capability system.

**Alternative considered:** Register `operation` as a full Entity Kind. Rejected for the same reasons as `Endpoint`'s Decision 1.

**Not a Facet either:** `openspec/specs/entity-facets/spec.md` requires a Facet to be a `OneToOne` model keyed by `CatalogEntity.id` — one record per entity. `ApiOperation` is one-to-many (many operations per `API`), so it does not fit that shape, exactly like `Endpoint`/`ServiceEndpointUsage` (see `add-endpoint-dependency-explorer`'s archived design.md, which makes this same comparison explicitly). Recorded here so a future reader doesn't have to re-derive why this isn't modeled as a Facet.

### 2. Channel identity fields: `channel_address` + `channel_protocol`, not the raw document channel key
**Decision:** `ApiOperation` stores `channel_address` (the AsyncAPI 3.0 `channel.address` value; for 2.x, or for a 3.0 channel with a null `address`, falls back to the channel's own map key/identifier) and `channel_protocol` (from the document's/channel's `servers`/`protocol`, when resolvable). Neither field is used as a cross-document join key in this change (Non-Goals) — they exist so:
- the Operations list/tab can group rows by `channel_address` without conflating two unrelated channels that happen to share a literal name on different brokers (`channel_protocol` disambiguates the display), and
- a future importer or ingestion connector has a stable, already-normalized field to match on, without a later migration to split "channel identifier" from "wire address" after data already exists.

**Why:** AsyncAPI 3.0 explicitly separates a channel's map key (an arbitrary document-local identifier) from its `address` (the actual routing key/topic) — the two are not the same string in general. Storing the map key would be storing an implementation detail of one document's authoring style, not the fact that would let a human recognize "these two operations are about the same event." Following `Endpoint`'s own precedent for `path`: identity should be exact and unresolved, but the *display*/*grouping* field should be the most durable, cross-document-comparable value available, which for AsyncAPI is `address`, not the map key.

**Alternative considered:** Store only the raw channel key (whatever the document calls it) and defer any address/key distinction to the importer change. Rejected: the model itself would need a migration later to add `channel_address` once the importer needs it, and the UI (Decision 6/7 below) needs a grouping field now regardless of whether real spec data exists yet.

### 3. `direction` is a canonical `send | receive` enum — never the raw `publish`/`subscribe` words
**Decision:** `ApiOperation.direction` is stored as `send | receive` (AsyncAPI 3.0's own vocabulary), computed by whatever writes the row (admin/fixtures now; the importer later) using the verified mapping: AsyncAPI 2.x `publish` → `receive`; AsyncAPI 2.x `subscribe` → `send`; AsyncAPI 3.0 `action: send`/`action: receive` map through unchanged.

**Why:** See Context, point 1. Storing `publish`/`subscribe` literally would mean every future reader of this model has to already know (or look up) which AsyncAPI version's semantics applied when the row was written, and would make the field's meaning depend on which spec version produced it — exactly the ambiguity AsyncAPI 3.0 itself eliminated by introducing `send`/`receive`. The UI (Decision 8) still uses the words "Send"/"Receive" for this field's badge, matching the stored enum one-to-one — no separate UI-vocabulary translation layer to keep in sync.

**Alternative considered:** Store the direction as `publish | subscribe`, translated to `send`/`receive` only at read time by a per-version adapter. Rejected: pushes the version-perspective bug (Context, point 1) into every reader instead of resolving it once at write time; also produces a stored value that reads as self-evidently wrong to anyone who knows AsyncAPI 3.0's vocabulary but not 2.x's specific inversion.

### 4. Operation identity for re-import stability: `operation_key`, not `channel_address + direction` universally
**Decision:** `ApiOperation.id` is its own UUID (never derived from channel/direction/operation_id — same reasoning as `ApiEndpoint.id`, so it survives a channel rename across re-import and keeps `ServiceOperationUsage` links stable). Business identity for upsert (used by the future importer, but the field is part of this change's model) is `operation_key`, computed per spec version:
- **AsyncAPI 3.0:** the operation's own key in the top-level `operations` map — always present (spec-mandated), always unique within the document, and stable across an edit to the *channel* it references (a channel rename doesn't change the operation's own map key).
- **AsyncAPI 2.x:** `channel_address + direction` — 2.x has no separate operation-map key (operations are the fixed `publish`/`subscribe` fields nested under a channel), but this pairing is inherently unique (at most one `publish` and one `subscribe` per channel).

`operation_id` (the spec's optional `operationId`/`title` field) is stored separately, purely decorative — like `ApiEndpoint.operation_id` — and is never used for identity, since it's just as editable as any other documentation field and no more stable than the channel key it would otherwise be a fallback for.

**Why:** `Endpoint`'s `method + path` is a natural key precisely because both parts are structurally stable positions in an OpenAPI document. AsyncAPI has no single equivalent: 2.x's most stable position is the channel-plus-fixed-field-name pair; 3.0's most stable position is a different thing (the operations-map key), which happens to be strictly more stable than 2.x's own key (it survives a channel address edit, which 2.x's `channel_address + direction` cannot). Recognizing that the "most stable position" isn't the same shape in both versions, and picking each version's actual best key, is more correct than the initially-proposed but weaker rule ("operationId if present, else channel + direction") — `operationId` is decorative in both versions and no more durable than the fallback it would precede.

**Known accepted gap:** renaming a channel in a 2.x document changes that operation's `operation_key`, which (once the importer exists) reads as a soft-remove of the old row plus a new row with no `ServiceOperationUsage` history — same class of gap `Endpoint` doesn't have (a `path` rename has no 2.x-only equivalent problem). Not solved in this change or its importer follow-up; noted for whoever builds cross-document matching later (Open Questions).

### 5. `ServiceOperationUsage` carries an explicit `role`, and the document owner is never self-linked
**Decision:** `ServiceOperationUsage` (FK to `ApiOperation`, FK to the linked Service's `CatalogEntity`, `role: publisher | subscriber`, `created_at`, `created_by`, `unique_together(operation, service, role)`) is a bespoke, plugin-owned link — not routed through core `entity-relations` — mirroring `ServiceEndpointUsage`'s own Decision 2 rationale (a plugin-specific query shape the generic relations endpoint doesn't support). Its REST surface mirrors `ServiceEndpointUsage`'s:
- `POST /api/operations/{operationId}/services` — body `{"serviceId": "...", "role": "publisher" | "subscriber"}`
- `DELETE /api/operations/{operationId}/services/{serviceId}?role=publisher|subscriber` — `role` is a required query parameter, not inferred or removed-for-all. Since `unique_together(operation, service, role)` allows one Service to hold *both* roles on the same Operation, a service-scoped-only DELETE couldn't unambiguously target one row; the Linked Services table already renders one row per (service, role) pair (task 5.5), so its per-row Unlink action already knows which role to pass.
- `GET /api/operations/{operationId}/services`
- `GET /api/operations/{operationId}/consumers` — reshaped for Decision 7's channel-scoped graph, not a single-operation projection (see Decision 7)

The API document's own owning Service — found via the existing `apiProvidedBy` relation (already surfaced today as `EndpointConsumersGraph.tsx`'s `providerRelation`) — is never created as a `ServiceOperationUsage` row for its own API's operations. Its role on any graph/list view showing that operation is derived purely from `ApiOperation.direction` (`send` → shown as publisher, `receive` → shown as subscriber), computed at read time, not stored.

**Why:** See Context, points 1 and 2. `direction` and `role` answer different questions — "what does this document declare" vs. "what does a human assert about some other Service" — and collapsing them into one field (as `Endpoint`'s single-sided consumer model could get away with) would make it impossible to record "Service B and Service C are both subscribers to this send operation," which is the graph this whole change exists to produce. Not requiring a link for the document's own owning Service avoids doubling manual work for the one relationship the spec already states unambiguously, and avoids a human accidentally recording a `ServiceOperationUsage` role that contradicts the operation's own `direction`.

**Alternative considered:** A single `role` field on `ApiOperation` itself (no separate `ServiceOperationUsage.role`), with every linked Service assumed to hold the "other" role from the operation's `direction`. Rejected: this cannot express two Services holding the *same* role against one operation (e.g. three subscribers to one channel), which is a completely ordinary real-world shape this feature needs to represent.

### 6. Operations list is grouped by `channel_address`, not a flat sortable table
**Decision:** The Operations tab (analogous to `EndpointsListTab.tsx`) renders **grouped sections keyed by `channel_address`** — each section shows a producer/consumer count summary (e.g. "order.created — 1 producer, 3 consumers") with its `ApiOperation` rows nested underneath, rather than one flat table with a sortable Channel column.

**Why:** Context, point 3 — a flat table with a sortable column still lets two rows about the same real-world channel land far apart depending on sort order, silently under-communicating that they're related. Grouping is what actually solves the "two documents, one event" fragmentation visibility problem; a sortable column only makes it *possible* to notice by manually re-sorting, which defeats the purpose of building this feature in the first place.

**Alternative considered:** Flat table, mirroring `EndpointsListTab.tsx` exactly, with Channel as a sortable/filterable column. Rejected per the above — considered and explicitly rejected during design discussion with the user, not an oversight.

### 7. `OperationConsumersGraph` is scoped to `channel_address`, not to a single `ApiOperation`
**Decision:** The compact "Publishers & subscribers" graph on the Operation Overview tab (mirroring `EndpointConsumersGraph.tsx`'s endpoint-center/service-ring layout) aggregates **every `ApiOperation` row sharing the current operation's `channel_address`** — across potentially multiple `API` documents — into one graph, rather than showing only the current operation's own direct `ServiceOperationUsage` links. `GET /api/operations/{operationId}/consumers` resolves the operation, then queries by its `channel_address` rather than by its own `id` alone.

**Why:** Directly follows from Decision 6 and Context point 3: if the list groups by channel to avoid presenting two related operations as unrelated, the graph built from clicking into one of those operations has to do the same or it re-introduces the exact fragmentation the list just fixed — a channel with a `send` operation on one API document and a `receive` operation on another would otherwise render as two disconnected single-node graphs instead of one connected picture with both a publisher and its subscribers.

**Alternative considered:** Scope the graph strictly to the single `ApiOperation` (mirroring `EndpointConsumersGraph.tsx` exactly, minimal change). Rejected — this was the design's first instinct, walked back specifically because it reproduces the fragmentation problem this change exists to solve; kept here for traceability, not as a live option.

**Visibility filtering is required at the aggregation boundary:** Decision 10 grants `operation.read`/`operationDependency.read` to *any authenticated principal* when `resource=None` — the RBAC layer does not scope this by which `API`s a principal can otherwise see. The only thing standing between a viewer and a restricted-visibility API's data is that API's own `visibility` field (already the mechanism protecting its own detail page — see `specs/api-operations/spec.md`'s "Operation documentation displays its API's owner/domain/visibility" requirement). Because Decision 7 aggregates across *every* `ApiOperation` sharing a `channel_address`, including ones on API documents the current viewer cannot otherwise see, `GET /api/operations/{operationId}/consumers` (and the equivalent data feeding the Overview graph/preview) MUST filter out any aggregated `ApiOperation` whose owning `API` is not visible to the requesting principal, and MUST do so silently (omit, don't error) — surfacing even the count or existence of a hidden API's operation on a shared channel is itself a disclosure. This applies whether or not the RBAC permission grant above turns out to be exactly as described; the aggregation is cross-API by construction (Decision 7), so it needs this check regardless of how permission checking is implemented.

**Why this wasn't caught earlier:** the single-operation-scoped alternative (rejected above) never had this problem — a `ServiceOperationUsage` query scoped to one `ApiOperation.id` only ever touches data already gated by that operation's own API visibility. Aggregating by `channel_address` deliberately reaches across API-document boundaries (Context, point 3), and that reach has to stop at the same visibility boundary the rest of the catalog already enforces, or the channel-grouping feature this change exists to build becomes a way to route around it.

**Verified during implementation (task 3.4) — no such boundary exists today:** the premise above ("whatever mechanism gates an API's own detail page must also gate this aggregation") assumed some form of per-entity read restriction already existed to reuse. It doesn't. `openspec/specs/catalog-auth/spec.md`'s own requirement states read access is unrestricted for any logged-in user ("v1 has no per-entity read ACL"), `RBACPolicyEvaluator.check()` (`core/backend/server/apps/catalog/authorization.py`) grants every `*.read` permission to any authenticated principal unconditionally regardless of `resource`, no `CatalogEntity`/`ApiDetails` model field named `visibility` or `domain` exists anywhere in the backend, and `ApiDetailController.get` itself performs no resource-level check beyond session authentication. There is nothing narrower than "authenticated" to filter on. Per user decision (2026-09-06): `GET /api/operations/{operationId}/consumers` ships with **no visibility filter** — every authenticated principal already sees every API's operations today, so omitting the filter changes no actual exposure; the filtering clause in this Decision and in `specs/operation-service-dependencies/spec.md`'s "Cross-API aggregation respects each aggregated API's visibility" requirement is **not implemented** and should be revisited only if/when a real per-entity visibility mechanism is introduced elsewhere in the catalog.

### 8. Direction and role badges use deliberately different vocabularies
**Decision:** The `direction` badge (on an `ApiOperation` row, mirroring `MethodBadge`'s "text alongside color, never color alone" accessibility rule) reads "Send"/"Receive," matching the stored enum verbatim. The `role` badge (on a `ServiceOperationUsage` row/graph node) reads "Publisher"/"Subscriber" — different words, deliberately.

**Why:** These are different kinds of facts (Decision 5) and using the same words for both would visually imply they're the same kind of assertion (or worse, invite a reader to assume one is derived from the other, which is only true for the document owner's own implied role, not for every linked Service). Using AsyncAPI's own 3.0 vocabulary for the spec-derived field and ordinary role words for the human-asserted field keeps the two visually distinguishable at a glance, without reintroducing `publish`/`subscribe` as a stored value anywhere (Decision 3).

### 9. Operations are read-only in this change; removal is soft, never destructive
**Decision:** Same as `Endpoint` Decision 7, applied to `Operation`: no self-service create/edit UI ships; documentation is entered administratively (Django admin/fixtures). `ApiOperation` gains `status` (`active` | `removed`, default `active`); `ServiceOperationUsage` rows are never cascade-deleted when their operation is removed. `GET /api/apis/{apiId}/operations` defaults to `status=active`, with removed operations surfaced separately (same pattern as `Endpoint`'s "Removed endpoints" filter). No `operation.edit` permission is introduced.

**Why:** Identical rationale to `Endpoint` Decision 7 — the central product value here is impact analysis ("who's affected if this event goes away"), which a hard, cascading delete would destroy at exactly the moment it matters. Self-service/import-driven authoring is deferred to the same follow-up shape `Endpoint` deferred to (OpenAPI import → this change's Non-Goal, AsyncAPI import).

**Audit trail:** the "Mark as removed" admin action (tasks.md 1.4) MUST go through Django admin's standard `log_change`/`LogEntry` recording (the default behavior for an admin action that saves a model change), so who removed an `Operation` and when is recoverable from the standard admin history, not lost. This change does not build a bespoke notification system for `ServiceOperationUsage` owners whose link now points at a removed operation — that's a real gap (a linked Service's team has no push notice), but disproportionate to build here; the admin log entry is the minimum needed so the fact is at least recoverable on request. Revisit a real notification if this proves to be a recurring support question.

### 10. Permissions — no evaluator change needed this time
**Decision:** New permission strings, registered by `atlas.apis` following the exact naming convention already established (`atlas.apis.endpoint.read` → `atlas.apis.operation.read`; `atlas.apis.endpointDependency.{read,create,delete}` → `atlas.apis.operationDependency.{read,create,delete}`). Both `Operation` and `ServiceOperationUsage` have no owner of their own (Decision 1/5), so every check is requested with `resource=None`.

Unlike `add-endpoint-dependency-explorer` (which found `RBACPolicyEvaluator` only handled `.read` specially and had to extend it to also grant `.create`/`.delete` to any authenticated principal for resourceless permissions), that fix already landed generically — `RBACPolicyEvaluator.check` now treats any permission ending in `.read`, `.create`, or `.delete` the same way when `resource=None` (`core/backend/server/apps/catalog/authorization.py`). This change's new permissions get that behavior for free; no evaluator change is needed.

## Risks / Trade-offs

- **[Risk]** The direction-mapping fix (Decision 3) depends on this document's stated 2.x semantics being correct, and the actual parser that applies it doesn't exist until the follow-up import change. → **Mitigation:** this design document itself is the durable record of the verified mapping (quoted against the primary spec source), so the follow-up change's parser has an unambiguous, already-fact-checked rule to implement rather than re-deriving it — and re-deriving it incorrectly a second time is exactly the failure mode this document exists to prevent.
- **[Risk]** `channel_address + channel_protocol` grouping (Decision 2, Decision 6) can still under- or over-group if two genuinely different channels happen to share both an address string and a protocol, or if `channel_protocol` can't be resolved for a given document. → **Mitigation:** accepted for this change (exact-string, no fuzzy/semantic matching, per Non-Goals); revisit only if real seed/demo data surfaces an actual collision.
- **[Risk]** A `role` free-form per `ServiceOperationUsage` row (Decision 5) with no constraint against the operation's own `direction` could let a human record a Service as "publisher" on an operation whose direction already implies the document owner is the sole sensible publisher, producing a channel with two asserted publishers and no consumer — which may or may not be a real-world-valid shape. → **Decision (confirmed, not left open):** ship unconstrained. Multiple publishers on one channel is an ordinary real-world shape (e.g. several services fanning in to one topic) — AsyncAPI itself doesn't forbid it — so a hard rule against it would encode a business assumption the protocol doesn't make. Revisit only once real usage data (or the follow-up importer) shows unconstrained `role` actually producing confusing states in practice; adding a constraint later is cheaper than removing a wrong one now.
- **[Risk]** `operation_key`'s 2.x fallback (`channel_address + direction`, Decision 4) cannot survive a channel rename, unlike 3.0's operations-map key. → **Mitigation:** accepted and documented (Decision 4's "Known accepted gap"); not solved here.
- **[Risk]** Decision 7's cross-API channel aggregation, combined with Decision 10's `resource=None` permission grant to any authenticated principal, could leak the existence and linked-Service data of an operation belonging to a restricted-visibility `API` document to a viewer who only has access to a different, publicly-visible `API` sharing the same `channel_address`. → **Resolved as a non-issue (verified during implementation, task 3.4):** no restricted-visibility `API` concept exists anywhere in this catalog today — `catalog-auth`'s own spec makes unrestricted read for any authenticated user an explicit requirement, not a gap. There is nothing for a restricted API to leak past, so no filter was implemented; see Decision 7's "Verified during implementation" note. Revisit if a real per-entity visibility mechanism is ever introduced.

## Migration Plan

- New Django migrations in `atlas_plugin_apis` for `ApiOperation` and `ServiceOperationUsage` — purely additive (`CREATE TABLE`), no changes to existing `ApiDetails`/`ApiEndpoint`/`ServiceEndpointUsage` tables or migrations.
- No data backfill: operations and links start empty; existing AsyncAPI-typed `API` entities are otherwise unaffected (their `AsyncApiViewer.tsx` rendering keeps working as-is regardless of whether any `ApiOperation` rows exist for them).
- Rollback: reverse the two migrations (drop the new tables); safe at any point before operation data is created in a live environment, same as `Endpoint`'s migration plan.

## Open Questions

- **What does a future ingestion connector need from this model to auto-derive `ServiceOperationUsage` rows by matching `channel_address` across documents (Non-Goals)?** Not designed here; flagged only so this change's manual-link data model and REST surface aren't accidentally shaped in a way that would force a schema change for that later — a connector should be able to write through the same `POST /api/operations/{operationId}/services` surface a human uses, in bulk.
- **Does `ApiOperation` need a `deprecated` field at all?** AsyncAPI's core Operation Object has no native `deprecated` field in either 2.x or 3.0 (unlike OpenAPI's Operation Object). Left out of this change's model (see proposal.md's field list) rather than invented from a non-standard extension; revisit if the follow-up importer finds a real, common convention for it (e.g. a widely-used vendor extension) worth surfacing.
