## Why

The catalog can already say an API is `type=asyncapi` (`ApiDetails.type`), but nothing models the individual operations inside that document — `AsyncApiViewer.tsx` only renders the whole raw spec via the third-party `@asyncapi/react-component`. There's no sub-resource recording which channel an operation is on, whether the API document's own service sends to it or receives from it, and no way to say which *other* Services publish or subscribe to that same event. This change adds an `Operation` sub-resource under `API` (mirroring `add-endpoint-dependency-explorer`'s `Endpoint`) plus a manual `Service <-> Operation` link with an explicit role, so the catalog can answer "who publishes/subscribes to this event?" for AsyncAPI APIs the same way it already answers "who consumes this endpoint?" for OpenAPI APIs.

## What Changes

- Add an `Operation` model under the existing `api` kind (channel address, channel protocol, direction, operation key, operation ID, summary/description, tags, message payload), owned by the `atlas.apis` plugin. Operations are plugin-owned child data, not a registered Entity Kind — no top-level `/catalog/entities/operation/...` route, mirroring `Endpoint`'s precedent exactly.
- `direction` is a canonical `send | receive` enum (AsyncAPI 3.0's own vocabulary), spec-derived and never user-edited once imported. It deliberately does **not** store the literal `publish`/`subscribe` words from AsyncAPI 2.x documents — those terms are defined from the document's own confusing perspective (2.x `publish` means the application *receives*; 2.x `subscribe` means the application *sends* — the opposite of the intuitive reading, which is exactly why AsyncAPI 3.0 replaced them with explicit `send`/`receive`). Storing the spec-version-agnostic normalized form now means the parser change (below) has nothing to retrofit later.
- Add an Operation documentation UI: an API's detail page gains an "Operations" tab, **grouped visually by channel address** (not a flat table) — each channel address gets a section (e.g. "order.created — 1 producer, 3 consumers") with its operations nested underneath. Each operation also gets its own page (`/apis/:apiId/operations/:operationId`) with Overview / Message tabs, mirroring the existing Endpoint detail page conventions. The direction badge always renders the text "Send"/"Receive" alongside its color (not color alone), matching `MethodBadge`'s accessibility precedent.
- Add a `ServiceOperationUsage` link (Service <-> Operation), owned by `atlas.apis`, with its own create/delete API, mirroring `ServiceEndpointUsage` — with one structural difference `ServiceEndpointUsage` didn't need: an explicit `role: publisher | subscriber` field on the link itself. Unlike a REST endpoint (which only ever has one kind of consumer), an AsyncAPI channel has two distinct roles, and an operation's own `direction` is a fact about the document that declared it, not a fact about any other Service that might also touch the same channel — the two are recorded as separate fields (`Operation.direction` vs. `ServiceOperationUsage.role`) rather than one being derived from the other for linked services.
- The Operation's own document-owning Service (found via the existing `apiProvidedBy` relation — already surfaced today as `EndpointConsumersGraph.tsx`'s `providerRelation`) is never linked to its own operations through `ServiceOperationUsage`; its role is implied automatically from `direction` (`send` implies publisher, `receive` implies subscriber). Only *other* Services are linked manually, so documenting an API doesn't require redundantly re-asserting what its own spec already states.
- Add a compact "Publishers & subscribers" graph on the Operation Overview tab (React Flow, read-only), mirroring `EndpointConsumersGraph.tsx`'s endpoint-center/service-ring layout, but scoped to the operation's **channel address rather than the single operation row** — it aggregates every `Operation` (including ones on different `API` documents) that share that channel address into one graph, so a channel with a `send` operation on one API document and a `receive` operation on another still renders as one connected picture instead of two disconnected ones. This aggregation silently excludes any operation whose own `API` document isn't visible to the current viewer (design.md Decision 7) — a restricted API sharing a public channel must never leak into another viewer's graph. Plus a Linked Services management tab (search, team filter, sort, link/unlink, role picker) reusing the same consumer data.
- Operations are read-only in this change (documentation entered via Django admin/fixtures, no self-service create/edit UI) — only Service<->Operation linking is interactive, exactly mirroring `Endpoint`'s precedent. Removing an operation is soft (`status=removed`) — existing links are preserved and surfaced with a warning, never silently discarded.
- Add `operation.read`, `operationDependency.read`/`.create`/`.delete` permissions gating documentation reads and link/unlink actions.

Out of scope for this change (deferred, see design.md Non-Goals): AsyncAPI 2.x/3.0 spec parsing/import (a dependent follow-up change, mirroring how `import-openapi-endpoints` followed this change's sibling), any automatic/derived graph edges from matching `channel_address` across independently-authored API documents, AsyncAPI 3.0's `reply` (request/reply) operations, a full multi-channel topology explorer beyond the compact per-channel graph, and — unlike `Endpoint` linking's auto-`consumesAPI` behavior — linking a Service to an Operation does **not** auto-create or touch any `ComponentDetails` relation field; no `publishesEvents`/`subscribesToEvents`-style M2M exists today, and inventing one is a separate cross-plugin decision this change doesn't make.

## Capabilities

### New Capabilities
- `api-operations`: the `Operation` sub-resource of `API` for AsyncAPI documents — data model, CRUD, and documentation UI (Overview/Message tabs, channel-grouped list), independent of who publishes/subscribes to it.
- `operation-service-dependencies`: the `Service <-> Operation` link with an explicit `publisher`/`subscriber` role — its CRUD API, the auto-implied document-owner role, the channel-scoped consumers graph, and the Linked Services management tab.

### Modified Capabilities
(none — `apis-plugin`'s existing requirements are reused unchanged; `api-endpoints`/`endpoint-service-dependencies` remain OpenAPI-specific and untouched by this change)

## Impact

- **Backend**: `plugins/apis/backend/atlas_plugin_apis/` gains `models/operation.py` (`ApiOperation`, including `status` for soft-delete), a `ServiceOperationUsage` model (with `role`), new migrations, read-only views/routes under `/api/apis/{apiId}/operations/` and `/api/operations/{operationId}/...` for linking.
- **Frontend**: `plugins/apis/frontend/` gains operation pages/components under the existing `pages`/`components`/`entityDetailTabs` layout (mirroring the Endpoint components: list tab, overview tab, message viewer, consumers graph, link dialog), new routes/nav entries. Reuses the existing React Flow dependency already introduced by `add-endpoint-dependency-explorer` — no new frontend dependency.
- **Permissions**: new permission strings registered by `atlas.apis`; no change to existing ones. The channel-scoped consumers aggregation (`/api/operations/{operationId}/consumers`) additionally reuses the existing `API` visibility check to filter out aggregated operations from APIs the viewer can't see (design.md Decision 7) — this is a visibility filter, not a new permission string.
- **No breaking changes**: existing `API`, `ApiEndpoint`, and AsyncAPI viewer behavior is unchanged; this is purely additive.
