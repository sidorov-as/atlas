## Context

`FlowStepModal.tsx` (the "Add Step"/"Edit step" dialog behind both the toolbar "Add step" button in `FlowFormPage.tsx` and each canvas node's own inline "+" in `FlowCanvasEditor.tsx`) hosts two conceptually similar "pick an existing catalog thing" fields with different implementations:

- **`entity_ref`** (Actor/Team/Component/Data/API/System): `core/frontend/src/components/RefSelect.tsx`, a plain Gravity `<Select filterable>` backed by `useRefItems` → `useAsync(() => kindApi.list({ pageSize: 100 }))`. Fetches one page (cap 100) on every mount, no `loading` prop wired to `Select` despite `useAsync` exposing `isLoading`.
- **`query_ref`/`event_ref`** (API Call/Event): a bespoke `<Select filterable>` in `FlowStepModal.tsx` wired to `useEndpointSearch`/`useOperationSearch`, which debounce (300ms) and hit `GET /api/apis/endpoints/search/` / `/operations/search/` (`atlas_plugin_apis`, default `limit=20`, max `100`), with `loading` wired and a custom `renderOption`/fixed row height for two-line results.

Because `FlowStepModal` is mounted twice independently (no shared state between the toolbar and per-node entry points), and `RefSelect`'s fetch is capped at one page with no loading affordance, authors see inconsistent latency/flash behavior for what should be "the same field" — this is the change unifying that experience. A related, narrower issue: `FlowNodes.tsx`'s `EntityNodeComponent` computes a just-added step's node title as `refStatus?.title || clientDetails?.title || refName(step.entity_ref) || step.id` — before the Flow's first save, `refStatus` is absent, so the node briefly shows `refName(entity_ref)` (parsed from the ref string) and then swaps to `clientDetails?.title` once `useEntityRefDetails` resolves, if that differs.

Gravity UI's `Select` (`^7.48.1`, already a dependency) has a built-in infinite-scroll mechanism: `SelectProps.onLoadMore` plus `loading` — when `loading` is `true`, `SelectList` appends a sentinel row wrapping `SelectLoadingIndicator`, whose `onIntersect` (an `IntersectionObserver`) fires `onLoadMore` once that row scrolls into view. This is the same `loading` prop already planned for the shared loading-state treatment (Decision 2), just also used as "more pages may exist" while `Select` is idle between fetches. `atlas_plugin_apis`'s `api/schemas.py` already has a sibling pagination convention (`EndpointServicesQuery`/`OperationServicesQuery`: `page: int = 1`, `page_size: int = Field(default=20, le=100)`, returning a `Paginated<T>` shape `core/frontend/src/lib/types.ts` already defines app-wide) that the search endpoints don't yet follow. Both `ApiEndpoint` and `ApiOperation` already declare deterministic `Meta.ordering` (`['path', 'method']` and `['channel_address', 'operation_key']` respectively), so offset-based pagination across sequential requests is safe without further changes. A repo-wide search confirms `plugins/flows/frontend/src/lib/apiSearch.ts` is the only frontend consumer of `/api/apis/endpoints/search/`/`/api/apis/operations/search/`, so changing their response shape has no other call sites to update.

Investigated and explicitly rejected: a backend JSONB snapshot/cache table for picker data. Current volumes are small (entity counts per kind well under 100; Endpoint/Operation counts in the hundreds, unbounded across APIs) so query cost isn't the bottleneck — the redundant-refetch-per-modal-mount problem is fully addressed by fetching once at the page level instead. A persisted cache table would need invalidation wired through the ingestion pipeline (`plugins/ingestion/backend`, which upserts in bulk and may bypass Django model signals) plus every plugin's own entity-edit write path plus deletes — a real, cross-plugin maintenance burden for no measured performance win.

## Goals / Non-Goals

**Goals:**
- One shared visual/interaction shape (icon + primary + secondary item row, one loading-state treatment) for the `entity_ref` lookup and the `query_ref`/`event_ref` lookup inside `FlowStepModal`.
- `entity_ref` lookup data fetched fully (all pages, not capped at one page of 100) exactly once per Flow editor page visit, shared across both `FlowStepModal` mount points, instead of once per modal mount.
- An author can reach every matching Endpoint/Operation for a `query_ref`/`event_ref` search by scrolling, not just the first page's worth.
- A just-added entity-backed step's node title never visibly changes from one guess to another.

**Non-Goals:**
- Changing `core/frontend/src/components/RefSelect.tsx` or any of its other consumers (Flow's own "Home system" field, `RelationsTab`'s `TargetRefSelect`, other entity forms' owner/system fields). This change adds new, Flow-scoped code rather than modifying the shared component.
- Changing the `query_ref`/`event_ref` fetch strategy from debounced server search to a client-prefetched list — the corpus (potentially hundreds of Endpoints/Operations, unbounded across APIs) doesn't fit the "fetch everything once" model the way the bounded entity-catalog lists do. Pagination lets an author reach the full corpus without prefetching it all.
- A new backend cache table (see Context) — pagination on the two existing search endpoints is in scope; a persisted snapshot/cache layer is not.
- The Step icon picker (`IconPickerDialog`) — left exactly as-is.

## Decisions

**1. New Flow-scoped `FlowEntityCatalogContext` instead of modifying `RefSelect`.**
A React Context, provided once in `FlowFormPage` (the common ancestor of both `FlowStepModal` mount points via `FlowCanvasEditor`'s own instance and `FlowFormPage`'s own instance), fetches every `entity_ref`-backed kind's full list on mount — looping through pages via the existing `Paginated<T>` shape until exhausted, rather than requesting a single `pageSize: 100` page — and exposes `{ itemsByKind, isLoading }` to consumers. `FlowStepModal` reads from this context instead of calling `RefSelect`/`useRefItems` directly for its own entity_ref field, rendering the same combobox UI itself (so the item-row markup is shared code, not a `RefSelect` prop). `RefSelect` and its other call sites are untouched.
*Alternative considered*: widen `RefSelect`/`useAsync` itself to support "fetch all pages" and a shared cross-mount cache, used everywhere. Rejected — broadens behavior (and risk) for owner-picker fields elsewhere in the catalog that were never reported as a problem, for a fix that's only needed inside the Flow editor.
*Alternative considered*: `react-query`/`SWR` for cross-mount caching. Rejected — no such dependency exists anywhere in the codebase today; a page-scoped Context fetched once already eliminates the redundant-refetch problem without adding a new library or its conventions to the project.

**2. Shared item-row component, not a shared fetch strategy.**
Extract the existing two-line result row (`SearchResultContent` in `FlowStepModal.tsx`, already deliberately built to mirror this look per its own code comments) into a small shared component used by both the entity lookup and the endpoint/operation lookup's `renderOption`. Each lookup keeps its own data source (context-provided full list vs. debounced search results) and passes items through the same row renderer, so visual parity does not require fetch-strategy parity.
*Alternative considered*: force both fields onto one fetch strategy for "true" unification. Rejected per the Non-Goals above — the two corpora have genuinely different size/boundedness characteristics (confirmed: entity kinds are comfortably under 100; Endpoint/Operation counts scale with however many APIs/commands exist, with no fixed ceiling), so one fetch strategy would either break at scale (prefetch-all for endpoints/operations) or degrade the currently-bounded entity fields unnecessarily (debounced search for a list of 20 components).

**3. Offset pagination on the search endpoints, loaded via `Select`'s built-in `onLoadMore`.**
`ApiEndpointSearchQuery`/`ApiOperationSearchQuery` gain `page: int = 1` and `page_size: int = Field(default=20, le=100)`, matching the sibling `EndpointServicesQuery`/`OperationServicesQuery` convention already in the same file. `ApiEndpointSearchController`/`ApiOperationSearchController` return the existing app-wide `Paginated<T>` shape (`count`, `numPages`, `perPage`, `page: {number, objectList}}`) instead of a flat capped array — safe to page across requests because both models already declare deterministic `Meta.ordering`. On the frontend, `useEndpointSearch`/`useOperationSearch` (`FlowStepModal.tsx`) track accumulated `results` across pages plus the latest `numPages`; `hasMore = numPages === null || page < numPages`; the `Select` is given `loading={fetching || hasMore}` — true both while a request (first page or a subsequent one) is in flight, and, once idle, for as long as further pages remain unfetched, since `Select`'s sentinel-row-for-`onLoadMore` only renders while `loading` is `true`. `onLoadMore` is a no-op guard (`if (fetching || !hasMore) return`) before fetching the next page and appending. A new debounced search term resets accumulated `results`/`page`/`numPages` and re-fetches from page 1, using the same in-flight-request cancellation (`cancelled` flag) pattern `useEndpointSearch`/`useOperationSearch` already use.
*Alternative considered*: a static "results may be incomplete, refine your search" indicator with no pagination, triggered by `results.length === limit`. Rejected once `onLoadMore` and the existing `page`/`page_size` backend convention were found — pagination gives an author the actual data instead of just a hint to type more, at comparable implementation cost given `Select` already has the mechanism built in.
*Alternative considered*: have the backend report only a boolean `has_next` instead of the full `Paginated<T>` shape, to minimize the response-shape change. Rejected — `Paginated<T>` is already the established convention for every other paginated list in this codebase (including the sibling `EndpointServicesQuery`/`OperationServicesQuery` in this same file), and the one known consumer (`apiSearch.ts`) is being reworked in this change anyway, so there's no reason to invent a narrower one-off shape.

**4. Node-title stability: resolve before first paint using the context's already-loaded data, rather than removing the `refName()` fallback.**
Once `FlowEntityCatalogContext` has fetched the full entity list for the page (Decision 1), the node-title code path in `FlowNodes.tsx` can look up the referenced entity's real title synchronously from that already-loaded list for a just-added step, instead of falling back to `refName(entity_ref)` while a separate `useEntityRefDetails` fetch is in flight. This removes the flash because the "guess" and the "resolved" value become the same lookup, sourced from data that's already in memory by the time an author is picking a reference in the modal.
*Alternative considered*: keep `useEntityRefDetails`'s independent fetch but suppress rendering the node's title until it resolves (skeleton state). Rejected — introduces a new empty/loading state on the canvas for a value the app already has in memory via Decision 1's context, once that context exists.

## Risks / Trade-offs

- [Risk] `FlowEntityCatalogContext`'s "fetch all pages up front" could become slow if an installation's entity counts grow well past today's observed sub-100 range. → Mitigation: this is explicitly the same shape of trade-off the codebase already accepts for `query_ref`/`event_ref` staying on server search — if entity counts are later observed to grow large, the same "switch that one kind to server-side search" escape hatch applies; not a blocking concern at today's confirmed scale.
- [Risk] Introducing a second data-fetching path for entity lists (the new context) alongside the existing `RefSelect`/`useRefItems` path could drift out of sync in behavior/type shape over time since they're now two independent implementations reading the same backend list endpoints. → Mitigation: the context reuses the same `entities.ts` API client functions and `Paginated<T>` type `RefSelect` already uses; only the pagination-loop and cross-mount sharing are new.
- [Risk] Moving the "resolve title" responsibility into the context (Decision 4) could regress the fallback-to-name/fallback-to-id behavior specced for after a save, when `refStatus` should already be authoritative. → Mitigation: the context lookup is additive, used only when `refStatus` is absent (i.e. the just-added, not-yet-saved case); the existing `refStatus`-first, `step.id`-last fallback chain is unchanged for the saved/read case.
- [Risk] Changing `ApiEndpointSearchController`/`ApiOperationSearchController`'s response shape from a flat array to `Paginated<T>` is a breaking change to that endpoint's contract. → Mitigation: confirmed via repo-wide search that `apiSearch.ts` is the only consumer; it's updated in this same change, so no other call site is affected. Covered by the existing `test_endpoint_search.py`/`test_operation_search.py` backend tests, which will need updating alongside the response-shape change.
- [Risk] A rapid sequence of keystrokes (each triggering a new debounced search) racing with an in-flight page-2+ fetch from the previous term could append stale results onto the new term's list if not guarded. → Mitigation: reuse the existing `cancelled`-flag pattern already in `useEndpointSearch`/`useOperationSearch`, extended to also reset accumulated pages on every new debounced filter value, not just on unmount.
- [Risk] `Select`'s `onLoadMore` sentinel is intersection-observer-driven and could, in principle, fire again while a page fetch it already triggered is still in flight (e.g. on a fast scroll). → Mitigation: guard `onLoadMore` with an in-flight check (`if (fetching || !hasMore) return`) as described in Decision 3, so a duplicate trigger is a no-op.

## Migration Plan

No data migration (no model/column changes — only request/response shape on two existing endpoints), no feature flag — this is a UI-consistency and correctness fix behind existing routes. Land as a single change, backend and frontend together (the frontend's reworked `apiSearch.ts` depends on the new paginated response shape). Update `test_endpoint_search.py`/`test_operation_search.py` for the new request/response shape. Verify manually in the Flow editor: add a step via both the toolbar and a node's "+" and confirm identical picker behavior; add an entity-backed step and confirm no title flicker; open the query/event lookup with a broad or empty search and scroll to confirm further pages load and the loading indicator disappears once exhausted.
