## Context

This design was settled through a full grilling/domain-modeling session (transcript: `local/entities-removal.txt`, raw dialogue: `local/entities-deprecation.txt`), grounded in three research passes over openspec, docs-site, and the codebase. Key facts established there:

- There is no "Service" entity kind — `service` is one `type` value of `Component`. This document says "Component"/"entity", never "service", unless the type specifically is meant.
- Today, whole CatalogEntity kinds (System/Component/Resource/API) have exactly two lifecycle end-states: active, or hard-deleted (blocked by `validate_delete` if anything still references it). There is no soft-decommission path at all for them.
- `ApiEndpoint`/`ApiOperation` already have a narrower, one-level-down mechanism: a `status` field (`active`/`removed`), re-ingestion sets `removed` when an operation disappears from a spec and revives it (same id, same usage links) if it reappears, and a separate, orthogonal `deprecated` boolean that is purely cosmetic (never hides or archives anything).
- The concrete, already-real bug (found in `upsert.py`): when a repo's `catalog-info.yaml` stops declaring an entity it previously declared, the entity itself is never touched — it stays active forever, still locked read-only (`source_kind=yaml` rejects manual edits) — while that same ingestion pass *does* prune the entity's YAML-origin relationships. Net effect: a "zombie" entity, fully active/healthy-looking, silently missing its architecture edges, unfixable by anyone.
- Hard-deleting an entity today frees its `(kind, namespace, name)` slot instantly (verified by test) — a freed name is claimable on the very next ingestion pass.

## Goals / Non-Goals

**Goals:**
- One soft-delete vocabulary and state machine (`Removed`/`Revive`/`Purge`) for CatalogEntity kinds, unifying with — not duplicating — the existing ApiEndpoint/ApiOperation mechanism.
- Fix the zombie-entity bug: ingestion reconciles whole-entity disappearance the same way it already reconciles relationships and Endpoints/Operations.
- Guarantee a new entity can never silently inherit an old (removed) entity's identity, ownership, or history via name reuse.
- Make `removed`/`deprecated` status visible everywhere an entity is referenced (relations, Architecture Relationships, Linked Services, Flow steps/diagrams), not just on the entity's own page.
- Make destructive purge auditable, permission-scoped, and blind-spot-free (it must scan ref-string references, not just FK-backed ones).

**Non-Goals:**
- Per-table/per-column lifecycle tracking for `DatabaseSchema` facets. The facet stays a single JSON blob, fully replaced on every re-parse. Only the containing `Resource` (as a whole entity) participates in Removed/Revive/Purge. This is a real limitation, documented explicitly rather than half-shipped.
- Any change to sub-resource-level lifecycle below the container level (Endpoint/Operation already have their own `removed`/`deprecated`; nothing below *that* — e.g. individual response shapes — gets independent lifecycle).
- Read-side visibility ACLs (out of scope; `catalog-auth` already documents read as unrestricted for any authenticated user — this change does not add per-entity read gating for removed entities, it only adds a default-hidden/toggle-visible *list* behavior).
- Reworking `validate_delete`'s own dependency-check logic — it is unchanged, and now runs only as Purge's structural backstop (D14), since the standalone Delete action it used to gate is retired for System/Component/Resource/API.

## Decisions

### D1: Terminology — reuse `removed`, not a new word ("archived")
The codebase already has a word for "soft-removed, not deleted, revivable": `removed`, used by `ApiEndpoint`/`ApiOperation.status`. Introducing "archived" as a second word for a similar-but-not-identical concept is exactly the kind of ambiguity this change exists to close. **Alternative considered**: introduce `archived` as container-level vocabulary distinct from operation-level `removed`. Rejected — two words for adjacent concepts is itself a source of the "is this the same thing?" confusion the change is meant to fix.

### D2: `deprecated` and `removed` are decoupled, not staged
`deprecated` is a mutable, non-gating cosmetic flag ("still alive, going away later") that can sit on any entity independent of its `removed` status; `removed` is never a mandatory waypoint before an entity can be removed. Real decommissions aren't always announced in advance (deprecate-then-remove is a *common* path, not the *only* path). AsyncAPI-backed `ApiOperation` gets a new manual `deprecated` boolean override, since AsyncAPI has no native deprecated keyword and propagation would otherwise be asymmetric between OpenAPI- and AsyncAPI-backed operations once deprecated-propagation ships.

### D3: New identity on name reuse, never resurrection-by-name
When a name collides with an already-removed entity, three options were considered: (a) hard-block creation until explicit purge/rename, (b) resurrect the old identity (same id) under the new claim, (c) allow a genuinely new entity/id once purged, with the old one's history intact under its own id. **Chosen: (c) combined with (a)-until-purge** — a rival claim is rejected (ConflictRecord) while the removed entity still holds the name; only an explicit, permission-gated Purge frees the slot for a new identity. Ownership, team, and even what the name refers to can genuinely change between removal and reuse (e.g. name recycled by a different team after a reorg) — identity must never be inferred from name alone. This is a deliberate divergence from the ApiEndpoint/ApiOperation precedent (which resurrects the *same* row/id on reappearance) — that precedent is preserved unchanged for same-origin revival (D4), and only diverges for a *different* claimant after Purge.

### D4: Revive preserves identity; it is same-origin reappearance, not resurrection-by-name
Automatic Revive (Removed → active, same id) fires only when the *same* origin re-declares the *same* ref — a repo re-declaring a ref it previously declared, or a re-fetched spec re-including an operation it previously included. This is consistent with D3: reviving is not "a new claim happened to match an old name," it's "the same source said the same thing again." Manually-removed entities have no external source to diff against, so they additionally get an explicit human-triggered Revive action (Q1, round 3) — otherwise manual removal would be strictly more punishing than YAML removal for the same kind of mistake.

### D5: Auto-remove authority is sticky to origin
An ingestion source may only auto-remove an entity it itself created (tracked via `source_kind`/claiming repository), never a manually-created entity. A same-named YAML entity appearing while a different source's entity is active is a naming/claim conflict (existing `entity-claim-arbitration` machinery), not a takeover. Manual entities can only become `removed` via an explicit human/API action — there is no automatic staleness detection for them, since there's no external source of truth to diff against. This asymmetry is deliberate and must be documented, not silently inconsistent.

### D6: Removed keeps the name reserved; only Purge frees it
If `removed` behaved like today's hard delete and freed the name instantly, "soft-delete instead of hard-delete" would buy nothing against the name-collision confusion that motivated this change. So: `removed` reserves the name; claim arbitration treats a `Removed` entity as still claimed (new `removed_entity` ConflictRecord reason, alongside today's `manual_entity`/`other_repository`); only the new, separate, explicitly-gated `Purge` action frees the slot. This mirrors the existing "removing a plugin is reversible by default; actually destroying data is a separate, explicit action" pattern (Unavailable Entities).

### D7: Two-tier deletion, always remove-then-purge, no shortcut
Purge is reachable only from `Removed`, never directly from active — even for an entity that was created by mistake and never referenced by anything. This is a deliberate uniformity choice: one code path, one mental model, at the cost of one extra click for the "I made a mistake, nothing depends on this" case. **Alternative considered**: allow active→purge directly when there are zero references. Rejected for consistency — special-casing "never had references" doubles the code paths for a case that's already cheap via remove-then-purge.

### D8: Purge validation must scan ref-string references, not just FK relationships
`dependsOn`/`providesApis`/`consumesApis`/`owner` are real DB foreign keys (`PROTECT`), which is what today's `validate_delete` leans on. But Flow steps' `query_ref`/`event_ref` (and now `entity_ref`) are plain ref strings resolved dynamically at read time — nothing at the DB level stops deleting something a Flow still points at. If Purge only checked FK-backed relationships, it would have a blind spot that plain `validate_delete` doesn't even have today (today's delete only works by luck — everything it protects against happens to be FK-enforced). Purge validation must explicitly resolve and check ref-string-based references (Flow steps today; anything similar added later) in addition to FK relationships, and must tolerate/cascade purely `Removed`-status references while still hard-blocking on any active one.

### D9: Purge Grant is scoped per owner-Group, with a global-admin override
A group's own admins elevate specific members to hold Purge rights, scoped to entities owned by that group; a global-admin permission works regardless of grant or `source_kind`. **Alternative considered**: a single global permission cutting across all groups. Rejected — that would give every purge-capable person catalog-wide blast radius, bigger than the destructive-but-scoped action being described; scoping to the owning group keeps the permission boundary matching the ownership boundary already used everywhere else (adopt, manual writes). The Purge Grant explicitly carves out `source_kind=yaml` entities from the existing "no manual writes on YAML-managed entities" rule, the same way `adopt` already crosses that manual/yaml line for a narrow, specific purpose — this also resolves the existing tension where repository unregistration requires deleting each claimed entity individually (that path now runs Remove → Purge-with-grant).

### D10: Container-level scope only; children removed implicitly
`Removed`/`Revive`/`Purge` apply to CatalogEntity kinds (System/Component/Resource/API) and, extended for consistency, to `ApiEndpoint`/`ApiOperation`. No independent lifecycle exists below that: when a parent container is removed, its children (Endpoints/Operations) are implicitly removed with it rather than gaining their own independent container-vs-child removed state. Giving every sub-resource its own independent lifecycle doubles the state space for no real benefit. **Confirmed (2026-09-10 validation pass): this cascade is display/reference-checking-only — a child's own `status` field is NOT mutated when its parent container is removed.** This synthesizes Round 1 Q2 (answered before research revealed Endpoint/Operation already have independent `status`) with the later container+child model; it was not re-litigated verbatim in the original transcript, but is confirmed correct — it avoids spurious audit events for every child on a parent Remove, and a parent Revive doesn't require separately reviving each child.

### D11: Audit via the existing Entity Service transaction, plus a user-facing History tab
Remove/Revive/Purge are implemented as transactions through the existing Entity Service, so they get `EntityAuditRecord`s automatically, for free, with no new mechanism. But an audit trail nobody can see doesn't fix the "catalog is misleading" trust problem — so a minimal, read-only "History" tab is added to the entity detail page (who/what removed it and when, revived by whom, etc.), sourced from those same audit records.

### D12: Removed-visibility default is hidden, toggle is open to everyone
Removed entities disappear from default list/search views (matching how removed Endpoints already sit in a dedicated section separate from the default active list), with an explicit "show removed" filter open to *any* catalog viewer — not gated to the owning group. Hiding it from non-owners would undermine the whole point of archiving instead of deleting, which is to keep a truthful record visible to anyone investigating the catalog (e.g. "why doesn't this dependency resolve anymore").

### D13: Manual Remove is blocked for YAML-managed entities, same as manual edit/delete today
The transcript does not explicitly re-litigate this, but it follows directly from the existing, unchanged rule that `source_kind=yaml` rejects all manual writes "for any user regardless of group membership" (`entity-claim-arbitration`/`entity-catalog`). 
Only Purge gets an explicit, narrow carve-out (D9) — Remove does not. A YAML-managed entity can only become `Removed` via ingestion reconciliation (D5/R2-Q2), never via a manual Remove action, consistent with adopt/no-reverse-adoption being the only other place that line is deliberately crossed. 
**Confirmed (2026-09-10 validation pass)** — this was a design inference rather than a verbatim transcript answer, flagged for review in the original design; it has since been reviewed and confirmed as correct, consistent with the existing manual-write block. The same confirmation extends to manual Revive: a YAML-managed `removed` entity can only revive via ingestion reconciliation (D5), never via a manual Revive action — Revive is manually available only for entities a human could have manually removed in the first place (`source_kind=manual`).

### D14: Plain Delete is retired for System/Component/Resource/API; Remove → Purge is the only path
**Revisited after the original implementation shipped**, once the action menu was actually visible in the UI: sitting `Remove` and the pre-existing plain `Delete` side by side reads as two competing ways to destroy the same entity, and for the common "I made a mistake, nothing references it" case they *are* — Delete does it in one ownership-gated step, Remove→Purge does it in two Purge-Grant-gated steps, for the same end result. That silently undermines D7's "one code path, one mental model" — D7 only ever litigated whether *Purge itself* gets an active→purge shortcut (rejected), never noticing that plain Delete already *was* that shortcut, just left over from before this change. **Decided**: retire Delete entirely for these four kinds — no REST route, no UI affordance — so Remove→Purge is the only way to permanently destroy one of them, matching D6/D7's uniformity all the way through. `validate_delete` itself is untouched (Non-Goals) — it still runs, unchanged, as Purge's structural backstop check. **Consequence, accepted deliberately**: destroying a zero-reference entity now costs a Purge Grant, not just owner-Group membership — a real increase in the permission bar for that case, traded for one mental model instead of two. **Alternative considered**: keep Delete as a fast path for the zero-reference case, visually separated (e.g. moved into an overflow menu) from Remove/Revive/Purge. Rejected — a fast path with a *different* permission model than Purge (ownership vs. Purge Grant) reopens exactly the "which one do I use, and why do they need different permissions for the same outcome" question this revisit exists to close, no matter where the button sits on screen. Group/Actor are unaffected — they never gain the Removed lifecycle (D10) and already have no REST delete route at all (`entity-catalog`: "Group and User are read-only via API").

## Risks / Trade-offs

- **[Risk] Ingestion reconciliation is the single highest-blast-radius change here** (it changes standing behavior for every YAML-managed entity in every existing deployment) → **Mitigation**: implement and test it as its own isolated, clearly-flagged task (see tasks.md), symmetric to the already-proven Endpoint/Operation and relationship reconciliation code paths; ship it with the auto-remove-authority-sticky-to-origin guard (D5) so it cannot flip entities it doesn't own.
- **[Risk] Purge's ref-string scanning (D8) can miss future non-FK reference mechanisms if new ones are added without updating Purge's scan list** → **Mitigation**: implement the scan as a registered/extensible check (mirroring how `query_ref`/`event_ref` resolution is already an extension-point pattern in `flow-query-event-steps`) rather than a hardcoded Flow-only check.
- **[Risk] Propagating removed/deprecated status into many surfaces (relations, Architecture Relationships, Linked Services, Flow) is the largest single line item by surface area** → **Mitigation**: reuse the exact pattern `flow-query-event-steps`'s "live status" requirement and `endpoint-service-dependencies`'s/`operation-service-dependencies`'s "reflects a removed status" requirements already establish for Endpoint/Operation; this change is mostly "apply the same pattern one level up and to `deprecated` too," not new UX design.
- **[Trade-off] Always remove-then-purge (D7) costs one extra click even when nothing ever referenced the entity** → accepted deliberately for one code path / one mental model (see D7).
- **[Trade-off] DB schema per-column lifecycle stays unsupported (Non-Goal)** → accepted; documented explicitly rather than half-shipped, per the settled Q4 answer.
- **[Trade-off] Retiring plain Delete (D14) raises the permission bar for destroying a zero-reference entity** — from owner-Group membership to a Purge Grant → accepted deliberately for one destructive code path instead of two with different gates (see D14).

## Migration Plan

1. Data model: add `status` (`active`/`removed`) to `CatalogEntity` (or equivalent), default `active`; add `Purge` capability to `ApiEndpoint`/`ApiOperation` (no new `status` value needed there — they already have `active`/`removed`). Existing rows default to `active`; no backfill ambiguity.
2. Ship the ingestion zombie-entity fix (ADDED requirement in `catalog-ingestion`) as an isolated, independently-deployable/testable unit before or alongside the rest — it is the highest-priority item and does not depend on Purge/Purge Grant existing.
3. Add Remove/Revive/Purge Entity Service transactions, `ConflictRecord.removed_entity` reason, and the Purge Grant permission model.
4. Add propagation (relations, Architecture Relationships, Linked Services, Flow) and the History tab — these are additive UI/read-path changes with no data migration.
5. Rollback: every piece is additive (new state, new action, new permission, new read-path fields) except the ingestion reconciliation behavior change, which is a genuine behavior change to existing deployments — flag it in release notes as a behavior change, not silent.
