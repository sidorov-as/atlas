## Context

`flow-node-title-hierarchy` (archived 2026-09-09) added prefill-into-empty-field: picking a reference (`entity_ref`, or an Endpoint/Operation for `query_ref`/`event_ref`) fills a blank Title/Summary from the reference's own name/description, but the author can freely retype either afterward, and the fields are never resynced. That was a deliberate call at the time ("an author who has customized a step's Title/Summary should never have that silently discarded by picking a different reference"). Revisiting it: once both Title and Summary are freely overridable for any ref-backed kind, the rendered card carries no guaranteed relationship to the reference actually picked — a ref-backed node and an External node become visually indistinguishable once customized, and a reader can no longer trust that what's on the canvas matches the reference. This change removes editable Title/Summary from all three ref-backed step shapes — the six entity-backed kinds, and API Call/Event (`query_ref`/`event_ref`) — not only the entity-backed six as originally scoped (widened during implementation, see Decision 7): `query_ref`/`event_ref`'s `direction`/`channel`/`method`/`path` were never free text; they're picked, not typed, and are already a structural snapshot for a different, load-bearing reason (the offline-canvas-render invariant established in `add-flow-query-event-steps`) — Decision 7 renders Call/Event's title/subtitle straight from that same snapshot, so no live fetch is added and that invariant stays intact.

A parallel issue exists for a step's `id`: `FlowStepModal.tsx` exposes it as an editable `TextInput`, even though it's an implementation detail used only for transition wiring (`next_step`/`next_steps`). `nextFlowStepId(steps)` (`flowSteps.ts`) already auto-generates one for a new step; the JSON rail (`FlowFormPage.tsx`, Monaco, bidirectionally synced with the same `steps`) already exists as a power-user surface for exactly this kind of structural edit.

Reviewing the JSON rail while addressing `id` surfaced a real gap between spec and implementation: `visual-flow-editor`'s "Synchronized Visual and JSON modes" requirement says the canvas updates "only when the JSON parses and satisfies the supported step schema" — ambiguous about whether "schema" covers referential integrity (duplicate ids, dangling transitions, cycles, reconverging branches — everything `validateFlowSteps()` already checks) or only field shape (`parseFlowSteps()`). The implementation resolves that ambiguity as shape-only: `FlowFormPage.tsx`'s `useEffect(() => { if (parsedSteps) setSteps(parsedSteps) }, [parsedSteps])` commits any shape-valid JSON straight to the canvas; `structuralErrors` (from `validateFlowSteps(steps)`, computed on the already-committed state) is only surfaced at `handleSubmit`. This becomes a real problem once `id` is JSON-only: a rename that doesn't also fix every referencing `next_step`/`next_steps` would render a broken diagram immediately, with no feedback until Save.

Separately, reviewing the "Add Step" picker's tile colors for an unrelated reason surfaced that `FLOW_NODE_PALETTE.component` (green) has no relationship to any Component's actual canvas color (`componentTypeColors(subtype)` — service/website/library/worker map to blue/utility/normal/clear, never green) — the picker promises a color no real Component ever shows.

One more cross-change note: `flow-stale-ref-refresh` (a sibling change, scoped to `event_ref` drift on Event nodes) introduces a shared "warning icon + tooltip" component/handler for its own Event-drift indicator, designed for reuse from both `FlowNodes.tsx` and `FlowStepModal.tsx`. This change's entity_ref removed/deprecated warning (rendered by `EntityNodeComponent`, an existing, unmodified requirement in the `flow-management` capability) uses the same icon+tooltip visual pattern today. Rather than this change re-implementing that pattern a second time, it should reuse `flow-stale-ref-refresh`'s shared component — see Decision 6.

## Goals / Non-Goals

**Goals:**
- An entity-backed node's rendered title/description always matches its referenced entity's current catalog data — no author-supplied text can diverge from it.
- An API Call/Event node's rendered title/subtitle always matches its own picked Endpoint/Operation snapshot (method+path or channel+direction, plus the owning API's raw name) — no author-supplied text can diverge from it either (Decision 7).
- A step's `id` is treated as an implementation detail: auto-generated, and changeable only through the same JSON rail already used for other structural edits.
- The JSON rail's live sync to the canvas is exactly as safe as Save already is — a structurally broken edit never reaches the canvas silently.
- The "Add Step" picker's tile colors are truthful (a tile's color corresponds to what that kind can actually look like on canvas) and legible (no two adjacent tiles share a color).

**Non-Goals:**
- No live fetch added for `query_ref`/`event_ref` — Call/Event's title/subtitle come from the already-stored snapshot alone, preserving the offline-canvas-render invariant (see `flow-stale-ref-refresh` for the separate, live-fetched `event_ref` drift-detection work, which is unaffected).
- No change to Step/External — both keep fully free-text Title/Summary/label, exactly as today; this change only removes free text from the eight *ref-backed* kinds (the six entity-backed kinds, plus API Call/Event).
- No migration for already-saved ref-backed steps carrying custom Title/Summary. The catalog holds only test data right now and will be reseeded — no backfill, no compatibility shim, no deprecation window is designed here.
- No change to Component/API subtype resolution (`useEntitySubtype`, icon/color) — stays a separate client-side fetch; only `title`/`description` move onto the server-computed live-status payload in this change.
- No redesign of the JSON rail's editing experience beyond the collapsed default and the structural-validity gate — Monaco, the toggle, position-autolayout-on-missing-`position` are all unchanged.
- No re-litigating the exact tile grid order as a hard requirement — the spec states the "no adjacent same color" rule; the concrete order given here is one arrangement that satisfies it, not a contract on the literal sequence.

## Decisions

### Decision 1 — Entity-backed live title/description is computed server-side, reusing the existing `resolve_step_ref_statuses` resolution

`resolve_step_ref_statuses()` (`plugins/flows/backend/atlas_plugin_flows/models.py`) already calls `resolve_ref(ref)` for every `entity_ref` step to get `status`/`deprecated`. `title`/`description` are plain columns on that same base `CatalogEntity` row (`core/backend/server/apps/catalog/models/base.py`), not in a per-kind Details model — adding them to the same dict entry costs nothing extra: no new query, no new join. This is added unconditionally (not gated behind a staleness check, unlike `status`/`deprecated`'s original diagnostic purpose) because rendering now depends on it directly, not just as a warning signal.

Rejected: a client-side fetch (mirroring the existing `useEntitySubtype`/`useEntityRefDetails` pattern) *as the primary source*. That pattern already has a documented risk (`flow-node-title-hierarchy` design.md: "can match the wrong entity if two catalog entities of the same kind share a name differing only in case", since it resolves by a `q`-search-and-filter, not an exact ref match) and costs one fetch per distinct ref client-side instead of zero extra backend cost. Once title/description become load-bearing for every render (not just a one-time prefill convenience), the server's exact `resolve_ref()` match is strictly better and cheaper.

Refinement found during manual QA: a step just added, or just re-pointed at a different reference, in the current edit session has no `refStatus` entry yet — nothing's been saved, so the server hasn't resolved it — and would otherwise render with no subtitle (and a raw-slug title) until the next save+reload, a real regression from the old prefill-into-`step.title` behavior. `EntityNodeComponent` now falls back to `useEntityRefDetails` (the existing, previously-unused client-side fetch already built for `useEntitySubtype`'s cache) *only* when `refStatus` carries neither `title` nor `description` — a rendering-only, best-effort preview, never written into the step itself, so the wrong-match risk above only ever affects a transient, pre-save preview rather than persisted data or the read path most viewers hit.

### Decision 2 — Non-editability is enforced server-side, not just hidden in the UI

Removing the Title/Summary inputs from `FlowStepModal` for ref-backed kinds stops the visual editor from producing a step with both a ref and custom text, but the JSON rail can still hand-author one. `validate_steps()`/`_validate_step_shape()` gains a rule: a step carrying a non-empty `entity_ref`, `query_ref`, or `event_ref` together with a non-empty `title` or `summary` is rejected on save (widened mid-implementation from entity_ref-only to also cover query_ref/event_ref — see Decision 7). `parseFlowSteps()` (`flowSteps.ts`) mirrors it client-side, the same way it already mirrors the existing `entity_ref`/`external_label`/`query_ref`/`event_ref` mutual-exclusion rule. This keeps the constraint real rather than a UI-only suggestion a hand-edit can route around — consistent with why `id` (Decision 3) is left fully JSON-editable while this is not: `id` has no "correct" value the catalog can contradict, but a custom title/summary directly re-opens the exact problem (a node's rendered text not matching its reference) this change exists to close.

Rejected: silently ignoring `title`/`summary` on an entity-backed step at render time without rejecting it on save. That would still let a hand-edited JSON step carry dead, misleading text sitting unused in storage — confusing for anyone reading raw Flow JSON, and a bug waiting to resurface if a future change ever reads those fields again.

### Decision 3 — `id` stays fully editable, but only through the JSON rail

Unlike Title/Summary, `id` is not removed from the data model or made a live value — it's simply removed from the *visual* editor's surface. An author who wants a meaningful id (not `step-3`) still can, by typing it in the JSON rail. This is a UI-surface decision, not a validation rule — nothing new is rejected server-side for `id` itself; Decision 4's structural gate is what keeps a JSON-driven rename safe.

The modal's existing cascade-rename logic (`FlowFormPage.tsx::handleStepModalSave`'s `previousId` handling, which today fixes up every `next_step`/`next_steps` pointing at a renamed id) is not deleted — it simply becomes unreachable via the modal's id-changed branch, since the modal itself never changes a step's `id` anymore. Left in place rather than removed as dead code, since `handleStepModalSave` still legitimately branches on `previousId === null` (add) vs. not (edit) for other reasons.

### Decision 4 — JSON-rail sync is gated on structural validity, computed on the candidate parse, not the committed state

`validateFlowSteps(parsedSteps)` runs on the freshly-parsed candidate from the JSON text, not on `steps` (the already-committed canvas state) — today's `structuralErrors = validateFlowSteps(steps)` only ever validates what's already live, which is exactly why a bad edit reaches the canvas before anything complains. The `useEffect` that currently unconditionally does `if (parsedSteps) setSteps(parsedSteps)` gains that second condition: `setSteps` only fires when `parsedSteps` is non-null *and* `validateFlowSteps(parsedSteps)` is empty. While either check fails, the canvas keeps rendering its last good `steps`, and the rail's inline error area (already used for `jsonError`/`monacoError`) shows the specific structural error text.

This reuses `validateFlowSteps()` exactly as it exists today — same duplicate-id/dangling-transition/reconverge/cycle checks, same error message strings — just called one step earlier in the pipeline (on the candidate, before commit) instead of only after commit and only at Save.

Canvas-driven edits (drag-connect, the modal's own add/edit/remove/retype flows) are unaffected: they already can't produce a structurally invalid result today (drag-connect already rejects a bad connection inline per the existing "Visual editor structural feedback" requirement; the modal's own id field is gone per Decision 3, so it can't introduce a duplicate id or a dangling target either). The new gate is specifically closing the JSON-rail path, the one path that can currently produce a structurally broken `steps` array with no immediate feedback.

Rejected: keep validating only at Save (status quo). Explicitly rejected — the whole point raised is that a JSON-driven id rename should fail loudly and immediately, not render a broken diagram first.

### Decision 5 — Picker color fix changes one shared constant for System, and a picker-only constant for Component

`FLOW_NODE_PALETTE.system` drives both the picker tile and the actual canvas color for System (no subtype system exists for System, unlike Component/API) — changing it from `info` to `success` changes both consistently, with nothing further to keep in sync. `FLOW_NODE_PALETTE.component`, by contrast, is confirmed (by grep) to have exactly one call site: `TILE_COLORS.component` in the picker. `EntityNodeComponent`'s canvas color ternary for kind `'component'` always evaluates `componentTypeColors(subtype)`, never falling through to `FLOW_NODE_PALETTE.component` — so changing that one constant from `success` to `info` only changes the picker tile; every real Component's canvas color (subtype-driven) is untouched.

The grid reorder (Decision — see proposal's Part E layout) is a `KIND_TILES` array reorder in `FlowStepModal.tsx`, no change to the grid's CSS (still `repeat(2, 1fr)`).

### Decision 6 — Entity removed/deprecated warning reuses `flow-stale-ref-refresh`'s shared warning component, not a second implementation

The existing entity_ref removed/deprecated warning indicator (unchanged requirement, `flow-management` capability) and `flow-stale-ref-refresh`'s new Event direction/channel-drift warning are the same visual pattern: an icon on the canvas card with an explanatory tooltip. `flow-stale-ref-refresh`'s design extracts this into one shared component/handler consumed by both `FlowNodes.tsx` and `FlowStepModal.tsx`. This change's entity-backed rendering work (`EntityNodeComponent`, tasks.md section 5) should call that same shared component for its removed/deprecated warning rather than writing a second, parallel implementation — avoiding duplicate code and visual drift between the two warning styles over time.

This is the concrete reason to implement `flow-stale-ref-refresh` before this change: by the time `EntityNodeComponent` is touched here, the shared component already exists to import. This is a soft dependency, not a hard one — if the order is reversed or the changes land independently, `EntityNodeComponent` simply keeps its current, already-working inline implementation; the consolidation becomes a small follow-up rather than a blocker.

### Decision 7 — API Call/Event lose editable Title/Summary too, rendering straight from their own `query_ref`/`event_ref` snapshot (scope widened during implementation)

Found during manual QA of the entity-backed rollout: leaving Call/Event's Title/Summary freely editable reopens the exact problem this change exists to close, just for two more kinds — a Call/Event node's rendered text can diverge from what was actually picked (an Endpoint/Operation), the same way an entity-backed node's could before this change. `FlowStepModal.tsx` drops the Title/Summary inputs for `call`/`event` the same way it already does for the six entity-backed kinds (Decision 2's rejection rule, and `handleSave`'s zeroing, both widened from `entity_ref`-only to `entity_ref || query_ref || event_ref`).

Unlike entity-backed rendering, this needs no live fetch and no `refStatus` payload change: `query_ref`/`event_ref` already snapshot everything a title needs (`method`+`path`, or `channel`+`direction`) at pick time, precisely because they're a structural snapshot for the offline-canvas-render invariant (`add-flow-query-event-steps`) — the same reason they were originally scoped out of this change (see Context). `CallNodeComponent`/`EventNodeComponent` (`FlowNodes.tsx`) now compute title as `` `${method} ${path}` ``/`` `${channel} (${direction})` `` directly from the step's own `query_ref`/`event_ref`, replacing the old `step.title || step.id` read. This is strictly simpler than the entity-backed case (Decision 1): no `refStatus` dependency, no unresolved/new-step fallback gap (Decision 1's client-fetch refinement doesn't apply here — the snapshot is always present once `query_ref`/`event_ref` is set, and kind-picking already requires it before Save is enabled).

Rejected: leaving Call/Event out of scope, as originally designed. Once the entity-backed six could no longer show divergent text, an author could still make a Call or Event node say anything — an inconsistent carve-out with no principled reason once actually seen next to the fixed kinds in the running app.

**Addendum — subtitle is the picked Endpoint's/Operation's own `summary`, also snapshotted at pick time, not just the owning API's name.** Initially the subtitle was only the owning API's raw name (`refName(api)`) — but that's a weaker signal than what the old free-text prefill used to show (the Endpoint's/Operation's own `summary`, e.g. "Create a booking"), and `ApiEndpoint`/`ApiOperation` already carry that field. Rather than lose it, `query_ref`/`event_ref` gain an optional `summary` key, captured the same way `method`/`path`/`channel`/`direction` already are — at Select `onUpdate` in `FlowStepModal.tsx`, from the search result's own `endpoint.summary`/`operation.summary` — with no live fetch added (same offline-render invariant as the rest of this decision). `_validate_ref_shape()`/`isRefShape()` (`models.py`/`flowSteps.ts`) treat it as optional and empty-string-allowed (unlike the required keys), since the source `summary` field is itself optional (`blank=True`). The card subtitle becomes `queryRef.summary || refName(queryRef.api)` (and the `event_ref` equivalent) — falls back to the API name only when the picked Endpoint/Operation genuinely has no summary of its own.

**Addendum's addendum — the Monaco JSON-rail schema needed the same `summary` addition, separately.** `flowStepSchema.ts` (the schema `FlowFormPage.tsx`'s Monaco editor validates the JSON rail against) is a third, hand-maintained mirror of the same `query_ref`/`event_ref` shape — alongside `parseFlowSteps()` and `models.py`'s `_validate_ref_shape()` — and nothing enforces the three stay in sync. Updating `parseFlowSteps()` for the optional `summary` key above did not update this one; a user opening the JSON rail on an already-saved, already-valid Flow with a `summary` on its `query_ref` saw Monaco reject it inline ("Property summary is not allowed"), even though parsing and saving it both worked. Fixed by adding the same `summary: { type: 'string' }` (not `required`) to `queryRefSchema`/`eventRefSchema`, plus a regression test asserting both schemas declare it — this file has no other test coverage today (Monaco itself is mocked out in `FlowFormPage.test.tsx`), so nothing else would have caught this drift.

### Decision 8 — Extend `flow-stale-ref-refresh`'s existing drift machinery to cover `summary`, on both `query_ref` and `event_ref`

Found by the user, manually editing an Operation directly: a Flow step's `event_ref.summary` had drifted from the live Operation's `summary`, and nothing anywhere flagged it — not the canvas card, not the modal, not even a console warning. `flow-stale-ref-refresh` (archived 2026-09-11) built exactly this detect-and-refresh machinery, but scoped to `event_ref.direction`/`event_ref.channel` only, because at the time `summary` was not part of either snapshot at all — it's this change's own Decision 7 addendum that introduced it. Once introduced without a matching drift check, `summary` became a second field (after `direction`/`channel`) that can silently disagree with live data with zero signal — the exact class of bug `flow-stale-ref-refresh` exists to close.

Extend `resolve_step_ref_statuses()`'s existing `event_ref` comparison to also diff `summary` against the resolved Operation's current one, independently of the `direction`/`channel` comparison (an Operation's summary can change on its own, or together with direction/channel, or not at all — three independent outcomes, not one bundled with the others). Also add a symmetric comparison for `query_ref`, which had none before — previously correct, since `method`/`path` cannot drift by construction (Decision 6 of the archived change), but `summary` carries no such upsert-identity guarantee on `ApiEndpoint` either, so the same drift risk applies there for the first time.

This reopens Decision 6 of the archived change ("Query/Call nodes are unaffected... no drift check, no `↻` control"), narrowly: a `query_ref` still cannot drift on `method`/`path`, so that half of Decision 6's reasoning is untouched; only the conclusion "no drift check at all" no longer holds, since it implicitly assumed `query_ref`'s only fields were the drift-proof ones.

Both the `live` payload shape and the presence-based signal convention are unchanged from the archived change's own Decision 2 — `summary` is just one more independently-optional key alongside `direction`/`channel_address`, so a caller already handling "some subset of these keys might be present" needs no new branching, only the additional field.

Rejected (again, and for the same reason as the archived change's own Decision 1): a `summary`-drift check based on comparing `updated_at`/a revision counter rather than the field directly — the importer's own doc-fields set already includes several fields unrelated to `summary` (`tags`, `message`, `channel_protocol`, …), so a timestamp-based check would false-positive on unrelated changes; direct field comparison is exactly as cheap and has no such risk.

### Decision 9 — The canvas card's `↻` applies the refresh directly, no modal; the modal's own `↻` (opened normally) is unchanged

Found by user review: the canvas `↻` control (Decision 8/flow-stale-ref-refresh) opened the edit modal pre-filled with live values, requiring the author to then click the modal's own Save — an extra round trip to commit a change that's already exactly as reversible as any other canvas edit (a drag, a delete, a reconnect): none of those go through the modal, and none of them are persisted to the backend until the whole Flow is saved. `removeSteps` (the node's delete "×") is the precedent already in this file — a single-purpose icon button that mutates `steps` immediately, with "don't save the Flow" as its only undo.

The canvas `↻` now calls a new pure helper, `refreshStepRef(steps, stepId, live)` (`flowSteps.ts`, alongside `addTransition`/`removeTransition`/etc.), directly from `FlowCanvasEditor`'s `onChange`, bypassing `onEditStep`/the modal entirely. This removes the `{refresh: true}` option `onEditStep` used to carry, and the `autoRefresh` prop/effect it drove in `FlowStepModal` — both now dead, since nothing sets them.

The modal's *own* `↻` (shown next to the Operation/Endpoint select when a step happens to be open in the modal and its ref is stale) is intentionally unchanged: it still only writes to in-memory form state via `refreshEventRef`/`refreshQueryRef`, committed only by the modal's explicit Save. Inside the modal, other fields may be mid-edit at the same time (e.g. switching kind, or — before this change existed — Title/Summary), so an immediate-apply-on-click there would risk committing an unrelated in-progress edit alongside the refresh; on the canvas, refreshing a step's ref is the *only* thing that click does, so there's nothing else to accidentally commit.

Rejected: keeping the canvas `↻` routed through the modal, just skipping the "click Save inside the modal" step programmatically (i.e. auto-save on open). This would still pay the cost of opening/closing a dialog for a single-field mutation, and would make the canvas's own `↻` behave differently from every other single-purpose canvas control (delete, drag) for no benefit — the modal has nothing left to do once the refresh is the only edit being made.

## Risks / Trade-offs

- **[Reopens a one-day-old explicit decision]** `flow-node-title-hierarchy`'s free-text Title/Summary was adopted deliberately, specifically to never discard an author's typed customization. This change reverses that for all eight ref-backed kinds (the six entity-backed kinds, plus API Call/Event). Accepted: the reasoning that justified free text (don't silently discard typed text on reference *change*) doesn't extend to "text should be freely divergent from the reference at all" — and the catalog holds only test data, so nothing is actually discarded by this reversal.
- **[Losing in-modal cascade-rename for `id`]** Today, renaming a step's id in the modal auto-fixes every referencing transition. Once `id` is JSON-only, a rename requires the author to fix references by hand (or accept the immediate, blocking error from Decision 4 until they do). Accepted: replaced by *visible, immediate* feedback rather than *silent* auto-fix — arguably safer, since auto-fix could paper over an author's mistake (e.g. renaming the wrong step) as easily as it fixes the intended one.
- **[Picker recolor is a visible, if cosmetic, change]** Anyone with muscle memory for "Component = green" in the picker sees blue instead. Accepted: the green was never true of any actual Component on canvas; this trades a memorized-but-wrong association for a correct one.
- **[Duplicate-id-via-JSON now surfaces as a live rail error rather than only at Save]** An author pasting a large hand-edited `steps` block with an internal inconsistency now sees the error immediately rather than after finishing and clicking Save. Accepted as the explicit point of Decision 4, not a side effect to mitigate.
- **[Soft dependency on `flow-stale-ref-refresh`'s shared component]** If that change lands after this one, or not at all, `EntityNodeComponent`'s removed/deprecated warning keeps its current implementation unchanged — nothing here requires the shared component to exist. Accepted: Decision 6's reuse is an opportunistic cleanup enabled by sequencing, not a prerequisite this change depends on to be valid.

## Migration Plan

No database migration. No API/manifest change. Existing ref-backed steps whose stored `title`/`summary` are non-empty simply stop being rendered/editable for those fields going forward — the catalog holds only test data, which will be reseeded rather than migrated; this is not designed as a general backward-compatible transition.

1. Backend: `resolve_step_ref_statuses()` — add `title`/`description` to the `entity_ref` dict entry (Decision 1).
2. Backend: `validate_steps()`/`_validate_step_shape()` — reject `entity_ref`/`query_ref`/`event_ref` + non-empty `title`/`summary` (Decision 2, widened by Decision 7).
3. Frontend: `parseFlowSteps()` (`flowSteps.ts`) — mirror the same rejection rule.
4. Frontend: `FlowStepModal.tsx` — remove Title/Summary inputs for entity-backed kinds and API Call/Event (Decision 7); remove their now-dead Endpoint/Operation-selection prefill calls; remove the `id` input for every kind; `KIND_TILES` reorder; `TILE_COLORS` picks up the palette change automatically.
5. Frontend: `flowNodePalette.ts` — swap `FLOW_NODE_PALETTE.system`/`.component` (Decision 5).
6. Frontend: `FlowNodes.tsx` — `EntityNodeComponent` renders title/subtitle from the live `refStatus` entry, falling back to a client-side fetch when no `refStatus` entry exists yet (Decision 1's payload and refinement), not `step.title`/`step.summary`; `CallNodeComponent`/`EventNodeComponent` render title/subtitle computed from their own `query_ref`/`event_ref` snapshot (Decision 7), not `step.title`/`step.summary`.
7. Frontend: `FlowFormPage.tsx` — `isEditorOpen` default to `false`; JSON→canvas sync effect gated on `validateFlowSteps(parsedSteps)` being empty (Decision 4); surface the structural error inline alongside the existing `jsonError`/`monacoError` display.
8. Backend: `seed_booking_demo.py`'s `FLOWS` fixture — strip `title`/`summary` from every entity-backed/query_ref/event_ref step (found necessary during manual QA: the existing seed data predated this change and no longer validates).
9. Verify: existing `visual-flow-editor`/`flow-management` spec-scenario suites pass for every scenario not directly superseded by this change's deltas; new scenarios pass; a Flow with pre-existing ref-backed steps that had custom title/summary still loads and renders (using derived data instead), without erroring.

Rollback: every step is an independently revertible code change; no data to restore.

## Open Questions

- Exact inline-error UI treatment for a JSON-rail structural error (reuse the existing `jsonError` banner styling verbatim, or a visually distinct variant) — left to implementation.
- Whether `title`/`description` on the live-status payload should be omitted (rather than empty-string) when the entity itself has a blank title/description — mechanical, resolved during implementation; either way the frontend's title fallback chain (live title → client-fetched title → entity's raw name → `step.id`) already handles it.
